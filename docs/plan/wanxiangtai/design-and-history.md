## 2. 目标与边界

### 2.1 目标

让多个预设实例作为团队，为同一任务进行讨论、决策、独立执行和成果集成，并在独立的万象台桌面呈现组织与运行过程。

业务闭环：

```text
创建任务并声明验收条件
→ 校验项目来源及文件范围
→ 创建固定快照 S0
→ 调度者从已有预设创建团队
→ 按议题讨论、确认或逐级裁定
→ 执行实例在独立 work 中工作
→ 冻结交付
→ 指定集成团队合并并验证
→ 发布新快照 S1
→ 需要的实例在阶段边界显式更新
→ 用户确认具体差异后回写原项目
→ 调度者提议、用户确认结束
→ 实例退役，历史保留
```

## 4. 领域、协议与持久化方案

### 4.1 组织和身份

建议一期使用：

```text
用户（非 AI）
└─ 调度者 root chat
   ├─ 团队A记录 → 组长 chat → 成员实例 chat
   └─ 团队B记录 → 组长 chat → 成员实例 chat
```

- 团队容器是记录及组长会话，不额外生成无执行职责的容器 chat。
- 一层嵌套定义为调度者可以创建团队，团队不能继续创建子团队。
- 成员一期通过组长申请更多人手，不直接派发下级；普通工作台的既有递归不受影响。
- 业务 taskId 沿用已有 conversation task 语义，不与 spawn taskId 混为同一个 ID。
- teamId、instanceId、sourceId、snapshotId、topicId、discussionId、proposalId/revision、deliveryId、operationId 各有独立用途。
- 人物名称、皮肤称谓和实例编号都是显示信息；目录和消息路由按稳定身份。
- 同角色当前对话位的作用域为 teamId＋角色稳定 ID，跨团队不会相互顶替。
- 首个实例与后续编号均保持稳定，退役后不重排；归档复用原实例，新建使用新 ID。

### 4.2 数据归属

- 系统数据库：任务、团队、实例、会议、议题、决策、待办、操作和投递状态。
- `.agent/project.yaml`：项目配置事实来源；任务创建时保存配置版本。
- 项目文件：快照、执行目录、交付冻结内容和回写恢复数据。
- manifest：不可变文件清单、哈希和映射；不是可独立改写的第二套业务状态。
- 原消息正文继续使用已有历史存储；内存运行句柄和 UI 状态不是恢复事实源。
- 业务状态＋待投递记录在系统库同事务写入；跨消息库投递通过唯一 deliveryId 幂等处理，不宣称跨库天然原子。

文件发布采用 `preparing → 临时目录 → 校验 → 发布目录 → ready`。崩溃后根据 operationId 和清单补完或保持失败；执行中原始工作目录不自动删除。

## 5. 项目、快照和独立工作空间

### 5.1 目录结构

```text
<主项目>/
  src/
  docs/
  .agent/
    project.yaml                 项目配置，可随源码管理
    tasks/                       运行数据，排除快照与提交
      <任务ID>/
        manifest.json
        snapshots/<快照ID>/
          manifest.json
          files/<来源ID>/<项目相对路径>
        instances/<实例ID>/
          work/
          deliverables/
        integration/work/
        operations/<操作ID>/
```

- 默认在主项目内，不能静默移到外部；容量不足可由用户调整路径或预算。
- 不平铺文件；同名通过 sourceId＋relativePath 区分。
- 短目录 ID 必须有唯一约束，碰撞重新分配；角色改名不移动目录。
- 创建时验证 .agent 内已有未知数据，不覆盖、不自动接管别的工具目录。
- `.agent/tasks`、系统运行目录和 Git 元数据不进入来源快照。
- 项目配置由服务读取，模型凭据留系统；实例只获得与任务相关的有效配置/指引。
- 多来源在主项目 .agent 中组织，回写时逐来源定位原目录；路径规范化、大小写、符号链接与 Windows 长路径需预检。

### 5.2 来源与配置

项目配置包括 sources、include/exclude、prepare、validation、预算、预设候选范围、项目指引及交付约定。不能扩大系统安全权限。

Git 来源纳入当前存在的已跟踪文件与未忽略新文件，保存已删除跟踪文件的基线状态；普通目录按明确规则枚举。用户可以补选必要文件。依赖/构建产物不默认为源码；对被排除且影响构建的文件给出说明入口。

系统凭据和运行目录不得因“全量复制”混入。特殊文件、外部链接、子模块及必须的本地数据先预检；无法保持语义时阻止发布而不是静默跳过。

### 5.3 初始快照算法

1. 冻结配置、来源和纳入清单；估计文件量与空间。
2. 记录 preparing，创建任务管理范围内的临时目录。
3. 逐文件复制并计算内容哈希、大小、类型及必要属性。
4. 校验复制前后源是否变化；对变化项最多重试两轮。
5. 持续变化时停止发布，提示暂缓外部修改后重试。
6. 校验目标与清单，发布不可变 S0 并登记 ready。

发布后快照不会被原项目后续修改影响。普通复制只保证发布后稳定，不提供严格的跨文件瞬时快照承诺；必须在界面和文档说明创建区间与变化检测限制。

### 5.4 实例读取与执行

实例读取 = 固定基线＋自身修改；不得自动读取其他团队或原项目最新内容。

- 纯讨论实例按需提供资料、议题记录和交付目录。
- 执行实例从固定快照完整复制本次选定源码，准备成功后运行模型工具。
- 不使用可写源码硬链接，不以 worktree 等同零复制。
- 一期普通复制是基础实现；写时复制、内容去重和虚拟文件系统是后续优化。
- 任意命令的独立构建需要可用文件树；不能仅靠 read_file/write_file 路径代理就声称 shell 也有合并视图。
- 缺文件时不得回读实时原项目；应形成范围更新和新快照，再显式采用。
- 文件工具、搜索、cwd、shell 绝对路径及链接都遵守实例项目范围；必要系统运行库按既有沙箱能力处理。
- 实例复制不包含原仓库完整 Git 历史；依赖仓库历史的验证命令必须在项目预检中识别并报告不满足条件。

### 5.5 依赖与容量

执行实例依照锁文件和项目命令独立准备依赖，不直接共享可写 node_modules、虚拟环境或构建目录。下载缓存可在现有权限允许时复用，不通过符号链接绕过沙箱。

容量分开管理：实例派发硬上限、模型请求配额、工作区准备并行度、磁盘预留。配额不足排队不占模型槽位；派发硬上限按 D9 明确失败。归档释放运行缓存，但不等于释放所有磁盘。

准备状态：`requested → queued → preparing → ready / failed`。ready 之后可 updating 或 archived。准备失败和取消必须释放预留，临时半成品不能作为执行目录。

## 6. 成果、集成、阶段更新与回写

### 6.1 交付冻结

每次交付保存实例/团队、基线、决策版本、文件增删改、哈希、验证命令/环境/结果、未解决问题及接收责任方。

在安全边界暂停写入后冻结交付；继续修改生成新版本。文本、二进制、空文件和删除分别表达；重命名一期可标准化为删除＋新增。交付不包含随意生成的依赖或缓存。

### 6.2 集成

集成团队由调度者指定，一个集成目标串行接纳交付：

```text
交付基线 + 交付内容 + 当前集成状态
→ 三方比较/合并
→ 冲突处理
→ 关联验证
→ 发布不可变 S1
```

不同路径可直接合并；同文本三方处理；二进制、删除/修改及无法自动处理的冲突明确上报。没有文件冲突也要验证语义。过期决策依据的交付先复核影响，不能绕过决策版本检查。

### 6.3 阶段边界更新（已确认）

- 旧实例保持 S0，新任务可选 S1。
- 需要 S1 时保存自身修改，以 S0/自身修改/S1 在候选目录做三方更新。
- 成功后在没有模型/工具执行和未完成审批责任的安全边界切换目录。
- 失败保持原目录和修改。
- 切换后通知已变更基础和需重验的工作。
- 更新不重排实例编号，也不自动创建新克隆体。

### 6.4 回写

1. 固定最终集成版本，比较 S0、集成结果和当前原项目。
2. 保留无关用户修改；冲突先处理。
3. 展示具体增删改和验证结果，确认绑定候选版本/文件预期哈希。
4. 应用前重新校验；原项目变化使确认失效。
5. 逐文件备份与应用，写恢复日志；失败依据日志恢复。
6. 恢复时若文件又被用户改变，停止自动覆盖并给出待处理项。

不承诺多文件/多目录瞬时原子写入，不采用“最后写入覆盖”。回写确认与结束确认独立记录，可提供“应用成功后结束”显式选项；应用失败不得结束任务。

## 7. 讨论、共识、决策与有限上下文

### 7.1 议题和会议

议题保存问题、完成条件、依赖决策、候选、异议和下一步；讨论是推进议题的一次活动。小组保留关联会话消息，正式会议有公共流，两者均有持久控制状态。

完整历史供用户查询；默认只向参与者注入相关发言、结果、异议和依据引用，不广播所有工具输出。

### 7.2 回合与等待

- 组长只有一个活动讨论，其他邀请排队。
- 未占齐所需参与者不部分锁定；不同组长的会议可以并行。
- 每轮记录必需回复者集合，按轮次和参与者去重。
- 等待回复时释放模型请求配额。
- 父等子期间保留与任务相关的澄清处理通道。
- 新阻塞边形成环时拒绝并上报，轮数上限不是死锁处理。
- 用户暂停/取消走确定性控制，不等待模型同意。
- 超时/退出导致 blocked 或 cancelled，不自动产生同意或成功。

### 7.3 共识与授权

同意绑定 proposalId＋revision；新提案版本不能继承旧同意。必需组长一致通过才形成共识。主持方可关闭会议，但关闭不代表提案生效。

僵局交调度者在既有授权内裁定，范围/预算/用户偏好等无依据问题上报用户。裁定保留人、依据、范围与异议；下游仅按有效结论开工。

保留 ask_user_question 用户直达语义，新增向上澄清能力。安全审批永远走现有用户审批通道。用户可指挥任一实例，但仍通过统一业务控制；Agent 同层通信权限不因此扩大。

### 7.4 上下文三层

| 层           | 内容和用途                                             |
| ------------ | ------------------------------------------------------ |
| 完整历史     | 原消息、工具结果、提案与审批历史，持久保存并分页回忆   |
| 有效任务记录 | 当前目标、强约束、有效决策、议题、交付、待办与消费位置 |
| 当前上下文   | 本角色、本轮议题所需记录、证据和近期消息，受预算约束   |

调度者常驻目标/分工/阻塞，组长常驻团队任务/接口/成员摘要，执行成员常驻子任务/约束/输入版本，集成团队常驻交付/依赖/冲突。

每次模型请求前在最终消息和工具定义层计量，计入输出与安全预留。提前压缩，有界工具结果，按页回忆。没有合适 tokenizer 时用保守估计并校准服务商 usage，不以字符数/4 作为可靠硬限制。

已有事实和决策按 ID/版本重载。压缩不能修改已生效决策，也不能丢失异议、未处理消息、待办、成果版本或工作区基线。必需材料仍超预算则拆议题或阻塞，禁止静默丢约束。历史索引本身同样有界，不能随着代际数无限填满 system prompt。

### 7.5 压缩与接替

普通压缩保持 instanceId、chat 和 work。新实例接替需交接目标、验收、决策版本、待办/待回复对象、基线/成果及事件消费位置；待交接完成后转移后续路由。根会话主线切换和成员接替分别建模。已退役/旧纪元不能因界面唤醒恢复。

## 8. 生命周期、恢复与任务结束

分别管理：

- 运行：排队、执行、等待同伴、等待上级、等待用户、暂停、失败、空闲。
- 展示：台上、休息室、归档。
- 资格：可执行、退役。
- 当前对话位：是/否。

休息室只接收无执行、无排队、无会议/澄清/审批责任且非当前对话对象的空闲实例。被顶替但仍工作者保持可见。归档保留可恢复上下文，退役保留只读历史。

恢复顺序：配置及纪元→文件操作/快照校验→组织→待投递消息→讨论等待→用户待办→可执行队列。UI 动画不参与恢复判断。结果不明的副作用不自动重放。

结束检查：集成和必要验证完成，未解决事项明确展示，没有未处理的交付或必须继续的任务。调度者提议，用户确认后退役。归档/结束不自动删除执行目录、快照或交付；磁盘清理另设显式操作，校验引用和目标路径后才执行。

## 9. 桌面与交互设计

- 独立浏览器/Electron 入口，可从任务中心定位。
- 创建时显示目标/验收、后端路径、来源范围和空间、候选预设、调度者、资源预算与皮肤；缺前置禁用并解释。
- 根桌面显示团队；下钻显示成员并提供返回/面包屑。全局运行栏始终列出所有正在执行或承担等待责任的实例，可滚动并定位。
- 人物显示角色、编号、团队、任务摘要、真实状态、基线入口和待办。
- 气泡展示近期内容，完整历史进详情面板；审批/裁定可追溯到来源实例。
- DOM 处理文字/工具/审批，Canvas 仅装饰；动画完成不触发业务完成。
- 皮肤整包词表＋场景模板，专名可覆盖；每任务保存具体版本，切换保留语义区域与锚点。
- 新区域默认直角、非标题字重400、中文正文至少12px，使用项目主题 token。
- 同类可采用的称谓示例：公司“用户/总裁办/部门/外派实例/会议室/休息区”；皇权“皇帝/议政处/府衙/分身/议事厅/偏殿”；神话“上帝/中枢/神殿/化身/议席/仙居”；国家“用户/协调中心/部门/执行实例/联席会议/待命区”。语义键和通用解释固定，静态文案不改变角色权限。
- 归档、退役、回写、基线更新均说明含义、依据和后果。按钮操作携带稳定 ID 与版本。
- 不可见桌面停止装饰 rAF，继续同步事件；支持减少动态效果、缩放重排、恢复默认锚点。
- 纯展示组件 props/emits，controller 连接 application public；不建只有透传用途的包装层。

| 角色           | 责任                                                         |

## 1. 原始需求（用户原话整理）

### 1.1 需求背景

用户提出分析一种情况：基于现有设计，实现**跨预设交互**——分别预设了「开发团队」和「产品团队」时，允许产品团队与开发团队之间互相通信，实现 **Agent 预设之间的通信方案**。

### 1.2 核心意义

基于某个预设创建会话，并允许创建更多的子会话。具体机制：

1. **角色与层级管理**：需要一个角色负责创建预设会话（候选：Cherry、Nexus、或再创建一个预设的上层）。它能够创建某个预设的实例，让该预设负责一个任务，并让多个预设为了实现某个任务而互相讨论。
2. **讨论规则**：每个预设之间的角色允许互相讨论，但**禁止跨层级进行讨论**。
3. **实际应用示例**：
   - (a) 开发团队：讨论开发实现细节；
   - (b) 产品团队：讨论需求交互细节；
   - (c) UI 团队：讨论显示交互细节。
   - 讨论权限：产品和 UI 之间可以互相讨论，UI 和前端之间可以互相讨论，产品和后端之间也可以互相讨论。最后，产品或全团队一起互相讨论，在达成一致后输出结论：
     - 产品团队：开始书写文档；
     - UI 团队：开始规划交互细节；
     - 开发团队：基于这些内容进行开发。

### 1.3 前端交互层的原始设想

前端交互层**不再使用现有的工作台**（绘制一棵树或一张图，或者是极简模式）这种方案，而是给定一个**桌面**：

- (a) **角色展示**：创建若干个人物（可用颜文字或某些文本替代），每个人物带角色标签，将大量名称和头像排版在整个页面上；
- (b) **内容显示**：在每个人物身上用最早设计的 **pet 显示方案**，不停显示他们的思考和正文内容；
- (c) **工具调用**：使用**极简模式的协议**不停交互；涉及用户确认时，在头像上用气泡框显示；
- (d) **讨论显示**（用户点名需详细讨论）：内容汇总后角色之间互相讨论——如何显示讨论（绘制连线、角色互相移动靠近对话等）？还是用 canvas 绘制一整套房间内移动交互的画面（但前端 UI 层可能做得比较重）？

### 1.4 过程要求（用户明确声明）

1. **严禁猜测**：不进行猜测，不基于自己的考量预设实现逻辑；
2. **频繁沟通**：频繁对话，实现完整的交互细节分析与总结；
3. **反复讨论**：确认前一直反复讨论所有实现细节；
4. **确认后执行**：头脑风暴后由用户提出「已确认」（或由 AI 决定），所有细节无异议后再写实现计划文档。

## 2. 现状事实基础（讨论前从代码确认，非推测）

以下事实来自 `src/agent/builder.ts`、`src/agent/sense/spawn.ts`、`src/agent/spawnBroker.ts`、`src/service/chat/wake.ts`、`web/src/features/agent/settings/tabs/agent/PresetsTab.vue` 等现有实现：

5. **spawn 允许同角色多实例**：主 agent 可对同一角色 type 派发多个并行实例。
6. **配置生效约束**：配置保存后服务重启才生效（PresetsTab 明示「保存后服务自动重启后生效」）。
7. **前端**：工作台三形态（树/图/极简）、pet 显示方案（PetSprite/PetBody/思考流/光效等组件）、审批气泡、spawn 渲染器均已存在，可复用素材多。

## 3. 讨论过程全记录（按议题轮次）

> 记录格式：议题背景 → 我给出的候选方案与利弊 → 用户的选择/原话要点 → 落定决策。**所有候选方案均保留**，供复审时评估是否有更优选择。

### 议题 1：跨预设通信的身份、层级、人物粒度（首批三问）

**背景**：协议与交互设计的三个根本分歧点。

**候选方案**：

- 通信身份：① 仅组长（leader）作为团队唯一对外接口；② 团队内任意角色可对外发言；③ 先听分析再定。
- 层级结构：① 三层（调度者/团队/成员，同层互聊、上下层只能指挥/汇报）；② 两层（调度者 + 团队黑盒）；③ 开放讨论。
- 人物粒度：① 每预设实例一人；② 每角色一人；③ 先讨论。

**用户选择**：通信身份 = **仅组长**；层级 = **三层：调度者/团队/成员**；粒度 = 还没想好，先讨论。

### 议题 2：人物粒度分析 → 用户给出克隆体雏形与多实例疑问

**我给出的分析**：

- 方案 A（每预设实例一人/组长化身）：与「组长唯一对外」语义自洽；pet 方案直接复用；密度可控；内部活动走点开钻取。
- 方案 B（每角色一人）：沉浸感最强，但成员被禁止对外发言成「哑巴人物」；3 团队×4 角色≈12+ 只 pet 同屏信息密度崩溃；B 的价值可被 A 的钻取覆盖。

**用户回答（关键原话要点）**：

- 想象：先组长上台进入执行；组长觉得某任务需要交给某组员，就**唤起该组员**。
- 指出现有设计的误差：组长实际可以基于预设**创建同角色的多个实例**，这与「正常团队」直觉有偏差，需要详细设计。
- 显示逻辑倾向：① 初始只招出组长，组员默认不显示；② 组长召唤某组员时才显示（召唤显示）；③ 组员进入执行状态处于显示态；后续可一直显示或转入**休眠**状态，UI 对状态做区分。
- 调度者形态未想好，抛出新问题：已有两层，是否需要第三层？是**堆叠更多层**，还是**统一可任意架构层级的解决方案**（如总裁→CTO→管理层→执行→协助/监管的企业级组织架构）？
- 用户位置：**用户作为上帝存在**，单独显示一个超级角色作为上帝视角，统筹全局讨论或协议决策。附带新问题：子 Agent 的提问/决策功能点，是①直接交用户决策，还是②由子 Agent 提出交上级决策？

### 议题 3：组员多实例路线、层级架构、决策路由

**我给出的分析**：

- 组员多实例：A（人物唯一+分身化——桌面上一个人物多任务忙碌，点开看多会话）/ B（克隆体上台）/ C（限制单实例，牺牲并行）。
- 层级：关键洞察——现有 spawn 本身递归（子可 spawn 子），「任意层级」只需**把预设也变成可 spawn 项**：节点只有角色实例（执行叶子）与预设实例（容器）两种；固定三层即深度 3 特例；MVP 限嵌套 1 层；UI 逐层下钻。直接堆叠固定层会让协议/UI 绑死特定组织形态。
- 决策路由三分类：**信息澄清型**分级自决（成员→组长→上级→用户，可配自主权）；**安全审批型**必须到用户（上帝），任何上级不得代答（现有监管体系安全边界，不可稀释）；**跨团队协调型**走同层讨论通道，僵局才上报。核心原则：**上帝是安全边界和最终仲裁，不是第一响应人**。

**用户选择（原话要点）**：

- 组员实例：确认多实例并存可能性很强（① 避免上下文过长——聊多轮后唤新实例更省 Token；② 任务并行——A 页面/B 页面各唤一个实例，后续按任务分别召唤）；休眠角色需规整绘制到别处或排版处理，避免渲染太多无用角色。**克隆体是较好的显示方案**：一个人物对应一个角色，基于人物创建多个克隆体，符合直觉且契合赛博主题。
- 层级架构：**统一递归模型**。
- 决策路由：**三分类分级路由**。

### 议题 4：克隆体生命周期（状态机 → 用户重设计 → 闭环）

**我最初提案**：四态状态机（召唤中/活跃/休眠/退役）+ 休眠区三候选（边缘休息室/侧栏收纳/就地压暗）+ 本体=首个实例 + 组长声明策略触发休眠。

**用户重新设计（关键原话）**：组长唤起新实例 → 实例完成后**默认保留显示**；若组长后续唤起同类另一实例，则对话转向新实例，第一个实例**转入休眠**；否则保持显示。理由：频繁休眠/唤醒机制不友好。

**我的回应**：该规则命名为「**同角色单活跃位**」——每个角色桌面只有一个当前对话位，新实例上台即顶替，旧实例自动入休息室；休眠节奏完全跟随组长对话流，避免定时器抖动。同时指出两个必须补的细节：

- 细节 1：顶替休眠 ≠ 停止运行（并行 A/B 页面场景下，被顶替者可能还在跑）；休息室定义为纯视觉休眠、运行状态独立，后台忙碌带标记。
- 细节 2：续聊已入休息室实例的模式（换位上台 vs 临时对话不换位）。

**用户定案（关键原话）**：**只要在工作就不能待在休息室，所有工作必须在前台完成；进入休息室说明最近用不上他了**（即「跑完才能入休息室」）。

**由此形成的规则闭环**：

- 所有工作必须前台完成，运行中实例永远台上可见；
- 入休息室条件 = **空闲 + 非当前对话位**（被顶替且已跑完）；
- 唤醒 = 空闲换位（休息室实例上台，原对话位空闲则互换入休息室）；
- 休息室内全部空闲，续聊模式自然为「唤醒上台」，无需「临时对话」特例。

**退役触发**：上帝手动遣散 + 团队任务结束全员自动清场（用户确认）。用户补充：克隆体/休息室废弃角色太多没意义，提出 ① 长期不用自动退役；② 提示词加说明（克制创建克隆体/限制数量）。

**我的分析**：方案 2 拆软硬两层（组长 prompt 软引导 + spawn gate 硬上限 fail loud，与项目规则 12 一致）；方案 1 的「自动真退役（销毁上下文）」有误伤风险，降级为「休息室超容**自动归档**（移出桌面、上下文不销毁、可唤回）」。

**用户选择**：**三层控制**（提示词软引导 → 硬上限兜底 → 休息室自动归档；真退役仅上帝手动 + 任务结束）。

### 议题 5：平台命名 → 用户升级为体系皮肤系统

**背景**：我请求为整套模式命名，给出「剧场模式」（台上/后台/B角/杀青隐喻）等候选。

**用户回答（关键原话，设计升级）**：提出**架构体系选择**方案：

1. 提供若干预设体系：(a) 神话体系（欧洲/中国）；(b) 皇权体系（欧洲/中国）；(c) 国家架构体系（中国/美国/欧洲）；(d) 公司架构体系；
2. 这些选择**不一定必须是预设的，可以只是表面显示和名称上的选择**——整个架构体系实质不变，仅名称差异；
3. 顶层角色：用户作为顶层存在，名称随体系变化（皇帝/上帝/国家元首等）；
4. 团队模式使用对应体系名称显示，或用户自己取名。

**我的分析**：本质是**显示文案词表映射**（皮肤系统）——语义概念（上帝/预设实例/克隆体/休息室/退役）固定，各体系提供映射（神话：上帝/神殿/**化身**/仙居/归位；皇权：皇帝/内阁/钦差/偏殿/告老还乡；公司：CEO/部门/外派/人才池/毕业）。神话体系「克隆体=化身」的映射天然契合。协议层、DB、角色 type 键名全部不动。平台名须不绑任何单一体系。

**命名候选**：万象台（万象=一切形态显现，台=舞台/桌面/平台）/ Agora（希腊议事广场）/ 众生集。

**用户选择**：平台名 = **万象台**；皮肤粒度 = **每任务桌面独立选**（全局配置作新任务默认值）；自定义范围 = **体系词表整包生效 + 专有名词可覆盖 + 通用术语不散改**。

### 议题 6：桌面渲染架构、移动语义、布局权

**我给出的分析**：

- 渲染路线：① 纯 DOM+SVG 连线（成本最低、上限低）；② Canvas 全场景（表现力天花板，但审批气泡/思考流等交互组件全部重写、与 Vue 体系断裂，「为 10% 表现力付 300% 成本」）；③ **分层混合**——DOM 人物层（pet/气泡/审批/思考流全复用）+ Canvas 氛围层（连线/粒子/涟漪/光效，垫在人物层下），移动用 DOM transform，canvas 端点 rAF 读 DOM 位置跟随；代价仅双层坐标同步，克隆体数量被硬上限控制、规模可控。**交互的给 DOM，好看的给 canvas**。
- 移动语义：不移动仅连线 / 微倾向 / 离席制移动（临时离席向彼此移动、结束归位；拖拽=设工位锚点，自动移动不覆盖锚点）。
- 布局权：初始自动分区+自由拖拽 / 全自动力场 / 纯网格。

**用户选择**：渲染 = **③ 分层混合**；移动 = **离席制**；布局 = **场景化设计**（用户原话：按不同场景方案给出不同架构下的布局设计——公司架构下有**工位、会议室**等；皇权架构下有**议事厅、军机处**等类似设定）。

**我的分析（场景模板）**：体系皮肤升级为**词表 + 场景模板**两部分——语义区域（上帝位/团队工位区/讨论区/休息室）到场景元素固定映射（公司：总裁办/各部门工位/会议室/人才池；皇权：金銮殿/各府衙/军机处/偏殿；神话：神座/各神殿/天庭议席/仙居）。

**钉子 1（离席目的地）**：小组讨论就近聚拢；正式会议（上帝发起/跨多方）全员移入会议室。→ 用户选**双轨制**。
**钉子 2（排布拖拽）**：场景模板定区域，区域内按团队自动落位，上帝拖拽微调、锚点持久化、离席归位回锚点。→ 用户确认。

### 议题 7：后端协议——跨团队讨论机制

**我给出的分析**：

- 发起权三来源：组长自主（prompt 授权）/ 调度者指派 / 上帝点将。
- 阻塞语义：**回合制停等**（发起方本轮停等、回复即唤醒、多方栅栏收集——与现有 spawn immediate/barrier 唤醒链同构，复用 wakeScheduler/看门狗，技术风险最低）vs 异步消息（自由但节奏散，讨论语义变弱）。
- 持久化：双边各记（复用 message link，如 child_return 模式）/ 独立 meeting 实体（供会议室渲染/上帝旁听/记录导出）/ 混合（小组双边各记 + 正式会议建 meeting 实体）。

**用户选择**：

- 发起权：三来源全选 + **新增第四来源（用户补充）：某一个角色觉得任务重要，可以通知他的上级去发起会议，但自身没有发起会议的权限**（补全成员层通信出口，与「跨层只能指挥/汇报」自洽）；
- 阻塞语义：**回合制停等**；
- 持久化：**混合：双边各记 + meeting 实体**。

### 议题 8：上帝位、讨论终结、新旧关系

**我给出的分析**：

- 上帝位（用户化身，非 AI）：常驻**待决事项队列**（安全审批/僵局仲裁/成员上报）+ **全局状态总览**（各团队活跃/休眠状态、任务进度摘要）；上帝直接操作（点将/发消息指挥/遣散）从上帝位发起。
- 讨论终结：发起方终结（小组由发起方组长宣布结论、大会由发起者散会、结论注入所有参与方消息流）+ 轮数上限防死循环（类似 maxLoopCount 思路）+ 僵局逐级上报（成员→组长→调度者→上帝）。
- 新旧关系：万象台是预设任务专属形态 / 全面替代工作台 / 并列共存。

**用户选择**：上帝位 = **待决队列+全局总览**；终结 = **发起方终结+轮数上限**；新旧关系 = **这是一个全新的模式，需要单独设计一个全新的台面，现有的工作台保持不动即可**。

### 议题 9：调度者身份与任务开局

**我给出的分析**：

- 调度者身份：复用 Cherry Nexus（职责混淆、能力配置错位）/ **内置固定调度者预设**（类似 `cheryNyxus` 地位，专职创建团队/编排/主持，用户可定制）/ 上帝自选任意预设（质量不可控）。
- 团队创建权：调度者自主 / 上帝指定清单 / 提议-批准制。

**用户回答（关键原话）**：创建模式时可选，两个大入口：

1. **用户自主指定**：预先创建若干预设，勾选作为需要使用的团队进入任务；
2. **交由调度者分析**：调度者分析后交 Cherry Nexus 创建对应预设，再基于预设创建任务。用户指出问题：**创建新预设可能需要服务重启**；
3. （用户征求意见）或再给一种方式：**调度者基于现有已知预设自主唤起、随意组合**，而不是固定死的预设。

**我的分析**：入口 1 最稳（预设质量有保障、零技术风险，但需预先准备）；入口 2 的重启问题是硬伤（任务中途重启运行中团队实例全部中断走 rebuild，体验断裂；Nexus 动态生成质量不可控），唯一不可替代价值是冷启动；入口 3 是最佳主路径（复用现有预设无重启问题、质量可控，调度者有自主权，用户预创建预设依然必要）。

**推荐并获用户确认**：**三入口分层共存**——主路径 = 调度者从现有预设自主组合；用户勾选 = 候选范围圈定（勾了只在范围内组合，不勾 = 全集）；动态创建预设（Nexus 冷启动）留二期，一期降级为提示用户手动创建。**重启约束：一期规避（不做任务中动态建预设），二期专项解决（配置热加载或任务隔离重启）。**

## 6. 可优化/进步空间讨论点（复审关注点 b/c 类）

### 6.1 更优方案的潜在讨论点（b 类）

1. **氛围层升级路径**：D14 选了 2D Canvas 氛围层；若未来追求更强表现力，可在不推翻架构的前提下把氛围层升级为 WebGL（如 PixiJS），人物层仍留 DOM——这是 D14 相对 D16 路线（Canvas 全场景）保留的演进空间。
2. **克隆体硬上限动态化**：D9 的硬上限是固定数值；可演进为按 brain 吞吐/Token 预算自适应（并行度随资源伸缩）。
3. **meeting 实体承载会议纪要**：正式会议散会时，可由主持方（或影子角色）自动汇总「会议纪要」消息写入 meeting 流，供上帝位总览引用——D22 的自然延伸。
4. **体系皮肤用户可扩展**：D11 的四套体系是内置的；可开放自定义皮肤包（词表+场景模板的导入导出/分享）。
5. **上帝位时间线回放**：全局总览可加「桌面历史回放」——按时间轴回放谁在何时说了什么、谁被召唤/休眠（依赖讨论消息已持久化，技术上可行）。
6. **成员向上请求分级**：D20 的成员向上请求可分「普通汇报」（排队）与「紧急请求」（打断上级当前轮）两档，避免重要事项淹没。
7. **跨任务共享克隆体**：当前克隆体/上下文每任务隔离；远期可探索同角色跨任务复用上下文（显式授权下），进一步省 Token。
8. **调度者提案可视化**：D24 主路径是调度者自主组合；可加「组合方案预览」步骤——调度者先亮出拟创建的团队清单再执行，兼具可控性与自动化（类似被否决的提议-批准制的轻量版，仅展示不阻塞）。

### 6.2 现有设计中的不足点（c 类，实现时需正面处理）

1. **spawn 无同层 peer 通道**：现有唤醒链是严格父子树（`waitedChildren`/`wakeParent` 单向）；peer 通信需要扩展 `spawnBroker`/`wakeScheduler`。**防环是首要风险**（A 找 B、B 找 A 循环唤醒）——D21 回合制停等 + D23 轮数上限是主要防线，但 peer 等待与 spawn 等待叠加时，看门狗（feed-dog）语义需重新审视（等待 peer 回复期间算不算「活着」）。
2. **roster 快照锁定**：`metadata.spawnTypes` 在 chat.create 时锁定；万象台任务中途追加预设实例（调度者动态建团队）需要快照刷新机制，否则新团队不在既有 roster 内。
3. **配置重启约束**：配置保存需服务重启生效（现状 2.6）；即使二期做动态建预设，也绕不开此约束，故 D25 设专项。
4. **审批无归属概念**：现有 `approvalRegistry` → 前端的审批直达路径没有「归属人物/团队」维度；万象台审批气泡要挂到具体克隆体头像，需要审批事件补充来源 chat/角色信息。
5. **双视图一致性**：D19 万象台与现有工作台并存——同一底层会话若在两种视图中同时打开，状态/操作的一致性（如 abort、resume）需定义。
6. **Token 成本**：多团队并行 + 回合制讨论的上下文消耗可观；autoCompact 对子 chat 与 peer 讨论消息的覆盖需验证（peer 注入的消息是否纳入压缩统计）。
7. **`ask_user_question` 语义冲突**：现有提问直达用户，D3 要求分级自决——成员/组长的提问需改为「向上路由」，原 RPC 语义要兼容或并存（上帝直连场景保留）。
8. **同名角色多实例的追溯**：现状多实例已有（2.5），但消息溯源以 `[角色 type]` 前缀区分——多克隆体并存时，组长消息流里同 type 多实例的回复需要实例级标识（taskId/chatId），否则「A 页面实例」与「B 页面实例」的回复无法区分。

## 8. 复审补充记录（2026-09-05 · AI 复审第一轮）

> 复审范围与结论：核对第 2 节代码事实基础（与 `spawnBroker`/`wake.ts` 等实现一致）；逐项检查 25 项决策内部一致性；评估第 5/6 节完备性。**总体结论：决策记录过程质量高（候选全留、原话溯源、映射表、自知遗留清单），但「尽善尽美」谈不上——存在 1 个战略级盲区与若干状态机/工程面缝隙。** 缺口的共同模式：逐议题讨论收得住单点决策，收不住横切多议题的系统性视角；第 5/6 节自查是「从已定决策往下看缺什么细节」，而非「从系统运行时往上压」。以下按 H（战略）/ M（缝隙）/ L（细化）三级列出，归并建议见 8.5。

### 8.1 战略级缺口（H 类，建议优先补进第 5 节）

**H1. 与「任务中心」计划的关系完全缺失（最大盲区）**

`docs/plan/parallel-agent-task-center.md` 状态为**执行中**（overview 投影、task-center 前端已在工作区实施），而本文档全文未提及其存在。两者撞在三个面上：

| 维度     | 任务中心（在建）                                                           | 万象台（规划中）                            | 冲突点                                                                      |
| -------- | -------------------------------------------------------------------------- | ------------------------------------------- | --------------------------------------------------------------------------- |
| 全局总览 | `TaskCenterPanel`：任务列表 + `PendingOperationsPanel` 收件箱              | D18 上帝位：待决队列 + 全局总览             | 功能几乎同构——复用一套投影做皮肤化，还是两套并行？                          |
| 数据模型 | `buildTaskOverview` 按 rootChatId 平铺聚合 chat 树，agent 无「团队」中间层 | 需要团队（预设实例）→ 克隆体两级身份        | 任务中心 `TaskAgentOverview` 若不预留团队维度，万象台须另建投影（重复建设） |
| 任务身份 | `taskId` 语义刚落地（branch.taskId）                                       | 万象台任务的 root 是谁（调度者 chat？）未定 | 直接影响任务中心「按根会话聚合」能否套用于万象台任务                        |

另：6.2.5「双视图一致性」只写了万象台 vs 工作台，实际将是**三视图**（工作台/任务中心/万象台）并存的一致性。**时间锚点：H1 应在任务中心批次 3（前端任务中心）合入前裁定，否则上帝位与任务中心面板的边界会在两个方向各自长出来。**

**H2. 「禁止跨层级讨论」的强制面未定**

D1/D3 已定「跨层只能指挥/汇报、同层才可讨论」为规则，但未讨论强制手段：纯 prompt 软约束（Agent 可能违规越层发起请求），还是协议级闸门（peer 通道建立时校验双方同层，违规 fail loud）？项目对同类问题已有明确传统（spawn roster 闸门 + 规则 12 fail loud），应同款处理。这是协议设计的输入，不是实现细节。

**H3. 万象台状态的持久化与重启恢复未列**

现有系统的重启恢复是重要设计面（`rebuildWaitedChildren`、`resumePending`、`roleInjected` 幂等标记）。万象台引入两类新的可恢复状态：

1. **peer 回合制停等的跨重启恢复**：`rebuildWaitedChildren` 只认父子链；A 组长停等 B 回复期间服务重启，等待关系从哪恢复？
2. **桌面状态重建**：谁在台上/休息室、当前对话位是谁、进行中的 meeting——D17 只持久化拖拽锚点、第 5 节 13 只持久化皮肤。重启后桌面是重放推导还是独立持久化？

这直接决定 D7 闭环（入休息室 = 空闲 + 非当前对话位）的工程成立性——「当前对话位」若不持久化，重启后规则无从判定。6.2.1 仅从看门狗语义角度碰到 peer 等待，未上升到恢复层面。

### 8.2 状态机与协议缝隙（M 类，25 项决策中的不自洽/欠深挖点）

**M1. D6 状态枚举缺一格：「被顶替但运行中」**

议题 4 定案两规则拼接产生一个未命名状态：并行 A/B 场景下组长唤起 B 实例 → B 占当前对话位、A 被顶替——但 A 还在跑，而定案「只要在工作就不能待在休息室」。于是 A = 「台上可见 + 非当前对话位 + 运行中」。D6 枚举（就位/活跃/休眠/退役）无此状态归属，与「活跃」的关系、UI 如何区分，需补状态机定义。**此为 25 项决策复审发现的唯一一处真实不自洽。**

**M2. 同一组长并发多讨论的后端排队语义**

第 5 节 11 只写了前端移动/连线仲裁。后端面：一个组长同一轮只能停等一处，第二个讨论请求（他组邀请/调度者指派）是排队、合并还是拒绝？会议邀请能否拒收（「忙，稍后议」）？是 D21 回合制停等协议的直接推论，未列。

**M3. 上帝审批延迟 × 看门狗 × 级联阻塞**

D3 安全审批必须到上帝 + D18 待决队列（多团队审批天然串行）+ D21 回合制停等（组长等成员、第三组等组长）——级联阻塞下上帝长时间不点审批会让多支链条同时静止。看门狗默认 5min 无 chunk feed 即触发（`spawnBroker.ts` `getWatchdogTimeoutMs`），审批挂起期间是否算「活着」在现状里就值得验证，万象台将其放大数倍。上帝位时效设计（提醒/超时策略）需进第 5 节。

**M4. LLM provider 并发与限流未提**

多团队并行 + 回合制讨论 = 同一 brain 配置（同 key 同模型）并发请求数量级上升：速率限制、429 retry 风暴、并发上限/排队/优先级。6.2.6 只提了 Token 成本（量的问题），未提并发工程面（节奏的问题）。一期至少要定「全局并发上限是否需要」。

**M5. 万象台任务的 chat 树形状未定**

调度者 chat 是 root？各团队 chat、克隆体 chat 如何挂（预设实例是「容器」，容器自身有无 chat）？决定任务中心聚合、档案抽屉分支选择（historyBranchSelection）、消息溯源链（6.2.8）三处现有功能是否被波及。第 5 节缺一条数据模型级条目。
