## 目标

把原文档与本次确定的需求映射到实施任务和验收场景，不重新设计产品。

## 输入与契约

- [完整设计记录](design-and-history.md) §2 已确认需求、§3～§10 补全方案及附录历史
- 本任务无前置依赖，直接使用总文档当前需求版本；C01 完成前不要求取得协议类型，仅记录需要核心负责人裁定的冲突。
- 后续发现契约变化先报告 C01／总负责人，不自行改动共享类型。

## 允许修改的范围

- `本任务文档中的需求追溯表`
- 追溯表直接填写在本任务文档内，不新增未登记的独立 Plan 文件，也不与总负责人同时编辑总计划。

## 范围与非目标

- 用户确认内容和建议分列，引用决策编号及历史议题；误发内容不新增决策。
- 每条需求至少有 C/S 任务归属及具体测试场景；冲突交 C01，不自行裁定。
- 不修改总计划、协议、模块规则或其他任务的状态。
- 禁止修改数据库、公共协议、权限、业务状态机、RPC 注册和应用装配；禁止直接编辑总进度。
- 只实现明确完整产物，不新建只有透传用途的 container，不额外安装依赖。

## 执行步骤

- [ ] 1. 阅读指定输入与前置交接，记录契约版本，列出本任务产物和样例状态；缺失时报告交接对象。
- [ ] 2. 按范围完成「需求追溯与覆盖表」，满足上方逐条内容要求，保持可独立消费。
- [ ] 3. 执行下方局部检查，修正文案、类型、样例或展示问题；业务契约问题升级给 C01／总负责人。
- [ ] 4. 记录实际修改文件、检查结果与已知限制，交给 C01／总负责人 复核并由总负责人同步总进度。

## 定向测试与检查

- 对照用户决策逐条人工核对来源。
- 检查映射中的任务 ID 均存在，覆盖组织、皮肤、快照、上下文、恢复和交付。

纯文档不运行产品构建。核验标题、链接、来源与流程一致性即可；视觉验收不伪造通过。

## 完成标准

- 有效需求无遗漏且来源清楚。
- 产物可交 C01 审核，未完成实施不能写成已验证。
- 所有允许范围外变更均为零；四步有记录。
- 完成不等于整体前端或功能完成，由复杂任务接入真实业务后统一验收。

## 协作与变更边界

- 执行前核对前置任务已完成且契约版本一致；当前状态“未开始”，未解锁不等于发生故障。
- 本次落盘不是实现批准或验收。遵循总文档的已确认需求；新增技术方案以“补全建议”提供，执行时不得冒充用户原话。
- 先更新对应模块文档，再实现代码。不得修改本总计划以外无关需求、不得代用户审批。
- 共享文件由总负责人分配；遇到权限、状态或契约变更需求提交给核心负责人，不同时覆盖他人文件。
- 每完成一个步骤更新本任务；由总负责人同步总计划的步骤统计，避免多 Agent 同写总文件。
- 最终回归发现问题时在父计划登记新的修正小任务，不恢复已删除任务，也不改写原完成摘要。
