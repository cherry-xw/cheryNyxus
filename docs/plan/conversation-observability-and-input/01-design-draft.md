# 上下文统计、待办进度与连续消息：设计初稿

**文档创建时间：** 2026-09-18T00:56:28+08:00

**状态：** 进行中

**所属总任务：** [上下文统计、待办进度与连续消息交互](README.md)

**复杂度：** 3/5。需要把现有消息处理、统计来源和三种界面联系起来，形成后续可讨论的方案。

**依赖：** 现有工作台、会话时间线、工具执行记录；本稿的推荐方向尚未经过产品确认。

## 1. 本稿用途与初步方向

用户在执行任务时，应能回答三个问题：模型现在带着哪些信息工作、清单执行到了哪里、新补充的消息何时会被采用。三项需求共用会话与执行记录，但各自保留清晰入口，避免堆成一个大型监控面板。

建议先统一消息、执行步骤和统计范围，再分别增强展示：

1. 上下文采用“常驻简要占用 + 可展开的统计详情”。先提供可靠的逐次请求记录，再增加堆叠柱状图和对比；旧侧边入口在新入口完整承接功能后再考虑移除。
2. To-do 采用“当前清单摘要 + 完整清单 + 历史更新记录”。三种模式读取同一份进度，展示密度不同；明确它是模型报告的计划进度。
3. 连续消息默认建议沿用“下一次可采用时加入”的方向，同时把等待和采用状态说清楚。“等本次任务完成再处理”保留为待讨论的另一种策略。

本文中的“现状”来自当前工作区源码和所链接文档；“建议”均是未实施的设计。未运行界面，不能把源码发现写成实际视觉验收结论。用户原述“代码的压缩次数”暂按上下文压缩次数理解；如果另指工具输出或代码文本压缩，需另列指标。“聊天模式”“对话模式”在本稿中指同一种展示。

## 3. 先统一统计和展示中的概念

“轮次”目前容易混指不同阶段，详细需求中应使用下面的明确名称，不用一个数字代表全部过程。

| 名称 | 建议含义 | 不计入或需分开记录的情况 |
| --- | --- | --- |
| 用户消息数 | 服务端成功接收的不同用户消息数，按稳定消息身份去重 | 重发同一命令不新增；系统附加指令、子 Agent 回传不算用户发送 |
| 一次运行 | 一段具有同一 `runId` 的执行；可包含多个模型请求和工具步骤 | 连续补充消息可能并入同一次运行，不能按用户消息数推算 |
| 模型请求次数 | 实际尝试向模型服务发送请求的次数 | 自动重试单列“尝试次数”；展示成功回复数时不混入失败尝试 |
| 执行步骤 | 模型步骤、工具步骤分别计数；运行中数量单独显示 | 审批等待不是工具已执行；一个回复包含多个工具不等于一个工具步骤 |
| 压缩次数 | 已成功产生并采用上下文摘要的次数 | 压缩尝试失败不算成功；配置时期变化、工具结果去重另算 |
| 当前上下文占用 | 某一次请求携带的输入组成及总量 | 不是历次请求用量之和，也不是磁盘历史文本总量 |
| 累计请求用量 | 所选范围内有记录的请求输入、输出用量累计 | 包含重复发送的历史；有缺失记录就显示覆盖情况，不充当完整账单 |

统计默认范围建议为当前会话分支中的主 Agent，允许查看指定子 Agent；任务整体可汇总用量和步骤，但各 Agent 的上下文容量必须分开显示。不同模型没有共同的容量分母，不给整个任务画一个占用百分比。

三项功能都保留根任务、实际会话、运行、消息或工具调用之间的关联。已有 ID 能表达的关系直接复用；确实缺失的请求尝试 ID、清单版本等在详细方案中再定义。时间只用于展示，不能靠“时间差不多”猜测归属。

## 4. 上下文显示模块增强

### 4.1 问题与容易踩坑的地方

- 只有当前占用看不出增长原因，也无法解释某次工具返回为什么使上下文明显变大。
- 当前估算会重新构建提示词；修改配置后再重算旧请求，可能把新内容套到历史上。应在实际请求构建完成时记录当时组成，并保留模型、配置时期和估算方式。
- 对话中展示的思考、附件标记、原始工具输出不一定全部原样发给模型。统计以实际转换后的请求为依据；无法准确拆分的媒体、格式开销单列“未细分”，不能拿文件字节数当 token。
- “工具定义”“工具调用参数”“工具返回内容”是三种不同占用；调用参数不能因缺少正文而漏算。思考若已包含在合计中，展开时不能再加一次。
- 历史占用曲线可能因压缩、去重、撤回而下降。增长量允许负数，压缩不能改写过去的柱子。
- 精确输入总量与分段估算可能不相等。不能为了让图表相等而按比例捏造精确分类；明确标注“总量来自服务返回，组成是估算”。
- 未知容量、统计失败、尚未记录和确实为零必须区别显示；当前实现中的零值降级不足以承载新界面的所有状态。

### 4.2 建议的信息结构与交互

常驻处显示“上下文：约 X / Y token”，有可靠分母才显示百分比；点击打开同一统计模块。首次使用无需先理解配置和事件名称。

详情按三个区域组织：

1. 当前概况：当前 Agent、模型、数据时点、占用、最近一次增减；显示“估算”“服务返回”“历史重建”等来源标签。切换 Agent 后标题和范围同步变化。
2. 请求趋势：横轴为模型请求顺序，按运行分组；纵轴为 token 数，每根柱子表示该请求的输入组成。选中柱子后展示分类数值、与前一次差额、关联用户消息和工具记录。可选任意两次作对比。
3. 详细内容：占用较大的工具结果、缓存统计、用户消息数、模型与工具步骤数、压缩记录；系统提示词和工具定义保留在明确的“查看上下文内容”入口中，并保留旧快照质量说明。

初版柱图建议将现有六类中的“对话”继续拆为用户输入、模型历史文本、实际保留的思考、工具调用参数、工具结果、子任务回传及未细分内容。主图保持有限类别；工具结果区域可再按工具名或单次调用展开，避免每个工具都占一个主图颜色。

柱图旁提供同数据表格，键盘聚焦或点击可查看数值，不能只依赖 hover 和颜色。简短说明用现有 tip；必需状态和操作结果直接显示。图例隐藏某类后，仍保留原始总量并写明当前筛选，避免把筛选后高度误认成全部占用。

增长详情展示“本次相对上次 +X / -Y”，并优先列明有记录支持的原因，例如“新增两条用户消息”“新增工具结果”“采用压缩摘要”。尚不能归因的变化显示“其他变化”，不根据相关性推断因果。

### 4.3 缓存指标必须分开定义

| 指标 | 推荐计算方式 | 数据不足时的表现 |
| --- | --- | --- |
| 模型输入缓存比例 | 同一统计范围内，已归一化的缓存读取 token 合计 / 有缓存统计且输入总量已知的请求输入 token 合计 | 未返回为“未提供”；分母为零为“不适用”；同时显示有统计的请求数 / 总请求数 |
| 工具结果复用率 | 实际返回已有结果、跳过工具执行的次数 / 适用该复用机制的调用次数 | 未确认存在该机制前不显示百分比；排除不适用的工具，并展示分子、分母 |
| 重复工具结果缩减 | 因已有去重逻辑而缩短的历史内容次数，以及估算减少的 token | 名称明确为去重或缩减，不叫缓存命中；没有缩减记录时只说明未采集 |

模型输入缓存比例先按请求或 Agent 展示，汇总使用分子合计除以分母合计，不能直接平均每次百分比。缓存写入和缓存读取分开；模型服务之间的字段定义可能不同，实施时逐一阅读对应官方文档、明确输入总量是否包含缓存部分，再完成换算。

一般请求级缓存数据不能准确归属某个工具；除非服务明确提供细分数据，否则工具表只显示占用和变化，不显示推算的“这个工具命中率”。本稿不承诺不同服务都支持缓存统计。

### 4.4 数据采集与历史策略

建议最小记录包含：请求尝试身份、所属会话与运行、实际模型、配置时期、请求顺序和时点、输入组成估算、返回用量、来源及缺失原因、结束状态。为后续比较保存数值和已有内容引用，不重复存储整份请求正文和密钥。

请求发出前记录输入组成；返回结束时补充服务报告用量。断流、失败或重试没有报告用量时保留未知状态，不能记为零；失败尝试和成功尝试分开，以免低估实际消耗。统计写入失败不得阻止正常回复，但要能追踪缺失并补查。

历史没有记录的请求显示“此时尚未采集”。若可从旧消息估算，只放在“历史重建”视图并标明限制，不与当时采集值混用。配置时期变化和压缩边界分别标记，沿用现有边界，不创造第三套历史分段。

趋势按范围查询和分页；长会话默认展示最近一段，可加载更早记录。概览与详情按需获取，避免每个流式文字片段都重算全历史或重画全部柱子。刷新、切换窗口和切换模式不应重置已保存的统计。

### 4.5 建设顺序与可形成的亮点

先统一定义与采集，再做趋势图、工具占用明细和两次对比；缓存按服务实际支持程度接入。亮点是从“哪根柱子增长了”直接定位到相关工具结果或用户补充，同时看到压缩前后差异。

新模块能完整访问系统提示词、工具定义和历史快照后，再评估去掉侧边旧入口。三种模式必须都能找到新入口，收起统计不影响阅读或输入；不为本任务重新设计整个标题栏。

## 5. To-do list 展示与进度

### 5.1 问题与推荐规则

单次 `update_todo` 工具卡片代表当时提交的清单，不能承担持续进度入口。工具折叠、消息滚出屏幕或切换到节点树后，用户仍需看到当前执行项和已完成项数。

建议由服务端或共享数据读取层提供“当前有效清单”，包括所属会话、来源调用、更新时间、完整列表和版本。只有成功执行的更新成为正式当前清单；参数流式生成或等待批准时显示“正在更新”，保留上一份有效清单。失败、拒绝、取消不覆盖旧清单。需核对并调整现有从 `sense_end` 参数恢复清单的规则。

清单继续由模型维护，初版保持只读。用户若需要修改任务，可通过补充消息表达；直接勾选完成会改变模型工作依据，属于后续独立需求。完成数表达“模型已标记完成的项数”，不等同于自动验证结果，也不用于推算剩余时间。

### 5.2 三种模式的展示建议

| 模式 | 常驻摘要 | 展开与历史查看 |
| --- | --- | --- |
| 节点树 | 树旁或输入区上方可收起的摘要：“计划 2/5 · 正在补测试”，标明所属 Agent | 展开完整列表；“查看这次更新”定位到原工具节点。用户正在浏览旧节点时不强制移动视角 |
| 对话模式 | 对话内容外保留紧凑进度条目，工具卡片仍展示当时清单 | 展开当前完整清单；旧卡片标识“当时的计划”，可跳转当前版本，避免旧消息随最新进度变化 |
| 精简模式 | 一行已完成数量与当前项；没有计划时不占用固定大片区域 | 点击展开简单列表或现有详情区域，长内容换行、已完成项可折叠，不新增另一套数据请求连接 |

收起偏好按窗口和会话保存。后续更新只改变摘要，不自动反复弹开；新建清单时可给一次轻量提示。暂停、失败、等待用户操作与当前项状态并列展示，例如“计划 2/5 · 执行已暂停”，不能仍只显示一个持续闪动的“进行中”。

### 5.3 边界与实现风险

- 空清单是明确清空，不能因数组为空退回上一份；“从未创建”“正在获取”“获取失败”“已清空”分别处理。
- 同一会话发起新目标时，旧清单不能悄悄成为新目标的计划。初版建议按来源运行展示“上一段执行的计划”；是否沿用由新更新或明确操作决定，不根据文本相似度自动归并。
- 主 Agent 与子 Agent 各有清单，默认展示当前所看 Agent 的清单，并明确来源。任务总览可按 Agent 分组，不把所有已完成项简单相加后称为全任务完成率。
- 现有“最多一项进行中”写在工具说明中，结构校验没有直接落实该数量限制。后续讨论是否服务端强制校验；面对已有多项进行中的记录，界面如实展示，不随便挑一项。
- 清单项没有稳定 ID，文本可能重复、改名或重排。初版以完整快照替换，不做不可靠的逐项动画和完成时间比较；需要逐项历史时再扩充 ID、版本和删除语义。
- 完成标记可能被模型改回未完成；展示最新状态及来源更新，不把“完成过”当作不可逆事实。
- 历史分页或压缩不能导致当前计划消失，也不能从只加载的一页推定最新清单。恢复应返回明确的当前有效记录及来源。
- 同一更新被实时通知、恢复快照、历史读取重复带回时，按来源调用和版本去重；多个更新乱序到达不能让旧清单覆盖新清单。

### 5.4 可形成的亮点与阶段范围

第一阶段让用户始终知道“现在做哪一项”；第二阶段再考虑计划变更对比、从当前项定位相关执行记录。当前工具调用没有明确关联某一清单项时，不能仅凭工具名给该项自动判完成或强行建立关联。

优先复用 `TodoPanel`、`TodoRenderer` 的状态和内容表达，但统一数据规则后再接入三模式。验收重点是切换展示方式仍看到同一版本，而不是增加更多面板。

## 6. 用户连续发送消息的并入与展示

### 6.1 默认策略建议与备选

| 策略 | 用户能理解的行为 | 优点与限制 | 初稿建议 |
| --- | --- | --- | --- |
| 下一次可采用时加入 | 当前请求或工具继续执行，后续模型请求带上已接收的补充 | 接近现有流程，补充能较早生效；不能撤销已经执行的动作，也可能要等审批或子任务 | 作为默认方向进一步讨论 |
| 本次任务结束后处理 | 补充先保留，到当前运行结束后再启动下一段执行 | 适合独立后续任务；“结束”与暂停、失败、等待子任务不同，需另建明确的等待与启动规则 | 保留为可选方向，不假定现在已支持 |
| 停止后按新消息继续 | 用户显式停止当前执行，再发送更正 | 可阻止后续步骤，但已完成副作用无法回退，未结束工具也未必能立即停止 | 复用明确的停止操作，不把普通发送自动解释成停止 |

默认不增加发送前确认框。输入区在运行时以简短文字表达所选行为，例如“将在下一次请求中补充”；若当前在等待批准，具体状态写“等待当前操作结束后补充”。如果后续确认需要两种发送策略，可在发送按钮旁提供选择，消息入队时记录该次选择，后改默认设置不影响已排队消息。

“立刻并入”不能解释为改动正在返回的请求。模型可能已经决定接下来执行哪些工具；普通补充不保证阻止这些工具，用户想改变当前动作时必须有清晰的停止入口。

### 6.2 状态与可靠反馈

| 阶段 | 建议文案 | 依据与允许动作 |
| --- | --- | --- |
| 本地提交尚未确认 | 发送中 | 保留原文和附件；避免重复点击产生新消息；超时不自动断言服务端没收到 |
| 服务端已接收，尚未采用 | 等待加入；显示目标会话和必要的等待原因 | 以服务端接受记录为准；如将来支持撤回，只能在此阶段尝试 |
| 已加入执行消息列表 | 已加入，等待模型请求 | 现有 `consumed` 能证明这一阶段，不能证明模型已经读完或执行完 |
| 已进入实际模型请求 | 已随第 N 次请求发送 | 需要补充输入到请求的确切关联；缺少该记录时只显示已加入，不造这个状态 |
| 提交被拒绝或确认失败 | 未发送／发送结果待确认 | 队列满等确定拒绝显示原因并保留内容；网络结果不明先查同一命令，再重试 |
| 撤回或暂停等特殊情况 | 已撤回／执行已暂停，消息仍在等待 | 撤回需后端确认；暂停不能默认等于消息已撤回 |

消息被采用后不立即消失：待正式时间线消息到达，以同一消息身份替换临时展示。重复事件和先后顺序变化都不能制造两条消息、闪空或退回“等待”。如果多条连续消息在同一次循环一起被采用，各条保留独立身份和顺序，允许共同关联到一次请求。

是否回答了某条消息是另一回事。模型可能一次回应多条或未充分回应某条；不因回复结束就为所有补充消息自动打上“已解决”。

### 6.3 三种模式的展示建议

| 模式 | 尚未进入循环 | 已加入与正式记录到达 |
| --- | --- | --- |
| 节点树 | 使用现有输入状态展示能力，呈现待加入消息和目标 Agent；与实际执行节点有明确的文字和形态区别 | 原消息原位更新为已加入，正式节点按真实关系接入树；不得提前画成当前模型请求已读到它 |
| 对话模式 | 保留用户气泡并标注等待；连续补充可视觉分组但不拼接原文 | 气泡移除等待标记并可查看采用时间或关联请求；避免只按发送时刻让它看起来早于已经发出的回复 |
| 精简模式 | 输入区附近显示“待加入 2 条”，可展开逐条文本、附件和状态 | 同一条目更新状态后进入紧凑消息列表；保留失败重试入口，不仅弹一次会消失的提示 |

时间表达建议保留“发送时间”和“加入时间”，默认只显示必要状态，详情中可查看两者。多个窗口操作同一会话时，各自的展开偏好独立，消息状态一致；切换会话不转移或重新发送等待中的内容。

### 6.4 必须提前考虑的情况

1. 快速连发：A、B、C 依次收到，可能一起进入下次请求；不能假定一条消息对应一个独立回复。队列顺序由服务端确认，前端序号只是显示信息。
2. 模型刚结束时新消息到达：决定它属于当前运行还是下一次运行必须由后端完成；两个窗口同时提交不能启动两个竞争执行器。
3. 工具运行或等待审批：补充不视为批准、拒绝或回答问题，不修改已确定的工具参数。等待原因可见，必要时用户通过原停止或审批入口行动。
4. 子任务运行：消息发给主 Agent 还是子 Agent 取决于明确的目标选择，不因用户正在看某个子节点而静默改投递目标。主 Agent 等待子任务时需明确补充何时可采用。
5. 循环上限、暂停、错误：尚未采用的输入保留为待处理，告诉用户需要继续；不要循环自动重启绕过上限，也不要把等待结束策略在失败后自动触发。
6. 断线、页面刷新、服务重启：复用已有持久输入与恢复流程，核对接收、采用和完成记录；恢复后不会丢失已确认消息，也不会重放已经执行的消息。
7. 队列满：现有新输入接口上限为 16，拒绝时保留原文和附件。旧的无 `commandId` 路径存在移除最早输入的兼容行为，后续统一入口时应明确处理，不能承诺所有入口现在都不会丢弃。
8. 重试：网络结果未知时沿用原命令身份查验或重试；用户修改内容则产生新命令身份，不能复用已接收命令发送不同内容。
9. 编辑与撤回：初版不承诺编辑已接收消息。若加入撤回能力，后端必须同时检查是否已经采用；撤回与采用同时发生时返回明确结果，界面不能先删除再假装撤回成功。
10. 附件与目标失效：消息被接收后，其附件在等待期间必须仍可读取。归档、删除会话或分支变化不能让消息悄悄转发到另一个目标，需明确拒绝或保留待处理原因。
11. 连续消息包含压缩指令或新计划：按实际采用顺序关联统计和清单更新。输入入队时不增加当前上下文占用，真正纳入请求后才进入请求柱图。

### 6.5 建设顺序与亮点

先把现有接受、排队、采用、正式消息四段展示统一并验证异常恢复；再决定是否增加“任务结束后处理”和队列撤回。用户能从任意模式知道“我这条消息在哪里、何时被采用”，还可从采用记录跳到对应请求统计，这比单独显示一个排队数字更有解释力。
