# Plan 操作方案 v1.0

> **状态**：强制执行。
>
> **适用范围**：所有需要实施的新任务，以及现有实施计划的后续维护。
>
> **核心路径要求**：所有 Plan 文档必须写在仓库的 `docs/plan/` 目录树内，禁止写在仓库其他位置。

## 1. Plan 文档位置与结构

每个大型任务由一个总任务文档和若干小任务文档组成：

```text
docs/plan/
├── <task-id>.md
└── <task-id>/
    ├── 01-<subtask-name>.md
    ├── 02-<subtask-name>.md
    └── ...
```

1. 总任务文档固定写在 `docs/plan/<task-id>.md`。
2. 小任务文档固定写在 `docs/plan/<task-id>/`，每个小任务单独一个 `.md` 文件。
3. 总任务必须汇总并链接其包含的全部小任务，不允许存在未登记的游离小任务。
4. 总任务至少包含：目标与边界、批次、小任务清单、依赖、步骤进度、批次综合测试、用户审批、计划删除状态。
5. 小任务至少包含：所属总任务、状态、依赖、范围与非目标、执行步骤、定向测试、完成标准。
6. `docs/plan/` 整个目录树是受 `.gitignore` 排除的临时工作区，任何总任务或小任务 Plan 均不得加入版本控制；发现已被跟踪的 Plan 时，必须只从 Git 索引移除并保留本地工作文件，不改写既有提交历史。

## 2. 拆分与分布执行

1. 新任务先拆成若干可独立执行、可独立验证的小任务，再开始实现。
2. 每个小任务只承担一个明确目标；范围可以交给不同执行者分布执行，但共享文件、前后置依赖和互斥关系必须在总任务中注明。
3. 小任务状态统一使用：`未开始 / 进行中 / 阻塞 / 已完成`。
4. 总任务状态统一使用：`规划中 / 执行中 / 待批次综合测试 / 待用户审批 / 审批通过待删除`。
5. 同一批次可以分布执行无冲突的小任务；有依赖的小任务必须按依赖顺序执行。

## 3. 执行与进度同步

1. 实现前，先在 `docs/plan/` 建立或更新总任务和全部已知小任务文档。
2. 小任务每完成一个执行步骤，立即勾选小任务文档中的步骤，并同步总任务清单中的 `已完成步骤 / 总步骤`。
3. 执行步骤、定向测试和完成标准全部通过后，才可把小任务标记为 `已完成`，并在总任务中勾选该小任务。
4. 小任务的定向测试用于尽早发现局部问题，不替代批次综合测试。
5. 后续发现问题时，将关联小任务重新标为 `进行中` 或 `阻塞`，同步总任务，禁止保留虚假的完成状态。

## 4. 批次综合测试

1. 只有一个批次的所有小任务均为 `已完成` 后，才将总任务标为 `待批次综合测试`。
2. 全量测试、类型检查、构建、静态检查、跨模块回归以及约定的人工验证，统一在总任务文档中执行并记录。
3. 任一综合测试失败，总任务退回 `执行中`，重新打开关联小任务；修复并通过定向测试后，重新执行受影响测试和该批次的完整综合测试。
4. 自动化通过但人工验证未完成，不算全量通过，总任务仍保持 `待批次综合测试`。
5. 多批次任务逐批执行本流程；所有批次完成后，按总任务约定完成最终全量回归。

## 5. 用户审批与最终删除

1. 全部批次及最终全量回归通过后，将总任务标为 `待用户审批`，向用户报告结果并暂停后续归档动作。
2. 测试通过不等于审批通过；只有用户明确表示批准，才将状态改为 `审批通过待删除`。
3. 用户要求修改时，保留全部 Plan，重新打开对应小任务并返回执行与测试流程。
4. 用户审批通过后，删除 `docs/plan/<task-id>.md` 和 `docs/plan/<task-id>/` 下的全部小任务 Plan；同时清理其他 Plan 对它们的临时引用。
5. 最终删除仅针对任务 Plan。模块说明、架构决策、操作规范、测试规范及用户要求保留的验收证据不得随 Plan 删除。
6. 未经用户明确审批，不得提前删除总任务或任何小任务 Plan。

## 6. 总任务最小清单

- [ ] 已在 `docs/plan/` 建立总任务和每个小任务的独立文档。
- [ ] 总任务已登记全部小任务、批次、依赖、状态和步骤进度。
- [ ] 每个小任务完成一步后已同步总任务进度。
- [ ] 本批次全部小任务均已完成。
- [ ] 本批次综合测试已全量通过。
- [ ] 所有批次及最终全量回归已通过。
- [ ] 用户已明确审批。
- [ ] 已删除总任务及全部小任务 Plan。
