# 按场景开展需求调查与设计

> 状态：通用执行规范。
> 适用范围：需求澄清、技术选择、完整设计、现有项目需求审核及实施交接。
> 权限：本文规定工作方法和结果要求，不授予实验、产品修改、外部操作、模型切换或其他 Agent 执行权限。具体授权、审批、暂停范围与人工验收遵守采用项目的协作规范，由[入口模板](entry-template.md)的项目配置区直接链接。

## 1. 目标与职责

先判断需求能否解决真实使用问题，再选择合适的技术；调查和讨论逐步形成完整、经确认的需求与设计文档，满足项目开工条件后进入实施。设计方法随问题选择，完成标准保持一致。

AI 负责查证事实、发现矛盾、提出候选和有依据的建议。用户决定目标、重要取舍及功能行为；不改变约定的内部实现细节由执行者安排。已有实现只证明当前行为，不能替代目标要求；用户提出的技术或功能可能是解决问题的建议，也可能是硬性限制，存在实质歧义时先确认。

AI 应主动指出方案与场景不符、重复功能、不必要复杂度或成本不合理之处，说明依据、影响与替代建议。可以建议复用、简化、调整流程或暂不开发；不能迎合用户而隐瞒缺陷，也不能凭个人偏好推翻用户目标。没有证据时明确是推断或待核实。

优化目标是讨论、开发、验证和返工的总成本。文档长度、提问次数、搜索数量及单次模型价格都不能单独证明质量或成本改善。

## 2. 从当前问题选择方法

### 2.1 阅读与操作顺序

1. 从项目入口确认任务范围、授权和相关模块，判断处于调查、设计、只读审核还是已批准实施。
2. 找出阻碍当前决定的主要未知，按第 2.2 节选择主要方法；无可靠文档入口时先按[存量项目梳理指南](existing-project-guide.md)建立事实入口。
3. 按第 3 节组织讨论，第 4 节查证关键能力，第 5 节完成技术选择。
4. 用第 6 节检查完整行为，再按第 7 节核对当前检查点；必要时返回受影响层。
5. 按第 8 节整理交付资料，取得项目要求的实施授权后交接；第 9 节说明模型分工与成本。

已经明确且未变化的内容直接复用，不逐次重读所有规范。小型任务可以在一轮完成，不强制搜索、实验、固定数量的候选、提问轮数或单独计划；必要的影响检查不能省略。大型任务也不要求使用全部方法。

### 2.2 方法选择表

这些是可组合的分析方法，不要求学习或照搬整套理论。选择由 AI 根据实际场景与证据判断，不通过关键词自动决定业务行为。

| 当前问题 | 主要方法 | 操作路径 | 结果与返回条件 |
| --- | --- | --- | --- |
| 目标模糊，用户给出的是功能或技术名 | 先探索问题，再比较解法 | 了解使用者、当前做法、困难和目标；区分目标、例子与限制；先探索解决方向，再集中比较可行方向 | 得到已确认的问题、范围和成功条件；方向不能解决问题时返回目标 |
| 功能齐全但使用不顺畅 | 按完整使用过程逐步检查 | 从触发、准备、操作、等待、系统反馈到最终结果，核对相关人员、设备、失败与恢复 | 每个关键困难对应需求或经确认的不纳入决定；推演不能冒充真实用户研究 |
| 速度、容量、稳定性或资源限制不明确 | 用具体条件描述质量要求 | 明确环境、触发、对象、响应和可观察标准；核实当前基准及限制来源 | 得到可验证的要求；数值无依据时补调查或询问，不自行编造阈值 |
| 多种技术可行但难以选择 | 先确定比较标准，再比较方案 | 确认硬性限制及取舍，核实能力与版本，按第 5 节比较项目适配与成本 | 得到有依据的选择、缺陷及改选条件；方案不满足硬性限制时返回条件或候选 |
| 关键能力或假设可能使方案失败 | 优先核实决定性假设 | 先查官方资料和项目环境；仍不能判断时按第 4.3 节提出最小实验 | 明确证实、否定或尚未证实；必要条件未证实时不能据此实施 |
| 多模块、多端、数据或事件互相影响 | 按操作、状态与接口检查 | 从用户操作检查到最终结果，再从结果倒查所需数据、调用方和失败处理 | 得到各端一致的约定；发现缺失或矛盾返回最早受影响的设计层 |
| 已有行为不符合需求，尤其重复修复失败 | 先查原因，再做最小修正 | 对比预期与实际，复现并收集证据，提出可排除的原因，核对实际入口、配置覆盖及官方用法 | 原因与修正有证据联系；原因不明继续调查，预期冲突返回需求讨论 |
| 审核现有项目是否符合已确认场景 | 按需求与证据逐项对照 | 从需求查设计、实现和验证；再从重要实现查需求依据，按第 6.3 节报告 | 得到差异、影响、建议及待决定事项；只读审核不自动授权修改 |

方法选择简述：**当前未知是什么 → 为什么此方法适合 → 需要哪些证据 → 预期结果 → 何时换方法或返回。** 通常选择一个主要方法，需要解决另一类问题时再组合其他方法。改变调查方法不必重复审批；涉及目标、成本、范围或执行权限变化时，按项目政策确认。

例如跨设备同步：先明确哪些设备、哪些内容及离线预期，再比较技术，核实决定性的部署能力，最后检查多端状态与恢复约定。不能仅因为用户提到“同步”就直接选择某种数据库或队列。

## 3. 从整体到细节讨论

### 3.1 层次与场景

| 层次 | AI 调查与说明 | 需要明确的结果 |
| --- | --- | --- |
| 目标与范围 | 谁在什么环境下遇到什么问题，当前如何处理，期待什么改善 | 目标、场景、成功条件、必须保持的行为及不包含项；区分硬性限制和偏好 |
| 整体方案与职责 | 现有能力、可复用部分、主要方案、依赖、可行性及重要取舍 | 方案方向，用户、模型、程序和模块的职责，必要的数据与旧功能处理 |
| 完整功能流程 | 从触发到结果的操作、状态、数据变化及副作用 | 正常与重要失败过程、完成含义、异常反馈与恢复 |
| 接口与交互细节 | 按第 6.1 节逐项检查读写双方和调用方 | 功能行为和跨模块约定明确，界面需求与实际可取得数据相符 |
| 整体复核 | 核对场景、需求、设计、证据和验收之间的关系 | 反例已处理、设计完整、可交接，并满足项目的实施授权条件 |

覆盖典型过程以及会改变设计的重要失败和边界情况，不机械规定场景数量。上层方向未定时，可以调查下层判断可行性，但不能将下层猜测写成已确认方案或提前实施。

场景记录可采用：**使用者与环境 → 触发与前提 → 当前困难 → 期望过程和结果 → 失败与恢复 → 成功标准**。输入、规模或体验目标需要可观察，无法确定时保留问题；不要凭空把“快”“方便”换成未经确认的数字。

### 3.2 提问与关联影响

先查能从项目文档、代码、测试及公开资料确认的事实，不将调查工作转交用户。按关联主题从目标、方向逐步问到细节，避免方向未定时集中询问大量字段。

以下情况需要继续讨论：

- 同一句需求的不同理解会导致不同使用结果，或缺少决定性场景、环境与成功标准。
- 候选方案改变操作、费用、保存方式、部署条件或职责分工。
- 正常过程明确，但关键失败、取消、结果未知或恢复方式尚未确定。
- 用户回答影响此前决定，或技术证据推翻原方案。

每轮采用：**当前问题 → 已知事实 → 缺少的决定 → 候选及影响 → AI 建议与理由 → 用户决定 → 文档和关联影响更新**。问题应让用户判断真实取舍，不要求审批普通变量或函数名称。

每次回答后检查前端、后端、接口、数据、其他调用方和验收是否受影响。已确认且未变化的内容不重复询问；新事实导致重问时说明变化。用户未反对、没有回应或 AI 推荐均不等于批准。

调查事实、已确认决定、候选与未决问题分别记录，位置见[计划规范](plans.md#21-设计记录与实施授权)。讨论期间持续完善文档，状态与正式事实的区别遵守[内容规范](content.md#71-设计记录与正式文档)。

## 4. 主动调研与可行性证据

### 4.1 何时搜索与如何核对

涉及新技术、新依赖、外部服务、不确定的能力或版本限制、部署条件、可能变化的费用或维护状态时，主动查询公开资料；已有可靠证据足够时不机械重复搜索。

按“影响决定的问题 → 搜索 → 阅读原始资料 → 核对版本与条件 → 对照当前项目 → 寻找不利证据 → 更新结论”执行。优先调查一旦判断错误会推翻方案、造成大量返工或证据最薄弱的关键事项。

- 官方文档、版本说明和维护者资料优先；社区讨论可提供线索，但核实其版本、环境和复现条件。
- 不只查询如何实现，也查询不支持的场景、已知限制、必要配置、迁移代价和更简单的替代方式。
- 官方支持某能力不代表当前项目可用；核对项目实际版本、依赖、部署、配置与调用方。
- 搜索摘要不能替代原文证据，没查到不能解释为不支持；无法联网或访问资料时明确尚未核实，不伪造引用。
- 仓库实现证据从权威文档进入项目源码、类型与测试；第三方能力按项目允许的调查方式核实。

### 4.2 证据与停止条件

| 关键问题 | 为什么影响决定 | 来源及查阅日期 | 适用版本和条件 | 结论与项目影响 | 未知与下一步 |
| --- | --- | --- | --- | --- | --- |
| 写需要回答的问题 | 写不成立时会影响什么 | 官方链接、项目路径或实验记录 | 不将别的版本和环境混用 | 区分资料事实、推断、实验结果和用户决定 | 没有证据时明确缺口及核实方法 |

证据在设计中只维护一份，其他位置引用。决定性的结论必须能回到来源；时间敏感的价格、版本和服务条件注明查阅日期，不能当作永久事实。

当关键问题已有证据、项目适配条件清楚、剩余调查不会影响当前选择时，结束本轮调研。重要未知仍存在时说明阻塞、所需条件及受影响决定；需调整范围时交用户决定。来源、版本或环境改变后，重新核对受影响结论，不机械推翻无关决定。

### 4.3 设计期小实验

资料不足以证明关键可行性时，可以提出最小实验。先说明待核实假设、必要性、范围、环境与输入、预期结果、失败含义、费用与外部访问、证据保存及清理责任，获得具体授权后执行。授权不足时继续允许的调查或明确阻塞，不能把实验当成默认权限。

实验只回答约定的可行性问题，与正式产品实施分开；不得借实验提前开发完整功能。记录实际环境和结果，模拟数据、其他版本或隔离环境的成功不能冒充目标环境保证。实验、实施期间最小校验和整体完成后的集中测试是不同活动，分别按项目政策执行。

## 5. 技术方案选择

先确认不可违反的限制，再确认使用体验、成本、性能、维护等重要取舍，最后比较候选。不先选喜欢的技术再倒推评价标准；不以热门程度或无依据的综合分代替判断。硬性限制不满足，不能靠其他优点抵消。

| 比较方面 | 每个有效候选需要说明 |
| --- | --- |
| 场景满足程度 | 满足哪些目标，哪些做不到，是否改变用户操作 |
| 适用环境 | 版本、平台、网络、运行资源、部署与配置要求 |
| 当前项目适配 | 已满足哪些条件，能复用什么，需要新增或替换什么 |
| 改造与影响 | 接口、数据、旧功能、其他调用方、迁移顺序和退出代价 |
| 总成本 | 开发、运行、维护、学习及返工成本，估计的依据与不确定性 |
| 优势与缺陷 | 对本次目标的具体收益、限制、失败风险及应对条件 |
| 可验证性 | 依据、待核实能力、验证方法与必要环境 |
| 推荐结论 | 为什么推荐或不推荐，何种变化会使选择不再适用 |

存在有效的简单方案时，应比较复用现有能力、调整流程或不新增组件的做法。不为凑数量加入明显不合适的候选；只有一个可行方向时解释限制及排除依据。无依据不提供精确工期、性能或价格数字。

用户确认重要取舍与最终选择后，保留当前决定的背景、理由、正负影响和改选条件，避免接手者重新猜测。有效候选资料按[计划规范](plans.md)管理，长期结论进入所属权威文档；不建立多份可独立变化的决定正文。

## 6. 完整设计与现有项目审核

### 6.1 功能细节检查

对每项功能，从“用户或外部入口触发 → 请求 → 处理与保存 → 响应或事件 → 使用者看到结果 → 失败恢复”检查以下适用内容。已有可靠约定直接引用；无关项说明原因，不为填表新增机制。

| 方面 | 必须回答的问题 |
| --- | --- |
| 场景与职责 | 谁在什么条件下操作、作用于哪个对象、期望什么结果？判断由用户、模型还是程序完成？哪些行为不允许？ |
| 入口与操作 | 入口是否可发现，需要什么上下文和输入？默认值与校验依据是什么？何时可操作、禁用及原因是什么？提交、取消、关闭和返回如何处理？ |
| 界面状态与反馈 | 初始、加载、空数据、编辑、提交中、成功、失败、无权限和断开连接时展示什么、允许什么？草稿保存、刷新、会话切换及多窗口如何处理？必要的窄窗口、键盘与帮助如何支持？ |
| 请求与响应 | 调用入口、方法、身份、目标、字段类型、必填性、默认值、单位、范围、缺失与空值含义是什么？谁产生和校验？成功、失败和结果未知如何区分？字段与界面、保存如何对应？分页、过滤、排序怎样约定？ |
| 事件与异步 | 请求、任务与事件如何关联？已接受、已保存、已生效和已完成分别如何证明？流式过程、延迟、乱序、重复、取消与完成同时发生、订阅恢复如何处理？ |
| 处理与持久保存 | 接口到处理再到存储的路径、校验顺序、状态变化、保存和生效时机及副作用是什么？重复、并发、部分成功如何处理？哪些数据重启后保留，谁读写和清理？ |
| 异常与恢复 | 无效输入、对象不存在、权限变化、超时、网络中断、服务失败和保存失败时返回什么，用户看到什么？已发生动作如何处理，是否允许重试、由谁触发、如何防重复副作用？结果未知怎样查询？ |
| 数据与权限 | 谁可读写哪个对象？不同用户、会话、连接和模块如何隔离？敏感字段怎样保存、返回与记录？保留、删除和历史访问是否明确？ |
| 依赖与迁移 | 哪些客户端、插件、工具、后台任务、配置模板使用同一规则？第三方是否支持？需要什么环境？旧接口、入口与数据怎样处理，顺序有何约束？ |
| 验证与交付 | 怎样观察成功和失败？自动验证、真实服务与设备、用户操作分别检查什么？测试入口、数据、账号交付方式、环境和权限是否具备？是否包含部署，从哪里验收？ |

新增或变化的接口给出足以核对含义的正常请求响应和关键失败示例；异步流程给出必要的消息顺序或状态表。字段表、示例、界面和保存必须一致。

例如“保存设置”需要说明保存内容、是否立即生效、成功证明什么、失败后草稿怎样保留，以及重复提交、并发修改和响应丢失的处理。具体行为由已确认需求决定，本文不预设业务策略。

### 6.2 双向核对与反例

先从每个操作检查请求、处理与最终结果，再从每个界面结果倒查字段、生产方和取得时机，对关键失败同样核对。每项需求都应找到设计和验收方法，每项重要设计也应解释服务于哪项需求或必要限制，避免无依据地增加功能。

| 需求或场景 | 已确认行为与异常结果 | 设计位置 | 实现入口与调用方 | 验证方法与预期结果 |
| --- | --- | --- | --- | --- |
| 稳定编号或清晰名称 | 可观察结果 | 链接唯一说明 | 已有路径与符号；拟新增明确标注 | 区分自动验证和人工验收，写明前提 |

复用已有需求或验收表，不维护重复清单。主动寻找：哪项假设不成立会推翻方案，哪个场景最容易失败，是否把请求成功当作用户任务完成，是否把复杂度转移给用户或接手者，以及是否有同样满足目标的简单做法。结论给证据和可执行建议，不要求输出内部思考过程，也不为完成反思而编造缺陷。

### 6.3 现有项目审核

审核开始先确定适用需求、场景、对象版本或工作区、环境和允许的验证范围。需求本身未确认时，先澄清，不能自行建立标准后判项目不合格。用第 6.2 节的对应关系查找证据，记录：

| 场景与要求 | 当前证据和适用对象 | 结论 | 差异与影响 | 建议及所需决定 |
| --- | --- | --- | --- | --- |
| 已确认预期结果 | 设计、源码、测试或实际使用证据 | 符合／不符合／尚未验证／经确认不适用 | 说明影响谁及何种行为 | 建议先后顺序、技术选择和用户需要决定什么 |

已有代码不等于已验证；静态检查通过不等于真实使用符合。证据不足标“尚未验证”，不以猜测补齐；不适用需有范围依据。按影响及前置依赖提出建议，发现问题不自动获得修改或新增功能的授权。

## 7. 结果检查点与返回条件

检查点是可观察结果，不是固定对话轮数、审批次数或新的任务状态。每项记录检查对象、依据、当前结论、未解决问题及下一步；可以合并讨论，但不能省略必要结果。用户同意不替代技术证据，测试通过不替代目标和使用场景确认。

| 检查点 | 通过条件 | 不满足时 |
| --- | --- | --- |
| 问题与场景明确 | 使用者、环境、困难、范围、限制、必须保持的行为与成功标准明确，目标获确认 | 返回目标讨论，不以技术名称代替问题 |
| 事实与关键未知查清 | 项目环境有依据，影响方案成立的未知有可靠结论 | 补调查、申请必要实验或明确阻塞；调整范围由用户决定 |
| 方案选择明确 | 比较标准明确，候选满足硬性要求，适配性有证据，重要取舍和选择获确认 | 返回条件、候选或目标，不以总分掩盖缺陷 |
| 完整设计成立 | 正常与关键失败过程相互一致，双向对应和反例检查完成，影响正确性的决定已解决 | 返回最早受影响层，重新检查依赖结论 |
| 终版可交接且获授权 | 第 8 节的资料完整、理解检查无关键缺漏，并取得项目要求的实施授权 | 补设计和文档，不把业务与技术选择缺口交给执行者猜测 |
| 实现与真实场景符合 | 整体需求完成核对后集中验证，技术结果与必要真实使用验收分别有证据 | 实现偏差修正；目标或设计问题返回讨论 |

发现矛盾时说明新事实、受影响决定和范围，返回最早出问题的层次；受影响结论不能继续作为实施依据。没有变化的决定继续有效，不重复询问。暂停范围、重新确认及恢复实施权限由项目协作政策规定。

方法、方案或环境变化后，检查依赖该变化的证据、设计和验收项。不能通过换个方法名称跳过失败的检查点，也不能在等待决定时把未确认内容写成现行规则。

## 8. 终版文档与交接准备

终版可以是一份完整文档，也可以是一个入口连接多个专题；详细程度以接手者无需猜测业务和关键技术决定为准。根据任务规模包含以下适用内容：

1. 目标、使用者、场景、范围和成功条件。
2. 当前项目事实、限制、必须保持的行为及证据。
3. 调研结论、来源、适用版本与条件、关键假设的验证结果。
4. 候选比较、当前选择、理由、缺陷和改选条件。
5. 完整操作、状态、接口、数据、副作用、失败与恢复约定。
6. 依赖、迁移、部署要求及其他调用方影响。
7. 实施路径与关键符号、任务顺序、共享文件安排、执行者可以自主决定的内部细节。
8. 每项需求的验证方法、输入条件、预期结果及人工验收范围。
9. 已确认决定、授权范围，以及遇到新问题时的停止和返回条件。

实施前整理为完整、相互一致且经确认的终版，影响当前实施范围的未决问题必须解决；不能把关键决定写成“开发时再看”，也不能仅标为后续工作来掩盖本次缺漏。范围调整需要用户确认。文档在讨论和实施中持续维护，确认终版不意味着禁止后续更新；具体状态与事实维护见[内容规范](content.md#71-设计记录与正式文档)。

交接理解检查：仅依据交付资料，说明交付目标、必须保持的行为、实际入口、依赖顺序、成功与失败的验证方法、必须停止并返回的问题，再与已确认设计对照。必须依赖原作者口头补充才能理解的关键内容，应补入文档。普通命名和函数划分不要求预先固定。

默认由当前执行者做文档自查；需要其他模型、新会话或独立执行者时，说明收益与成本，取得相应授权。自查不能标为独立评审，纸面推演不能标为实际模型执行验证。按[计划规范](plans.md)记录检查结果、剩余工作和当前授权。

## 9. 模型分工与总成本

高不确定性的调查、推理及整体决策需要相应能力；边界明确、资料充分、可验证的实施任务可以由满足能力要求且成本较低的模型承担。按风险、依赖、理解与工具能力和验证需要推荐，不将复杂度固定映射到型号、价格或厂商。模型切换和分配权限遵守项目政策。

交接资料提供最小充分上下文，不复制全部聊天。执行者先核对资料、真实工作区与有效授权，普通实现问题自行解决；遇到新业务决定、关键能力不成立或文档矛盾时按项目政策返回设计，不能为持续推进而猜测。

是否降低成本应观察关键遗漏、重复纠正、返工、交接补充、总耗时与模型费用。未实际测量前不承诺提升比例，也不假定长文档或换成经济模型必然更便宜。

## 10. 方法效果检查与参考来源

采用时可选模糊需求、过重技术方案、版本能力不确定、跨端行为、重复修复、只读审核、小型明确修改及模型交接等场景，对照预期动作、证据和返回条件。区分文字自查与实际任务试用，实际试用遵守项目授权。过程有效性看问题是否更早暴露、建议是否有依据、交接是否减少猜测，不看表格数量或模型自评分。

以下原始资料于 2026-10-19 查阅，用于解释方法来源，不授予执行权限，也不替代当前项目要求：

- [Design Council：Double Diamond](https://www.designcouncil.org.uk/our-resources/the-double-diamond/)：先探索并明确问题，再探索和验证解法；借鉴其思路，不将其当作逐步执行手册。
- [NASA：系统设计流程](https://www.nasa.gov/reference/4-0-system-design-processes/)：场景、需求、设计与验证相互对应，检查可行性、必要性和过度规定；不照搬航天项目流程规模。
- [GOV.UK：方案探索与高风险假设](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works)：优先验证决定性假设、关注完整使用过程；不采用其固定周期或默认实验权限。
- [AWS：技术决策记录](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)：记录背景、决定、理由和后果；历史保存方式依项目文档政策，不强制采用不可变记录制度。
- [Anthropic：有效 Agent 工作流](https://www.anthropic.com/engineering/building-effective-agents)：明确评价标准、简单工作流与能力匹配；不自动引入多 Agent、固定模型映射或程序化业务决策。
