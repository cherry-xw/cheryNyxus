# 文档内容与维护规范

> 状态：强制执行。
>
> 适用范围：仓库内所有持久文档；临时实施计划只遵守本规范的定位、链接与去重要求，结构和生命周期另见 [Plan 操作方案](./plans.md)。

## 1. 目标

文档必须让首次进入项目的人或大模型通过少量、确定的跳转完成以下定位，而不必先全仓搜索：

```text
任务意图 -> 所属领域 -> 权威模块文档 -> 代码入口与关键符号 -> 相关测试
```

优化目标按优先级排序：

1. **定位成本**：读者能从稳定入口逐层缩小到完成任务所需的最小代码集合。
2. **事实唯一**：同一契约、状态机、规则或流程只有一个权威来源。
3. **上下文最小**：入口文档只导航，专题文档只解释代码无法直接表达的知识。
4. **变更可信**：代码边界、契约或入口变化时，相关文档必须同步更新并验证。

文档不以覆盖所有代码为目标。容易从单个文件直接读出的局部实现，不得转抄成长期文档。

## 2. 权威层级与阅读路径

文档采用 L0 至 L4 五种导航角色，按需渐进披露。每一级只回答本级问题，并链接到下一级：

| 层级          | 典型位置                                        | 必须回答                                               | 不得承载               |
| ------------- | ----------------------------------------------- | ------------------------------------------------------ | ---------------------- |
| L0 项目入口   | `AGENTS.md`、根 `README.md`                     | 先读哪里、全局硬约束、如何启动和验证                   | 模块实现细节           |
| L1 文档总入口 | `docs/README.md`                                | 领域边界、跨领域权威入口                               | 专题正文、文件清单     |
| L2 领域入口   | `docs/<domain>/README.md`                       | 模块边界、任务到模块的路由                             | 具体算法和历史过程     |
| L3 模块入口   | `docs/<domain>/<module>/README.md` 或模块单文档 | 模块职责、代码地图、关键流程、依赖、专题索引、测试入口 | 大段源码、逐次变更日志 |
| L4 专题文档   | 模块目录内的主题文件                            | 一个稳定主题的契约、决策、流程或操作方法               | 其他主题的重复定义     |

已从统一入口确定领域或模块时，直接进入对应 README，无需重复读取上层索引。范围不明时按 `L0 -> L1 -> L2 -> L3 -> 必要的 L4` 定位。任何常见任务都应在不超过四次文档跳转后到达代码入口；超过时必须合并无信息增益的中间层或补充上级路由。

遇到冲突时，按以下顺序确定事实：

1. 协议、状态机和公共数据模型以其权威契约文档为准。
2. 强制行为以 `docs/standards/` 中最小适用域的规范为准。
3. 当前实现细节以代码和自动化测试为准。
4. 计划、归档、提交记录和注释不得覆盖当前权威文档。

## 3. 文档职责

### 3.1 导航 README

所有导航 `README.md` 必须保持短小，并至少包含：

1. 本目录负责什么、不负责什么。
2. 直接子模块或专题的链接及一句话职责。
3. 面向常见修改意图的路由；领域较小时可与子模块表合并。
4. 跨领域事实应前往哪个权威文档。

领域入口的推荐格式：

| 修改意图     | 先读       | 代码范围     | 验证入口         |
| ------------ | ---------- | ------------ | ---------------- |
| 添加某类能力 | `模块文档` | `稳定代码根` | `测试文件或命令` |

不要在导航 README 中复制下级专题内容，也不要只列名称而不说明何时进入该模块。

### 3.2 模块入口

模块入口是减少代码搜索的核心。每个有独立业务职责或稳定代码边界的模块，必须提供下列信息；没有对应内容时明确写“无”，不得编造占位内容。

1. **职责与非职责**：模块拥有的事实、明确不处理的边界。
2. **任务定位表**：常见修改意图对应的专题文档、代码入口、关键符号和测试。
3. **代码地图**：仅列稳定入口、核心目录和跨模块适配点，不枚举所有文件。
4. **关键流程**：用 3 至 12 个步骤说明入口、关键转换、副作用与出口。
5. **不变量与失败语义**：调用方不能从类型签名直接得知、但修改时必须保持的行为。
6. **依赖与影响面**：本模块依赖谁、被谁调用、契约变更会影响哪些模块。
7. **扩展点**：添加常见能力时应修改的注册点、工厂、配置或适配器。
8. **验证入口**：定向测试文件、测试筛选词、必要命令和人工验证边界。
9. **专题索引**：每个专题的适用场景和权威范围。

任务定位表使用以下统一格式：

| 修改意图           | 权威说明      | 代码入口          | 关键符号         | 验证入口                      |
| ------------------ | ------------- | ----------------- | ---------------- | ----------------------------- |
| `<用户或开发任务>` | `<专题链接>` | `<实现文件路径>` | `ExportedSymbol` | `<测试路径或命令>` |

### 3.3 专题文档

一个专题文档只解释一个可独立演进的主题，并优先按以下顺序组织：

1. 结论或现行契约。
2. 适用范围与非目标。
3. 入口和关键符号。
4. 数据流、状态机或调用顺序。
5. 不变量、失败语义与边界情况。
6. 依赖、调用方与变更影响。
7. 扩展或修改方法。
8. 验证方法。

只有存在真实内容的章节才保留。不得为了套模板制造空章节。

## 4. 代码定位规则

代码引用必须能直接帮助定位：

- 使用仓库相对路径，并在 Markdown 中链接真实文件或目录。
- 路径旁使用反引号标出关键导出、类、函数、配置键、事件名或测试筛选词。
- 优先引用稳定入口和命名符号，不使用容易漂移的行号作为唯一定位手段。
- 同一任务涉及多个文件时，说明各文件的职责和先后关系，不只堆叠路径。
- 生成文件、构建产物和第三方代码不作为实现入口；需要说明时指向其源文件或生成命令。
- 无法用稳定符号定位的逻辑，应先明确所属模块和搜索词；不要粘贴大段源码代替定位。

有效示例：

```md
运行时解析从 [`src/agent/runtimeResolver.ts`](../../../src/agent/runtimeResolver.ts) 的
`RuntimeResolver.resolve()` 进入；定向验证见
[`test/agent/runtimeResolver.test.ts`](../../../test/agent/runtimeResolver.test.ts)，筛选词 `sense group`。
```

无效示例：

```md
配置相关代码在 src 下面，可以搜索 provider。
```

## 5. 内容压缩与单一事实源

文档只保留能减少后续阅读或搜索的内容。下列内容应删除、改写或转移：

| 内容                                         | 处理方式                                  |
| -------------------------------------------- | ----------------------------------------- |
| 可从类型或短函数直接读出的字段、参数和控制流 | 链接代码符号，不转抄                      |
| 按日期不断追加的修复记录                     | 合并为现行规则；审计必要时移入 `archive/` |
| 已完成计划、步骤清单和交接过程               | 按计划规范删除；确有审计价值才归档        |
| 多处重复的协议表、状态机和配置规则           | 保留唯一权威版本，其他位置只链接          |
| 没有决策价值的背景叙述                       | 删除或压缩为一段“为什么”                  |
| 完整文件树或会频繁变化的文件清单             | 改为稳定入口、核心目录和扩展点            |
| 仅对当前任务有用的临时定位笔记               | 放入 `docs/plan/`，仅在需要跨环境恢复时提交；构建物和运行产物放入 `verify/out/` 并忽略 |
| 只提供一条跳转、没有独立规则、操作方法或事实的页面 | 合并到最近的 README 或权威入口；不得单独建导航页 |

同一事实的 owner 按边界确定：跨模块契约归项目配置的共享文档领域，实现事实归实现模块，强制规则归 `standards/`，操作步骤归 `guides/`，验证边界归 `quality/`。其他文档必须链接 owner，不得维护第二份可独立演进的副本。

## 6. 变更同步矩阵

写文档不是独立收尾动作。发生以下变更时，必须在同一任务中同步对应文档：

| 代码或行为变化                                   | 必须检查和更新                                  |
| ------------------------------------------------ | ----------------------------------------------- |
| 新增、删除或移动稳定模块                         | L1/L2 导航、模块入口、仓库内链接                |
| 入口文件、公共符号或注册点变化                   | 模块任务定位表、代码地图、扩展点                |
| 协议、状态机、公共数据模型变化                   | 唯一权威契约、调用方链接、相关测试入口          |
| 跨模块依赖或副作用变化                           | 双方模块的依赖与影响面，但事实只在 owner 处定义 |
| 新增常见开发任务                                 | 所属领域或模块的任务定位表                      |
| 测试文件、命令或人工验收边界变化                 | 模块验证入口和 `quality/` 中的权威说明          |
| 只改变局部实现且入口、契约、流程和扩展方式均未变 | 无需制造文档改动                                |

发现文档与代码不一致时，不得把未经验证的旧描述继续扩写。先根据代码和测试确认现行事实，再更新权威文档并删除冲突内容。

## 7. 写作与评审流程

新增或修改持久文档时依次执行：

1. 操作前从统一入口的项目路由确认领域和事实 owner；范围不明时读取 `docs/README.md`。
2. 检查是否已有相同主题；优先更新或链接，不新建近义文档。
3. 明确目标读者会用什么任务意图寻找该内容。
4. 先更新最近的导航或模块任务定位，再写必要的专题正文。
5. 使用路径加符号建立代码定位，补充验证入口和影响面。
6. 删除被新内容取代的重复描述、历史过程和失效链接。
7. 检查本地链接、源文件路径、孤儿文档和 `docs/plan/` 跟踪状态。

评审必须回答以下问题：

- 首次进入项目的读者能否从入口在四跳内定位到代码？
- 文档是否给出关键符号和验证入口，而不只是目录名？
- 是否出现需要再次全仓搜索才能判断职责、调用方或扩展点的模糊描述？
- 是否复制了代码、协议或其他文档中会独立变化的事实？
- 修改后是否仍描述当前状态，而不是保留变更前后的流水账？
- 代码未变化时，这篇文档是否仍提供代码本身难以表达的决策信息？
- 该页面是否有独立内容价值，而不是只把读者转到另一份文档？

任一答案不满足时，文档不得视为完成。

## 8. 自动化要求

大型项目应逐步把以下检查加入文档 lint 或 CI：

1. Markdown 本地链接和锚点有效。
2. 文档中引用的仓库路径存在。
3. 每个受管一级目录和大型模块存在导航 `README.md`。
4. 除显式归档外，持久文档都能从 `docs/README.md` 到达，不存在孤儿文档。
5. `docs/plan/` 的根入口、任务 README、未完成子计划和可复用验证说明可被版本控制跟踪；`verify/out/` 及其他运行产物不得跟踪。
6. 模块入口包含任务定位、关键符号和验证入口。

自动化只能证明结构可达，不能证明内容正确。契约、影响面和不变量仍需模块维护者评审。

## 9. 渐进采用

任务影响某模块文档时补齐其任务定位、关键符号和验证入口；修改专题时清理失效过程与重复事实。新模块直接提供最低可用结构，不要求一次性重写全部历史文档。规范目录名与领域划分按项目配置确定。
