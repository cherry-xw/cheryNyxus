# 实施计划管理规范

> 状态：强制执行。计划只维护当前目标、未完成工作、必要验证与恢复信息。项目参数由采用项目的配置维护。

## 0. 是否需要建立计划

小型、明确且本次能完成的工作无需建立计划；维护已有计划不另建一套计划。需要跨会话、拆分或持续跟踪时建立计划；用户明确要求时也建立。只需等待或简单恢复的任务允许单页计划；出现独立交接、多目标或复杂依赖时再拆小任务。任务扩大时仅为剩余工作建立计划，不补写开发历史。

## 1. 计划文档位置与结构

计划统一位于 `docs/plan/`。总入口为 `docs/plan/README.md`；每个任务入口为 `<task-id>/README.md`。恢复时先读总入口、再读目标任务，按需读取当前小任务，不先枚举整个计划树。

| 文档 | 独占维护的内容 |
| --- | --- |
| 计划总入口 | 任务链接、状态、一句话范围；每个实际任务目录恰好登记一次 |
| 总任务 README | 目标与边界、当前授权、小任务台账、依赖、唯一当前恢复检查点、待处理事项、最终验收入口 |
| 当前小任务文档 | 本项具体实施步骤、当前事实、剩余工作及可观察的完成条件 |
| 验证文件 | 验证对象、方法、当前结果与必要人工操作 |
| 权威模块文档 | 当前长期契约、行为和正式操作入口 |

1. 总入口使用连续的任务表格，不能用空行拆出无表头的任务行。任务目录与登记条目必须一一对应。
2. 单页计划在总任务标记 `计划形式：单页`；直接在 README 维护步骤、恢复与完成条件，无需空小任务文件。
3. 拆分计划由总任务台账维护小任务 ID、状态、复杂度及依据、依赖。即将执行或需要独立交接的小任务才创建文件并链接；远期未开始任务允许无文件。复杂度为 1 至 5，按风险、依赖和验证难度评估，不绑定模型名称、价格或厂商。
4. 小任务若重复声明状态，必须与台账一致；复杂度与依赖优先引用台账，避免多份维护。普通实现小任务完成后迁出有用事实、更新台账、移除文件链接并删除详细文件。
5. 设计比较与有效候选资料可以保留，只需有明确用途和入口；不因为文件没有任务状态就把它当作待删除任务。用户要求保留的有效方案按要求维护。
6. 计划入口、当前小任务、可交接脚本及验证说明纳入版本控制。运行产物忽略；忽略文件不等于允许长期堆积。
7. 总任务正文只保留一个“当前恢复检查点”，说明实际完成、剩余工作、下一步、当前授权、阻塞条件与必要工作区基准。新事实替换旧状态，不追加第二个“最新恢复点”。
8. Markdown 链接、任务台账、明确声明的状态与目录由[静态检查](plan-checks.md)比较；检查通过不能证明业务已完成。

### 1.1 文档创建时间

新建任务 README 和小任务文档在一级标题下、状态行之前写 `**文档创建时间：** YYYY-MM-DDTHH:mm:ss±HH:mm`，取实际创建时间，后续保持不变。总导航与验证资料无需此字段。

维护缺字段的历史任务时，优先补录可靠原始记录；仅有首次 Git 收录时间时注明来源；无法确认写“未知（历史文档未记录）”。不能以当前修改时间冒充原始创建时间。

## 2. 拆分与分布执行

总任务状态统一为 `规划中 / 执行中 / 待综合验证 / 待用户审批`；小任务状态为 `未开始 / 进行中 / 阻塞 / 已完成`。等待或暂停不另造总任务阶段，记录等待原因、恢复条件与下一执行人；只有用户明确要求才暂停。

先定目标、成功条件、必须保持的行为和未决事项，再决定实现；例子不自动成为固定参数。涉及现有实现时从权威模块定位真实代码与消费者，不把旧台账视为代码已完成的证据。即将执行的小任务说明稳定入口、关键符号、状态与数据路径、共享文件顺序、失败与恢复路径；远期任务只写目标、依赖和验收方向。

无冲突工作可以分配给不同执行者；共享文件和前置依赖要明确。同一任务内已经确认的 Agent 和授权在原范围内持续有效；仅在任务范围、风险或所需能力实质变化时重新评估并按项目政策确认，不逐步骤重复索要确认。分配权限由项目政策及用户授权决定。

跨任务依赖写出所需结果及其稳定入口。其他任务完成前引用其当前入口，完成后改指权威文档、正式代码或验证方法；不得只留下已删除计划的步骤编号。删除计划前核对其他活动任务的引用及文字依赖。

## 3. 执行与进度同步

实现、文档、引用和临时文件管理构成同一项交付。文档同步未完成时不得把该项标为完成。

| 变化 | 在继续依赖该变化的工作前同步 |
| --- | --- |
| 目标、方案、范围调整 | 总任务目标、受影响小任务和完成条件 |
| 文件、符号、配置或命令移动、重命名、删除 | 调用方、模块说明、活动计划、操作与验证入口；同时搜索正文和命令中的旧引用 |
| 有意义的实施步骤完成 | 当前步骤、实际剩余项；不能只追加“已处理” |
| 切换任务、出现阻塞或结束会话 | 唯一恢复检查点及下一执行人、下一步 |
| 验证对象或环境变化 | 受影响结论标为待重验；人工卡的地址和准备条件同步 |
| 提交或交接 | 对照当前工作区核对记录、引用与本任务临时文件 |

不要求每改一行代码就更新计划，但不得等到最后凭回忆补写。内容同步不等于逐步完整测试；实施时仅做必要最小校验，整体实现结束并逐项确认需求已完成后，才进行集中验证。项目可以进一步规定最小校验与最终测试范围。

普通小任务“已完成”表示实现、文档同步及约定的最小校验完成，不表示总任务综合验证通过。完成时把当前依赖事实及验证入口写回总任务，迁出长期内容，更新台账并删除详细文件。已有完成项出现缺陷时新增修正项，原完成摘要不伪造，当前限制明确登记。

### 3.1 待处理事项

待处理事项从任务建立起放在总任务 README，按发现时的性质分配：当前缺漏更新当前小任务；已完成部分的缺陷建立修正项；新增需求先确认范围；建议明确是否纳入；真实体验确认进入人工验收。不要把所有问题延迟到最后验收，也不要重复维护全文。

清零表示本次必须解决的事项已经解决，其他事项明确不纳入或已由用户同意转交并有去向；不能删除记录冒充解决。变更台账时在同一次修改中同步依赖、当前步骤和受影响验收项，不重建无关内容。

## 4. 最终综合验证与用户验收

拆分计划的最后小任务为“综合验证与用户验收”，整体实现与需求完成核对后进入；单页计划可直接在 README 承载。验收目标可以提前记录，验收文件可按需要提前准备，不等于提前开始完整测试。进入时总任务为 `待综合验证`。

1. **先核对需求完成**：逐项目标已有实现，必要文档和引用同步，本次必修反馈解决，临时文件已归位。未实现内容不能靠测试通过替代。
2. **集中自动验证**：每项记录编号、目标、可执行命令、结论、证据。结论统一为 `待执行 / 通过 / 失败 / 待重验 / 阻塞 / 不适用`。证据包含日期、验证对象的版本或工作区标识、环境、退出码、关键断言及产物位置；无产物明确写无。命令退出 0 不自动证明行为断言通过。
3. **必要人工验收**：视觉、交互、主观体验、真实设备、必须由用户授权或触发的动作可以保留人工项。操作卡放 `verify/manual-final.md`，提供实际入口、前提与账号交付方式、最小步骤、预计时间、期望现象和结论。尽量简短，一分钟是优化目标而非硬性上限。缺少环境或数据时标“阻塞”并说明谁补齐，不把未准备好的操作卡交给用户猜测。
4. **失败与重验**：失败时总任务退回执行中，登记修正任务。重验修改影响的行为和依赖；未变化的对象、环境及输入可以保留有效结论。公共契约或构建基础变化、影响无法判断时扩大检查。不能复用不适用的旧结果，也不机械重跑无关检查。
5. **审批准备**：全部必要项通过或有经用户明确同意的不适用范围，文档、引用及清理核对完成后进入 `待用户审批`。审批期间保留验收文件供审阅，不提前删除。
6. **抽样与权限**：是否抽样由用户或项目风险政策决定，不作为所有任务的固定门槛。抽样应核对对象、场景、断言与证据，而非只看日志存在。自动检查不能证明真实用户验收或授权；执行权限遵守项目配置。

## 5. 验证资产与临时文件

| 类型 | 位置与管理 | 结束处理 |
| --- | --- | --- |
| 一次性草稿、调试输出、命令中间文件 | 系统临时目录下按任务建立专用目录，如 `/tmp/<task-id>/`；禁止散放仓库根或源码目录 | 使用完清理，最迟本任务结束时清理 |
| 必须跨会话交接的验证脚本 | `<task-id>/verify/`，注明用途、运行前提与命令 | 无长期用途随计划删除；有价值的迁入正式位置 |
| 可重建运行产物 | `<task-id>/verify/out/` 或项目明确管理的输出位置；Git 忽略 | 无待核对用途后清理 |
| 正式测试与可复用方法 | 项目正式测试、指南或验证说明目录 | 正常维护，不存于临时计划作为唯一副本 |

需要恢复的脚本、方法与输入不能只放可能被清空的 `/tmp` 或个人缓存。原始输出可在受管理的仓库外位置保存；明确用途、负责人和清理时机，不把杂乱简单转移到外部目录。开发历史不要求迁为长期文档。

任务创建临时文件时就确定位置和清理范围；检查工作区中新建文件是否属于本任务，必要时在恢复点记录专用临时目录。只删除本任务明确拥有且不再需要的文件；未跟踪不等于垃圾，不能删除用户、其他任务或运行数据。静态扫描只报告确定的违规位置或可疑文件，不自动删除。

## 6. 用户审批与总任务完成

项目配置决定是否采用独立用户审批；默认保留。当前任务用户明确批准才执行最终收尾，已获得的完成批准包含按本规范清理计划，无需再次索要单独删除指令。批准实现方案不等于批准最终验收。

按以下顺序收尾：

1. 确认必要验证已完成、当前限制明确、用户批准适用于当前范围；不能以非空结论或无“待执行”代替全部必要项通过。
2. 确认长期契约、方法、正式测试及必要当前结论已迁入权威位置。
3. 检查其他活动计划、文档、命令中的依赖，更新指向本任务临时文件或旧步骤的引用。
4. 检查本任务所有新增文件和专用临时目录，包括计划目录外；迁出有用内容，清理已无用途的脚本、输出、缓存与备份。
5. 删除整个任务目录及总入口对应行，不保留完成台账、空目录或“留作参考”的残件；核对删除后的入口与引用。

静态检查能证明可解析的结构、状态与链接一致；真实需求完成、批准有效、知识迁移完整仍需执行者和用户判断。无法确认的事项明确保留，不能为了通过检查伪造状态。

## 7. 总任务最小清单

- [ ] 入口与实际任务一致，当前步骤、依赖、授权及恢复信息准确。
- [ ] 需求已逐项完成；范围变化明确处理；相关文档与引用已同步。
- [ ] 必要验证针对当前对象完成；未执行、不适用和限制如实记录。
- [ ] 人工操作材料已准备，用户按权限实际验收；审批前保留验证材料。
- [ ] 长期资料有正式归属，其他任务不再依赖即将删除的临时内容。
- [ ] 本任务临时文件已归位并按用途清理，不误删他人文件。
- [ ] 用户批准后整目录删除并移除入口，删除后静态检查无新断链。

检查方式、规则编号、差异展示与使用场景见[计划静态检查](plan-checks.md)。
