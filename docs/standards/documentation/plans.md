# 实施计划管理规范

> **状态**：强制执行。
>
> **适用范围**：需要拆分、跨会话恢复或持续跟踪的实施任务，以及现有实施计划的后续维护；小型即时任务按第 0 节豁免建计划。
>
> **核心路径要求**：所有 Plan 文档必须写在仓库的 `docs/plan/` 目录树内，禁止写在仓库其他位置。

## 0. 是否需要建立计划

1. 小型、范围明确、立即执行且能在本次工作中一次完成的任务不需要创建 Plan 文档，例如一次性的文档整理、链接修复或局部代码修正。直接完成必要修改和验证并报告结果，不为满足流程补建总任务、子计划或单独审批步骤。
2. 需要拆分实施、跨会话恢复或持续跟踪进度的任务，按后续章节建立或维护计划；用户明确要求计划文档时也应建立。
3. 小型任务执行中扩大为需要分阶段或跨会话继续的工作时，再为剩余工作建立计划，简要记录已完成事实，不补写完整过程。
4. 豁免只涉及计划文档及其生命周期，不免除文档影响评估、必要验证和真实结果报告。维护已有计划时仍同步实际受到影响的入口与状态，但不为这次小型维护另建一套计划。

## 1. Plan 文档位置与结构

`docs/plan/` 使用固定的两级 README 导航。根 README 选择任务，任务 README 负责恢复，详细小任务只在需要执行时读取：

```text
docs/plan/
├── README.md
└── <task-id>/
    ├── README.md
    ├── <unfinished-subtask>.md
    └── verify/
        ├── manual-final.md
        └── out/
```

1. `docs/plan/README.md` 是所有 Plan 的唯一总入口，只登记任务 ID、状态、一句话范围和任务目录 README 链接；不得复制任务台账或详细步骤。
2. 每个总任务固定使用 `docs/plan/<task-id>/README.md`。`docs/plan/` 根目录除 `README.md` 和任务目录外不得散放任务文档。
3. 未完成的小任务文档固定写在 `docs/plan/<task-id>/`，每个小任务单独一个 `.md` 文件；小任务完成后按第 3 节收口并立即删除。
4. 总任务 README 必须登记全部小任务。未完成项链接对应小任务文档；已完成项只保留结果摘要、验证结论和完成状态，不保留失效链接。
5. 总任务 README 是切换会话、执行者或环境后的唯一任务恢复锚点，至少包含：目标与边界、批次、小任务台账、每项复杂度及其依据、依赖、当前恢复检查点、最终综合验证、用户审批和总任务状态。
6. 小任务只承载当前尚未完成的工作，至少包含：所属总任务、状态、复杂度及其依据、依赖、范围与非目标、已完成事实、剩余步骤、定向自动验证和完成标准。创建时已经完成的内容如实勾选即可，不得要求重做，也不得补写无助于恢复的过程记录。
7. 查找任务时必须先读 `docs/plan/README.md`，再读目标任务的 `README.md`；只有选定小任务后才读取其详细文件。不得通过先枚举整个目录树来理解 Plan，也不得把文件树清单复制进 README。
8. `docs/plan/` 的导航入口、任务 README、未完成子计划和可复用验证说明纳入版本控制，用于跨环境恢复；`verify/out/` 下的构建物、截图、日志和测试产物由 `.gitignore` 排除。不得把已完成子计划的过程记录重新加入版本控制；发现旧计划被跟踪时，只清理不再需要的索引项，不改写既有提交历史。
9. 验证脚本、运行产物与最终手动验证操作手册统一放在 `<task-id>/verify/` 下，分类规则见第 5 节；禁止与计划文档平铺混放。

### 1.1 文档创建时间

新建总任务 README 和独立小任务文档时，生成者必须在一级任务名称标题下、状态行之前记录文档创建时间，标题与元数据之间保留空行：

```markdown
# <任务名称>

**文档创建时间：** YYYY-MM-DDTHH:mm:ss±HH:mm

**状态：** <当前状态>
```

创建时间取文档首次生成时的实际时间，使用带明确时区偏移的 ISO 8601 格式（例如 `2026-09-09T10:30:00+08:00`），不得保留占位符。后续编辑、状态变更、恢复执行或移动文档时保持原值，不将更新时间覆盖为创建时间。计划根导航 README 和验证资产不要求该字段。

维护缺少该字段的历史任务文档时一并补录：优先使用可确认的原始创建记录；只能取得首次 Git 收录时间时，在时间后明确注明“按首次 Git 收录时间补录，实际创建时间未记录”；无可靠记录时写“未知（历史文档未记录）”，不得用本次修改时间或文件系统复制、检出时间冒充。新建文档不得使用“未知”。

## 2. 拆分与分布执行

1. 新任务先在总任务中登记已知小任务，再开始实现；只在某个小任务即将执行或需要跨会话保留时创建其独立文档，不为已经完成的工作补建小任务文档。
2. 每个小任务只承担一个明确目标；范围可以交给不同执行者分布执行，但共享文件、前后置依赖和互斥关系必须在总任务中注明。
3. 每个小任务必须在总任务台账和独立文档中登记 `复杂度：1 至 5` 及一句依据。复杂度用于帮助用户为任务选择合适的执行 Agent 或模型，不是工期、优先级或代码行数估算。按状态或契约风险、跨模块依赖、兼容或迁移影响及验证难度综合判断：`1` 为边界明确的局部调整；`2` 为单模块的有限行为或数据映射；`3` 为需保持既有行为的多组件或多步骤流程；`4` 为涉及跨模块契约、异步状态、持久化或恢复边界的高风险工作；`5` 为核心执行语义、共享状态机、架构或迁移的广泛兼容风险。范围、依赖、技术方案或验证边界实质变化时，必须重新评估并同步台账与小任务文档。
4. 总任务中的小任务状态统一使用：`未开始 / 进行中 / 阻塞 / 已完成`；独立小任务文档只会处于前三种状态，达到完成标准后立即收口删除。
5. 总任务在计划区内的状态统一使用：`规划中 / 执行中 / 待综合验证 / 待用户审批`。完成不是需要长期保留的计划状态；用户批准后按第 6 节删除总任务入口和目录。
6. 同一批次可以分布执行无冲突的小任务；有依赖的小任务必须按依赖顺序执行。执行或分配任务前，按项目配置向用户报告复杂度和建议的能力特征，由用户确认具体执行 Agent 或模型；不得把复杂度写成固定的模型类型、名称或厂商映射。
7. 所有需要用户操作、主观判断或真实界面确认的事项集中到最后一个“综合验证与用户验收”小任务；实现类小任务不得把人工验证列为自己的步骤或完成条件。

## 3. 执行与进度同步

1. 实现前建立或更新总任务，并为当前要执行的未完成小任务建立或更新独立文档。
2. 小任务每完成一个执行步骤，立即勾选小任务文档中的步骤；在阶段性提交、切换会话、执行者或环境前，同步总任务的恢复检查点。
3. 阶段性提交统一遵守 项目协作规范。当前小任务不需要先完成；本规范只负责维护与提交状态一致的 Plan 恢复信息。
4. 恢复检查点只记录继续工作必需的信息：当前小任务、已完成事实、剩余步骤、依赖或阻塞、基准提交或工作区状态、下一条验证命令。不得把已完成小任务全文复制进总任务。
5. 实现步骤、定向自动验证和完成标准全部通过后，按以下顺序收口小任务：
   1. 将"执行记录"以及后续小任务真正需要的依赖事实写回总任务；执行记录只列变更对象、自动命令、退出码、关键断言行和产物路径，每项一行可校验，不得写叙述性段落，不得使用"全面验证""严格测试""理论上""应当""应该"等模糊词；
   2. 在总任务台账中将该小任务标记为 `已完成`，移除对小任务文档的链接，并把恢复检查点指向下一个未完成小任务；
   3. 将有长期价值的契约、操作方式和测试分别迁入权威文档、正式指南或正式测试；
   4. 删除该小任务文档。
6. 小任务的定向自动验证用于尽早发现局部问题，不替代最终综合验证。
7. 已完成小任务后来发现问题时，新建一个修正小任务并登记到总任务，不恢复已经删除的旧小任务文档，也不得篡改原完成摘要。
8. 台账发生实质变更（新增、删除或合并小任务，串行顺序调整，范围、契约或验证边界改变）时，必须在同一次变更内同步复核全部受影响的现存文档，不得只改台账一处：更新总任务的依赖与执行顺序、恢复检查点，改写或删除已失效的未完成小任务文档，并按第 4 节第 9 项同步最终综合验证小任务。变更后遗留指向已删除小任务的链接、依赖或验证项，视为计划未收口。

## 4. 最终综合验证与用户验收

1. 最后一个小任务固定为“综合验证与用户验收”。只有其他小任务均已完成并删除后，才创建或进入该小任务，并将总任务标为 `待综合验证`。
2. 该小任务顶部固定维护一个“反馈回填槽”，登记实施过程中产生的全部反馈、待补项、用户临时意见等。任何实施小任务或会话中发现的问题必须登记到这里，不得另开修正任务或悬空待办；该槽未清零前不得进入阶段二。
3. 该小任务统一汇总三部分内容：
   - **自动验证清单**：每行严格 6 列——编号、目标（一句话）、命令（一行可执行）、退出码、关键断言行、日期与产物路径；执行后逐行回填，结论列只填“通过 / 失败 / 待执行”，不写“通过”二字即视为尚未执行；不得登记任何不可执行的命令。
   - **手动验证清单**：只保留四类事项——真实视觉与交互、主观 UX 判断、跨设备/窗口/无障碍的真实使用、性能体验；其他事项一律改写为自动项。每一行只列编号、目标（一句话）、`verify/manual-final.md` 锚点链接、结论（通过 / 失败 / 待补 fixture），单条人工项用户应能在 1 分钟内给出结论。
   - **抽样信任记录**：登记用户对自动清单的抽样核对结论（用户随机挑选若干条命令确认退出码与断言行存在），不再逐条核对；项目配置允许时由 AI 主动提交抽样建议。
4. 实现小任务收口时，只需把应进入最终回归的验证目标和入口汇总到总任务；不得因为最终人工验收尚未执行而阻止实现小任务完成和删除。
5. 手动验证操作手册统一写在 `verify/manual-final.md`，改为“操作卡”形态：每张卡只含入口、操作步骤（≤1 分钟）、期望现象、结论字段（通过 / 失败 / 待补 fixture），不再写大段叙述；内容至少包含前置条件（环境、账号、测试数据）、与自动清单不重复的最小化操作步骤、证据留存要求（由人工留存的截图或文字记录及其存放位置）。
6. 全量测试、类型检查、构建、静态检查和跨模块回归统一在自动验证清单中执行并记录。允许的自动化范围、人工验收边界与执行人由项目配置明确；执行验证前读取该配置，不得把未执行的检查报告为通过。
7. 综合验证以“三阶段”推进：
   1. **阶段一：自动收口**。反馈回填槽清零；自动清单全量执行，每行有退出码与关键断言行；任一失败则新建修正小任务并回到执行流程。
   2. **阶段二：必要人工核对**。用户按 `verify/manual-final.md` 顺序逐条核对，每条 ≤1 分钟给出结论；任一失败立即回到阶段一登记修正。
   3. **阶段三：用户拍板**。阶段一与阶段二结论齐全后，用户明确批准才进入收口；未取得明确批准前总任务保持 `待用户审批`。
8. 任一验证失败，总任务退回 `执行中`，登记并创建对应修正小任务；修正完成并删除后，重新进入最后的综合验证小任务并从阶段一开始重跑。
9. 自动验证通过但必要的手动验证未完成、反馈回填槽未清零或抽样信任未登记，不算全量通过，总任务仍保持 `待综合验证`。
10. 自动验证、必要手动验证与抽样信任全部完成后，删除最后的综合验证小任务，将总任务标为 `待用户审批`。
11. 综合验证清单以最新台账为准，随任务变更同步重建。任一实现小任务被新增、删除、合并，或其范围与验证边界改变时，必须在该次变更内复核并更新自动验证清单、手动验证清单和 `verify/manual-final.md`：新任务引入的人工事项补入手动清单，已作废任务对应的人工事项和操作手册章节一并删除，仍然有效的条目重新确认通过标准。若该综合验证小任务在台账变更前已提前存在，按最新台账重建其清单，不在旧清单上追加；已记录的旧验证结论只有在验证对象未变时才可保留，否则作废重验。沿用未经复核的旧清单等同于未登记验证，不得据此判定全量通过。

## 5. 验证资产分类

Plan 内验证相关内容按「一次性脚本 / 运行产物 / 长期测试」三类分流：

1. **一次性验证脚本**（静态扫描、行为复现、UI 检查等 `.mjs` / `.cjs` 等）统一放 `docs/plan/<task-id>/verify/`，脚本头部注释说明用途与运行方式；禁止与计划文档平铺混放。
2. **运行产物**（测试结果 json、截图、日志、构建输出等）统一输出到 `docs/plan/<task-id>/verify/out/`；执行脚本时必须显式指定输出目录，禁止在 Plan 目录就地落产物。产物可随时重新生成，权威文档不得将其作为事实来源引用。
3. **有长期价值的测试**必须落入正式测试目录（路径和工具以项目配置为准），Plan 内只保留入口命令与文件路径引用；不得把临时脚本的断言原样复制成产品测试，产品测试应验证修复后的预期结果。
4. 版本控制边界统一遵守第 1 节第 8 项：计划入口、未完成子计划和可复用验证说明可跟踪，`verify/out/` 运行产物忽略。长期验证逻辑仍按本节第 3 项迁入正式测试，不以临时脚本代替。

## 6. 用户审批与总任务完成

本规范默认采用显式审批关口。采用项目必须在配置中明确审批人及是否保留该关口；若取消独立审批，则全部必要验证通过后直接执行本节的总任务收口，不再进入 `待用户审批`。未配置时采用下述默认流程。

1. 最终综合验证通过后，将总任务标为 `待用户审批`，向用户报告结果并暂停完成动作。
2. 验证通过不等于审批通过；只有用户明确表示批准，才执行总任务完成收口。
3. 用户要求修改时，总任务退回 `执行中`，登记新的修正小任务并返回执行流程。
4. 用户批准后，先确认所有小任务均已完成并删除，再把有长期价值的结果迁入对应权威文档、正式指南或正式测试，随后从 `docs/plan/README.md` 移除任务入口并删除整个 `docs/plan/<task-id>/` 目录；不得保留“已完成”总任务台账。
5. 模块说明、架构决策、操作规范、测试规范及用户要求保留的验收证据不得留在 Plan 中作为唯一副本。验收证据按以下规则迁出：
   - 任务级长期证据统一迁入 `docs/quality/verification/<task-id>/`，子目录与文件命名见 [quality 验证证据规范](../quality/verification/README.md)（项目配置可在 `verification/` 下自定义子目录形式）。
   - 必迁内容：自动清单原始命令输出（至少 1 份完整日志）、关键截图的描述（不存图，只存路径与说明）、人工清单结论文字、用户明确批准的原文。
   - 不迁内容：实施细节段落、未通过命令的失败记录、与本次任务无关的文件改动。
   - 迁出完成前不得删除 `verify/` 与 `verify/out/`；迁出后这两类目录随任务目录整体删除。
6. 删除小任务只依据其完成标准和定向自动验证，不需要等待总任务审批；删除总任务以“全部小任务完成、最终综合验证通过、用户明确批准、长期证据已迁出”为条件，不再要求用户另行发出删除指令。
7. 删除是整目录删除，不做选择性保留。总任务 README、任何剩余小任务文档、`verify/` 下的验证脚本与手动操作手册、`verify/out/` 运行产物及全部附属文件随目录一并移除，同时删除 `docs/plan/README.md` 中的任务行。计划完成意味着其内容已经内化进项目权威文档：需要长期保留的契约、模块说明、操作方式、测试和验收证据必须在删除前迁入 `docs/` 权威文档、正式指南、正式测试或 `docs/quality/`，Plan 不得是任何内容的唯一副本。
8. 不得以“可能还有用”“留作参考”“便于回溯”为由保留计划残件，也不得把已完成任务改写为归档条目、历史台账或空壳 README 继续留在 `docs/plan/`。收口后 `docs/plan/<task-id>/` 必须不存在，`docs/plan/` 下只应有根 `README.md` 与仍在进行的任务目录；历史过程记录由版本控制承担，不在计划区留档。
9. 删除前必须满足以下机器可校验条件；任一不满足则禁止整目录删除：
   - 全部实现小任务已删除（综合验证小任务除外）。
   - 综合验证小任务的反馈回填槽已清零。
   - 自动清单无“待执行”行。
   - 手动清单每行结论非空。
   - 抽样信任记录存在。
   - 用户明确批准。
   - `docs/quality/verification/<task-id>/` 存在且至少含 `auto-output` 与 `manual-conclusion` 两类文件。
10. 删除失败按以下诊断矩阵定位：

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| 任务目录还在 | 人工项未结论 | 回到阶段二逐条给出结论 |
| 任务目录还在 | 反馈回填槽未清零 | 回到综合验证小任务清空回填槽 |
| 任务目录还在 | 抽样信任未登记 | 在综合验证小任务补充抽样结论 |
| `verification/<task-id>/` 不存在 | 长期证据未迁出 | 按第 5 项规则迁出后再删除 |
| `docs/plan/README.md` 仍有任务行 | 总入口未同步 | 移除任务行后再删除 |
