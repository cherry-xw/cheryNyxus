# 实施计划管理规范

> 状态：强制执行。计划只维护当前目标、未完成工作、必要验证与恢复信息。项目参数由采用项目的配置维护。

## 0. 是否需要建立计划

小型、明确且本次能完成的工作无需建立计划；维护已有计划不另建一套计划。需要跨会话、拆分或持续跟踪时建立计划；用户明确要求时也建立。只需等待或简单恢复的任务允许单页计划；大任务必须拆成若干目标明确的小任务，不能以单页形式省略任务划分。任务扩大时仅为剩余工作建立计划，不补写开发历史。

## 1. 计划文档位置与结构

计划统一位于 `docs/plan/`。总入口为 `docs/plan/README.md`；每个任务入口为 `<task-id>/README.md`。恢复时先读总入口、再读目标任务，按需读取当前小任务，不先枚举整个计划树。

| 文档 | 独占维护的内容 |
| --- | --- |
| 计划总入口 | 任务链接、状态、一句话范围；每个实际任务目录恰好登记一次 |
| 总任务 README | 目标与边界、当前设计及决定入口、未决问题、当前授权、小任务台账、依赖、唯一当前恢复检查点、待处理事项、最终验收入口 |
| 当前小任务文档 | 本项具体实施步骤、当前事实、剩余工作及可观察的完成条件 |
| 验证文件 | 验证对象、方法、当前结果与必要人工操作 |
| 权威模块文档 | 当前长期契约、行为和正式操作入口 |

1. 总入口使用连续的任务表格，不能用空行拆出无表头的任务行。任务目录与登记条目必须一一对应。
2. 单页计划在总任务标记 `计划形式：单页`；直接在 README 维护步骤、恢复与完成条件，无需空小任务文件。
3. 拆分计划由总任务台账维护小任务 ID、状态、复杂度及依据、依赖。即将执行或需要独立交接的小任务才创建文件并链接；远期未开始任务允许无文件。复杂度为 1 至 5，按风险、依赖和验证难度评估，不绑定模型名称、价格或厂商。
4. 小任务若重复声明状态，必须与台账一致；复杂度与依赖优先引用台账，避免多份维护。普通实现小任务完成后迁出有用事实、更新台账、移除文件链接并删除详细文件。
5. 设计比较与有效候选资料可以保留，只需有明确用途和入口；不因为文件没有任务状态就把它当作待删除任务。用户要求保留的有效方案按要求维护。
6. 计划入口、当前小任务、可交接脚本及验证说明纳入版本控制。运行产物忽略；忽略文件不等于允许长期堆积。
7. 总任务正文只保留一个“当前恢复检查点”，说明实际完成、剩余工作、下一执行人及具体动作、当前授权、阻塞条件与必要工作区基准。验收期间说明当前在准备环境、等待用户操作、处理反馈还是修复复验，并链接详细验收记录；这些是当前工作说明，不增加总任务状态。新事实替换旧状态，不追加第二个“最新恢复点”。
8. Markdown 链接、任务台账、明确声明的状态与目录由[静态检查](plan-checks.md)比较；检查通过不能证明业务已完成。

### 1.1 文档创建时间

新建任务 README 和小任务文档在一级标题下、状态行之前写 `**文档创建时间：** YYYY-MM-DDTHH:mm:ss±HH:mm`，取实际创建时间，后续保持不变。总导航与验证资料无需此字段。

维护缺字段的历史任务时，优先补录可靠原始记录；仅有首次 Git 收录时间时注明来源；无法确认写“未知（历史文档未记录）”。不能以当前修改时间冒充原始创建时间。

## 2. 拆分与分布执行

大任务在实施前按功能或可单独说明的结果拆成小任务，每项有稳定编号或清晰名称、范围、依赖和完成条件。不能把多个独立功能统称为“实施”“收尾”或“恢复点”来代替拆分，也不按文件数量凑小任务。同一功能所需的前后端、协议、测试和必要说明可以属于同一小任务；共用前置工作明确归属并安排依赖顺序，不因共享文件而合并不同功能。

小任务是提交的划分单位，不是要求每做完一项就运行完整测试。按项目协作规范分别提交各小任务，保留已有的连续实施、最小校验和最终集中验证要求；拆分实施不等于允许把当前范围的设计留到以后再决定。

总任务状态统一为 `规划中 / 执行中 / 待综合验证 / 待用户审批`；小任务状态为 `未开始 / 进行中 / 阻塞 / 已完成`。设计尚未完成、尚未取得所需实施授权时保持规划中。实施中暂停不另造总任务阶段，在当前恢复检查点记录原因、暂停范围、恢复条件与下一执行人；具体暂停条件和范围遵守项目协作政策及用户要求。遇到影响正确性的未决事项或授权不足，不得以持续推进为由猜测并实施。

先定目标、成功条件、必须保持的行为和未决事项，再决定实现；例子不自动成为固定参数。涉及现有实现时从权威模块定位真实代码与消费者，不把旧台账视为代码已完成的证据。即将执行的小任务说明稳定入口、关键符号、状态与数据路径、共享文件顺序、失败与恢复路径。尚未纳入当前实施范围的远期任务可只写目标、依赖和验收方向；当前实施范围必须满足项目的设计完整度要求，不能以小任务尚未开始为由推迟影响本次方案的决定。

无冲突工作可以分配给不同执行者；共享文件和前置依赖要明确。同一任务内已经确认的 Agent 和授权在原范围内持续有效；仅在任务范围、风险或所需能力实质变化时重新评估并按项目政策确认，不逐步骤重复索要确认。分配权限由项目政策及用户授权决定。

跨任务依赖写出所需结果及其稳定入口。其他任务完成前引用其当前入口，完成后改指权威文档、正式代码或验证方法；不得只留下已删除计划的步骤编号。删除计划前核对其他活动任务的引用及文字依赖。

### 2.1 设计记录与实施授权

计划负责保存当前设计及确认状态，不把提案写成已批准要求或已实现事实。简单任务可直接在总任务 README 维护；复杂设计按职责拆专题，总任务提供唯一入口。[需求设计规范](requirements-design.md)维护方法选择、提问、调研、检查点和交接要求；具体开工授权、暂停范围及审批由项目协作政策规定。本规范只维护记录职责：

| 内容 | 记录要求 |
| --- | --- |
| 当前事实 | 调查依据、现有实现和关键依赖；与目标要求分别说明 |
| 方法与关键未知 | 主要未知、所选方法及理由、需要的证据、结果与返回条件；无需记录无信息增益的每次操作 |
| 调研与方案比较 | 关键来源、查阅日期、适用版本和环境、项目适配、候选的优势与缺陷；当前决定保留理由及改选条件，正文只维护一份 |
| 已确认决定 | 当前结论、适用范围、必要理由及用户确认依据；后续执行可恢复，无需复制聊天全文 |
| 候选与未决问题 | 候选明确未批准；问题说明影响、需要谁决定及关联设计；不能以“有默认方案”冒充已解决 |
| 需求与完成条件 | 每项需求对应设计位置、实现入口及验证方式；复用已有表格，不另造重复清单 |
| 当前授权 | 允许调查、文档设计还是实施；实施方案、范围、限制及确认依据；与最终验收批准分开 |
| 重新设计与恢复 | 返回的设计层、受影响决定和下游依赖、剩余问题及恢复条件；替换失效内容，不追加第二套执行方案 |
| 检查点与交接 | 检查对象、依据、结论、未解决问题和下一步；交接入口、顺序、验收和停止条件；标明文档自查或经授权的独立检查，不新增任务状态 |
| 实验与模型分工 | 具体权限、范围、环境、费用与证据清理责任；执行者能力需要及已确认选择，方法建议不能冒充调用或实验授权 |

授权引用应能让接手者识别用户批准的具体内容，不能只写无范围的“用户同意”。若用户已明确批准当前完整方案并要求执行，沿用已有授权，不因填写记录再请求一次确认。

文档的持续编写、状态区分与终版整理见[内容规范](content.md#71-设计记录与正式文档)。恢复已有计划时按项目政策检查剩余工作的设计和授权，复用有效结论；缺少新格式不能证明原决定无效，也不能用旧任务状态代替当前开工条件核对。

## 3. 执行与进度同步

实现、文档、引用和临时文件管理构成同一项交付。文档同步未完成时不得把该项标为完成。

| 变化 | 在继续依赖该变化的工作前同步 |
| --- | --- |
| 目标、方案、范围调整 | 已确认决定、当前授权、未决问题、总任务目标、受影响小任务和完成条件；需要新决定时先遵守项目暂停与确认规则 |
| 文件、符号、配置或命令移动、重命名、删除 | 调用方、模块说明、活动计划、操作与验证入口；同时搜索正文和命令中的旧引用 |
| 有意义的实施步骤完成 | 当前步骤、实际剩余项；不能只追加“已处理” |
| 切换任务、出现阻塞或结束会话 | 唯一恢复检查点及下一执行人、下一步 |
| 验证对象或环境变化 | 受影响结论标为待重验；人工卡的地址和准备条件同步 |
| 提交或交接 | 对照当前工作区核对记录、引用与本任务临时文件 |

不要求每改一行代码就更新计划，但不得等到最后凭回忆补写。内容同步不等于逐步完整测试；实施时仅做必要最小校验，整体实现结束并逐项确认需求已完成后，才进行集中验证。项目可以进一步规定最小校验与最终测试范围。

普通小任务“已完成”表示实现、文档同步及约定的最小校验完成，不表示总任务综合验证通过。完成时把当前依赖事实及验证入口写回总任务，迁出长期内容，更新台账并删除详细文件。已有完成项出现缺陷时新增修正项，原完成摘要不伪造，当前限制明确登记。

### 3.1 待处理事项

待处理事项从任务建立起放在总任务 README，按发现时的性质分配：当前缺漏更新当前小任务；已完成部分的缺陷建立修正项；新增需求先确认范围；建议明确是否纳入；真实体验确认进入人工验收。不要把所有问题延迟到最后验收，也不要重复维护全文。

每个未解决事项应能定位发现事实及依据、影响的需求或验收项、当前处理结论、处理人、下一步和解决判据。复用已有任务或验收编号与链接，不另建重复清单。开发、部署、自动验证及人工使用中的新发现均须更新；用户只在聊天中反馈时，由执行者整理到对应记录。已知遗漏与新取得的事实分别说明，具体暂停和授权由项目协作政策规定。

清零表示本次必须解决的事项已经解决，其他事项按第 4.2 节明确不纳入或已获批准转交；不能删除记录冒充解决。变更台账时在同一次修改中同步依赖、当前步骤和受影响验收项，不重建无关内容。

## 4. 最终综合验证与用户验收

拆分计划的最后小任务为“综合验证与用户验收”，整体实现与需求完成核对后进入；单页计划可直接在 README 承载。验收目标可以提前记录，验收文件可按需要提前准备，不等于提前开始完整测试。进入时总任务为 `待综合验证`。

1. **先核对需求完成**：逐项目标已有实现，必要文档和引用同步，本次必修反馈解决，临时文件已归位。未实现内容不能靠测试通过替代。
2. **集中自动验证**：每项记录编号、目标、可执行命令、结论、证据。结论统一为 `待执行 / 通过 / 失败 / 待重验 / 阻塞 / 不适用`。证据包含日期、验证对象的版本或工作区标识、环境、退出码、关键断言及产物位置；无产物明确写无。命令退出 0 不自动证明行为断言通过。
3. **必要人工验收**：视觉、交互、主观体验、真实设备、必须由用户授权或触发的动作可以保留人工项。操作卡放 `verify/manual-final.md`，单页计划可直接在 README 承载；内容见第 4.1 节。尽量简短，一分钟是优化目标而非硬性上限。缺少环境或数据时标“阻塞”并说明谁补齐，不把未准备好的操作卡交给用户猜测。
4. **失败与重验**：失败时总任务退回执行中，登记修正任务。重验修改影响的行为和依赖；未变化的对象、环境及输入可以保留有效结论。公共契约或构建基础变化、影响无法判断时扩大检查。不能复用不适用的旧结果，也不机械重跑无关检查。
5. **审批准备**：按第 4.2 节处理范围及延期事项后，当前范围全部必要项通过或有经用户明确同意且有依据的不适用项，文档、引用及清理核对完成，才进入 `待用户审批`。审批期间保留验收文件供审阅，不提前删除。未验证、用户接受限制和验收通过分别说明，不以调整范围伪造通过结果。
6. **抽样与权限**：是否抽样由用户或项目风险政策决定，不作为所有任务的固定门槛。抽样应核对对象、场景、断言与证据，而非只看日志存在。自动检查不能证明真实用户验收或授权；执行权限遵守项目配置。

### 4.1 人工验收交接与结果

验收目标依据当前已知需求提前安排，操作卡随实现、环境及反馈持续完善；不要求开工前预见全部问题。每项使用稳定编号或清晰名称，至少说明：

| 内容 | 记录要求 |
| --- | --- |
| 对象与目标 | 对应需求、测试版本或工作区、环境；哪些结果由用户确认，哪些由执行者核对 |
| 实际准备 | 实际入口、所需数据、账号交付方式、已完成准备及缺少条件；不记录密码或凭据 |
| 操作与判断 | 用户最小步骤、预期现象、预计时间；需要双方交替执行时写明顺序 |
| 反馈与跟进 | 用户最少需反馈的编号、结果或异常现象；收到反馈后执行者的检查或处理动作 |
| 当前结果 | 沿用第 4 节结论值，记录执行日期、适用对象和反馈依据；缺条件不能当作失败或通过 |
| 下一步 | 下一执行人、具体动作、所需条件；已解决项关联结果，异常关联修正任务或待决定事项 |

共享的环境与反馈方式只写一次。总任务保留摘要和唯一入口，不复制整张卡。操作卡存在不代表已经具备验收条件；交接时应明确哪些可以立即操作，哪些仍由执行者准备。执行者能自行查到的信息不要求用户重新收集。

允许逐项、分批反馈，不要求一次完成全部清单或填写正式报告。执行者将明确反馈写回相应项目，说明依据；未反馈项目保留原结论。修复后标明受影响的待重验项、原因及最小复验步骤，不重置仍然有效的通过项。每次交接或结束会话前同步唯一恢复检查点，不能仅回复“请继续测试”。具体职责和权限遵守项目协作政策。

### 4.2 延期、转交与范围决定

“未验证”是事实，“延期”是工作安排，均不等于通过或不适用。每个未完成项必须明确采用以下哪种安排：

| 安排 | 必须明确的内容 | 对当前任务结束的影响 |
| --- | --- | --- |
| 留在当前任务继续处理 | 未完成原因、下一执行人、具体动作、所需条件及恢复时机或触发事件 | 仍是必要项时阻止进入待用户审批 |
| 经用户同意转交 | 用户确认依据、影响和剩余限制、接手人、接手任务或受管理清单入口、触发条件及下一步；同步接手方记录 | 确认已移出当前完成范围后才不阻止当前任务；接手工作保持未完成 |
| 经用户决定取消验证或接受未验证限制 | 具体项目、未验证事实、影响、接受范围与确认依据；同步需求和完成条件 | 仅对明确调整后的范围判断结束，不改写为验证通过；只有确实不适用才标不适用 |

仅写“后续统一审核”、给出存放路径或长期无人处理，均不构成有效转交。不能默认用户同意延期、转交或接受限制；等待时间长也不自动结束任务。实际实现缺口不得改名为延期测试；涉及需求调整时先遵守项目设计与授权规则。

当前必要验收结论与经批准移出范围的事项分别说明，排除事项保留其真实结果和确认依据，不混入通过项。跨会话恢复或到达约定触发条件时，执行者核对安排是否仍有效；最终清理前将仍需保留的限制和接手入口迁到正式位置，不能随计划删除而丢失。

## 5. 验证资产与临时文件

| 类型 | 位置与管理 | 结束处理 |
| --- | --- | --- |
| 一次性草稿、调试输出、命令中间文件 | 系统临时目录下按任务建立专用目录，如 `/tmp/<task-id>/`；禁止散放仓库根或源码目录 | 使用完清理，最迟本任务结束时清理 |
| 必须跨会话交接的验证脚本 | `<task-id>/verify/`，注明用途、运行前提与命令 | 无长期用途随计划删除；有价值的迁入正式位置 |
| 可重建运行产物 | `<task-id>/verify/out/` 或项目明确管理的输出位置；Git 忽略 | 无待核对用途后清理 |
| 正式测试与可复用方法 | 项目正式测试、指南或验证说明目录 | 正常维护，不存于临时计划作为唯一副本 |

需要恢复的脚本、方法与输入不能只放可能被清空的 `/tmp` 或个人缓存。原始输出可在受管理的仓库外位置保存；明确用途、负责人和清理时机，不把杂乱简单转移到外部目录。开发历史不要求迁为长期文档。

任务创建临时文件时就确定位置和清理范围；检查工作区中新建文件是否属于本任务，必要时在恢复点记录专用临时目录。只删除本任务明确拥有且不再需要的文件；未跟踪不等于垃圾，不能删除用户、其他任务或运行数据。静态扫描只报告确定的违规位置或可疑文件，不自动删除。

## 6. 用户审批与总任务完成

项目配置决定是否采用独立用户审批；默认保留。当前任务用户明确批准才执行最终收尾，已获得的完成批准包含按本规范清理计划，无需再次索要单独删除指令。批准实现方案不等于批准最终验收。

执行者在满足审批条件后主动提供当前范围的验收摘要、已确认限制和转交入口，并说明是否可以结束。用户已明确确认验收结果且批准结束时直接沿用，不因记录或流程名称再要求一次相同批准；单项通过、暂缓验证或批准转交不自动等于批准整个任务结束。

按以下顺序收尾：

1. 确认必要验证已完成、当前限制明确、用户批准适用于当前范围；不能以非空结论或无“待执行”代替全部必要项通过。
2. 确认长期契约、方法、正式测试及必要当前结论已迁入权威位置。
3. 检查其他活动计划、文档、命令中的依赖，更新指向本任务临时文件或旧步骤的引用。
4. 检查本任务所有新增文件和专用临时目录，包括计划目录外；迁出有用内容，清理已无用途的脚本、输出、缓存与备份。
5. 删除整个任务目录及总入口对应行，不保留完成台账、空目录或“留作参考”的残件；核对删除后的入口与引用。

静态检查能证明可解析的结构、状态与链接一致；真实需求完成、批准有效、知识迁移完整仍需执行者和用户判断。无法确认的事项明确保留，不能为了通过检查伪造状态。

## 7. 总任务最小清单

- [ ] 入口与实际任务一致，当前步骤、依赖、授权及恢复信息准确。
- [ ] 大任务已按功能或独立结果拆成小任务，范围和依赖清楚；提交按小任务分别组织，不以总任务或收尾名义混合多个功能。
- [ ] 需求已逐项完成；范围变化明确处理；相关文档与引用已同步。
- [ ] 必要验证针对当前对象完成；未执行、不适用和限制如实记录。
- [ ] 人工操作材料可执行，反馈已逐项处理；未完成项有下一执行人、具体动作和所需条件，审批前保留验证材料。
- [ ] 延期、转交或接受未验证限制有明确范围决定及去向，不冒充通过或不适用。
- [ ] 长期资料有正式归属，其他任务不再依赖即将删除的临时内容。
- [ ] 本任务临时文件已归位并按用途清理，不误删他人文件。
- [ ] 用户批准后整目录删除并移除入口，删除后静态检查无新断链。

检查方式、规则编号、差异展示与使用场景见[计划静态检查](plan-checks.md)。
