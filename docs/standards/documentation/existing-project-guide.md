# 存量项目文档梳理指南

本文用于两类存量项目：尚未建立持久文档的项目，以及已有大量文档但入口、归属或内容不可信的项目。目标是先建立可以工作的最小导航和事实基线，再按真实任务逐步治理；不要求在开始开发前一次性补齐全部文档。

本文是梳理操作指南。新建或调整目录时遵守[目录规范](./structure.md)，编写和评审内容时遵守[内容规范](./content.md)。梳理规模需要拆分、跨会话恢复或持续跟踪时，按[计划规范](./plans.md)建立实施计划。

## 1. 判断起点

| 项目状态 | 进入方式 |
| --- | --- |
| 没有 `docs/`、模块说明或可信入口 | 从“无文档项目”开始，先调查仓库并建立最小入口 |
| 有零散 README、Wiki、设计稿或历史计划，但无法可靠定位 | 从“文档混乱项目”开始，先建立清单和事实归属 |
| 已有可靠领域导航，仅局部模块缺失或过时 | 直接按内容规范进行触碰式治理，无需执行完整梳理 |

如果无法判断，先抽取两个高频任务测试现有路径：读者能否找到负责模块、稳定代码符号和验证入口。任一任务必须依赖全仓盲搜或相互冲突的说明时，按“文档混乱项目”处理。

## 2. 受控仓库调查

没有可靠文档路由时，允许进行一次受控探测。调查范围以建立导航所需的稳定信息为限，不在此阶段解释所有实现细节。

依次确认：

1. 根目录入口：现有 `README`、Agent 指令、贡献指南、包或工作区清单。
2. 运行边界：主要应用、服务、库、命令行程序及其装配入口。
3. 稳定源码根：业务代码、共享代码、生成代码和第三方代码的边界。
4. 验证入口：测试目录、构建配置、CI 工作流、静态检查和人工验收要求。
5. 公共契约：跨模块数据模型、协议、事件、状态机和配置格式。
6. 现有知识：仓库文档、代码注释、Wiki 导出、Issue、历史计划和维护者说明。

调查结论必须附证据位置，例如仓库路径、配置键、导出符号、测试文件或命令。目录名称只能作为线索，不能单独证明模块职责。

遇到冲突时分别记录预期契约和当前实现。公共契约以经确认的权威说明为预期来源，代码与自动化测试证明当前行为；提交记录、计划和注释只能提供历史线索。无法确认的内容标记为待核实，不写成现行事实。

## 3. 无文档项目

先创建能支持下一次任务的最小集合：

1. 根 `AGENTS.md`：通用执行基线、专项规则直达链接和已确认的领域路由。
2. `docs/README.md`：完整领域索引，以及范围未知时的人工导航入口。
3. 通用规则包：本目录中的规范、模板和指南。
4. 项目配置：源码与测试根、验证入口、审批政策、人工验收边界、计划和产物策略。
5. 必要领域 README：只为调查证明确实存在的稳定领域创建。
6. 一个高频模块入口：包含职责、任务定位、代码符号、影响面和验证方式。

先用一个真实任务验证这套路径。读者应能从根入口进入正确领域，找到实现符号和验证入口。验证通过后，再把其他模块按实际修改逐步纳入；不要为了看起来完整而创建空目录、空专题或推测性契约。

## 4. 文档混乱项目

先建立临时梳理清单，按主题记录现有文档、可能 owner、可信度、冲突和处理决定。该清单属于实施过程；需要跨会话时放入 Plan，完成后不保留为第二份文档索引。

对每个主题执行以下判断：

| 现状 | 处理方式 |
| --- | --- |
| 内容正确且 owner 清晰 | 保留正文，接入最近 README 和任务路由 |
| 多份内容表达同一契约 | 确认一个 owner，合并现行事实，其余位置改为链接或删除 |
| 内容部分过时 | 根据代码、测试和维护者确认现行事实后重写，清除历史流水账 |
| 只有过程或交接信息 | 长期知识迁入正式文档；无审计价值的过程按计划政策清理 |
| 只有单一跳转 | 合并进最近 README；仅无法立即迁移历史引用时保留有淘汰条件的兼容页 |
| 无法确认真假 | 标记待核实，不纳入权威文档；记录验证责任和所需证据 |

迁移顺序优先服务高频任务和高风险契约：先统一入口与项目配置，再处理公共契约、核心模块和验证入口，最后治理低频专题和历史资料。每批迁移都应保持旧入口可理解、链接有效，并避免同时维护新旧两套正文。

## 5. 建立事实归属

为每类长期事实指定唯一维护位置：

- 跨模块协议、公共模型和状态机归共享契约领域。
- 模块内部行为、依赖和扩展方式归实现模块。
- 可复用强制行为归最小适用范围的 standards。
- 操作步骤归 guides，验证边界和长期证据归 quality。
- 未完成工作和恢复信息归 plan，不能成为长期事实的唯一来源。

项目可以使用不同目录名称，但这些角色必须可从统一入口定位。导航可以在多个入口重复链接；契约正文和规则不得形成多份可独立演进的副本。

## 6. 分批治理与变更控制

梳理不应长期阻塞产品工作。建立最小入口后采用“触碰即治理”：任务真正影响某模块时，补齐该模块当前工作所需的任务路由、稳定符号、影响面和验证入口，同时清理碰到的重复或失效内容。

一次迁移如果移动或删除文档，应同步根入口、文档总索引、最近 README 和所有已知入链。保留兼容页时注明原因、剩余引用和删除条件。发现范围扩大到多批或需要跨会话时，将剩余工作登记为计划，不在参考文档中保存临时台账。

## 7. 完成标准

存量项目完成初始梳理至少满足：

- 根入口能区分正常路由和“路由缺失或失效”的初始化路径。
- 文档总入口、项目配置和实际存在的领域 README 可达。
- 至少一个真实高频任务能定位到权威说明、代码符号和验证入口。
- 已识别的公共契约有唯一 owner；未确认内容没有被写成事实。
- 旧文档已有保留、合并、迁移、归档、删除或待核实决定。
- 链接、路径、孤儿文档和版本控制边界已经检查。
- 剩余治理有明确优先级，并随实际任务渐进完成。

初始梳理完成不表示项目文档已经覆盖全部代码。它表示后续任务已有可信入口、事实归属和维护方式，不再依赖无边界的仓库搜索。
