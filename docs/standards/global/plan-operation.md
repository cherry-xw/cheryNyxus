# Plan 操作方案 v1.4

> **状态**：强制执行。
>
> **适用范围**：所有需要实施的新任务，以及现有实施计划的后续维护。
>
> **核心路径要求**：所有 Plan 文档必须写在仓库的 `docs/plan/` 目录树内，禁止写在仓库其他位置。

## 1. Plan 文档位置与结构

`docs/plan/` 使用固定的两级 README 导航。根 README 选择任务，任务 README 负责恢复，详细小任务只在需要执行时读取：

```text
docs/plan/
├── README.md
└── <task-id>/
    ├── README.md
    ├── <unfinished-subtask>.md
    └── verify/
        ├── manual-final.md
        └── out/
```

1. `docs/plan/README.md` 是所有 Plan 的唯一总入口，只登记任务 ID、状态、一句话范围和任务目录 README 链接；不得复制任务台账或详细步骤。
2. 每个总任务固定使用 `docs/plan/<task-id>/README.md`。`docs/plan/` 根目录除 `README.md` 和任务目录外不得散放任务文档。
3. 未完成的小任务文档固定写在 `docs/plan/<task-id>/`，每个小任务单独一个 `.md` 文件；小任务完成后按第 3 节收口并立即删除。
4. 总任务 README 必须登记全部小任务。未完成项链接对应小任务文档；已完成项只保留结果摘要、验证结论和完成状态，不保留失效链接。
5. 总任务 README 是切换会话、执行者或环境后的唯一任务恢复锚点，至少包含：目标与边界、批次、小任务台账、依赖、当前恢复检查点、最终综合验证、用户审批和总任务状态。
6. 小任务只承载当前尚未完成的工作，至少包含：所属总任务、状态、依赖、范围与非目标、已完成事实、剩余步骤、定向自动验证和完成标准。创建时已经完成的内容如实勾选即可，不得要求重做，也不得补写无助于恢复的过程记录。
7. 查找任务时必须先读 `docs/plan/README.md`，再读目标任务的 `README.md`；只有选定小任务后才读取其详细文件。不得通过先枚举整个目录树来理解 Plan，也不得把文件树清单复制进 README。
8. `docs/plan/` 的导航入口、任务 README、未完成子计划和可复用验证说明纳入版本控制，用于跨环境恢复；`verify/out/` 下的构建物、截图、日志和测试产物由 `.gitignore` 排除。不得把已完成子计划的过程记录重新加入版本控制；发现旧计划被跟踪时，只清理不再需要的索引项，不改写既有提交历史。
9. 验证脚本、运行产物与最终手动验证操作手册统一放在 `<task-id>/verify/` 下，分类规则见第 5 节；禁止与计划文档平铺混放。

## 2. 拆分与分布执行

1. 新任务先在总任务中登记已知小任务，再开始实现；只在某个小任务即将执行或需要跨会话保留时创建其独立文档，不为已经完成的工作补建小任务文档。
2. 每个小任务只承担一个明确目标；范围可以交给不同执行者分布执行，但共享文件、前后置依赖和互斥关系必须在总任务中注明。
3. 总任务中的小任务状态统一使用：`未开始 / 进行中 / 阻塞 / 已完成`；独立小任务文档只会处于前三种状态，达到完成标准后立即收口删除。
4. 总任务状态统一使用：`规划中 / 执行中 / 待综合验证 / 待用户审批 / 已完成`。
5. 同一批次可以分布执行无冲突的小任务；有依赖的小任务必须按依赖顺序执行。
6. 所有需要用户操作、主观判断或真实界面确认的事项集中到最后一个“综合验证与用户验收”小任务；实现类小任务不得把人工验证列为自己的步骤或完成条件。

## 3. 执行与进度同步

1. 实现前建立或更新总任务，并为当前要执行的未完成小任务建立或更新独立文档。
2. 小任务每完成一个执行步骤，立即勾选小任务文档中的步骤；在阶段性提交、切换会话、执行者或环境前，同步总任务的恢复检查点。
3. 阶段性提交统一遵守 [AI 协作与工作流规范](./ai-collaboration.md#1-可恢复的阶段性提交)。当前小任务不需要先完成；本规范只负责维护与提交状态一致的 Plan 恢复信息。
4. 恢复检查点只记录继续工作必需的信息：当前小任务、已完成事实、剩余步骤、依赖或阻塞、基准提交或工作区状态、下一条验证命令。不得把已完成小任务全文复制进总任务。
5. 实现步骤、定向自动验证和完成标准全部通过后，按以下顺序收口小任务：
   1. 将结果摘要、验证结论以及后续小任务真正需要的依赖事实写回总任务；
   2. 在总任务台账中将该小任务标记为 `已完成`，移除对小任务文档的链接，并把恢复检查点指向下一个未完成小任务；
   3. 将有长期价值的契约、操作方式和测试分别迁入权威文档、正式指南或正式测试；
   4. 删除该小任务文档。
6. 小任务的定向自动验证用于尽早发现局部问题，不替代最终综合验证。
7. 已完成小任务后来发现问题时，新建一个修正小任务并登记到总任务，不恢复已经删除的旧小任务文档，也不得篡改原完成摘要。

## 4. 最终综合验证与用户验收

1. 最后一个小任务固定为“综合验证与用户验收”。只有其他小任务均已完成并删除后，才创建或进入该小任务，并将总任务标为 `待综合验证`。
2. 该小任务统一汇总两份清单：
   - **自动验证清单**：每项含验证目标、命令、范围与通过标准；执行后记录命令、结果与日期。
   - **手动验证清单**：只包含确实无法由自动验证替代的事项；每项含验证目标、操作手册链接与通过标准，执行后记录结论、执行人与日期。没有人工事项时明确写“无”，不得制造人工步骤。
3. 实现小任务收口时，只需把应进入最终回归的验证目标和入口汇总到总任务；不得因为最终人工验收尚未执行而阻止实现小任务完成和删除。
4. 手动验证操作手册统一写在 `verify/manual-final.md`；内容至少包含前置条件（环境、账号、测试数据）、操作步骤、预期结果、证据留存要求（由人工留存的截图或文字记录及其存放位置）。
5. 全量测试、类型检查、构建、静态检查、跨模块代码级回归统一在自动验证清单中执行并记录。自动验证不得启动或操控浏览器、Electron 等图形界面，不得执行页面截图、录屏、像素比对、浏览器 UI 自动化或以程序化 DOM/CSS 检查代替 UI 验收；浏览器构建本身不属于启动界面。浏览器与 Electron 实机操作、视觉与交互验收统一由用户按手动验证清单执行并记录，除非用户对具体任务另有明确授权。
6. 任一验证失败，总任务退回 `执行中`，登记并创建对应修正小任务；修正完成并删除后，重新进入最后的综合验证小任务。
7. 自动验证通过但必要的手动验证未完成，不算全量通过，总任务仍保持 `待综合验证`。
8. 自动验证与必要的手动验证全部通过后，删除最后的综合验证小任务，将总任务标为 `待用户审批`。

## 5. 验证资产分类

Plan 内验证相关内容按「一次性脚本 / 运行产物 / 长期测试」三类分流：

1. **一次性验证脚本**（静态扫描、行为复现、UI 检查等 `.mjs` / `.cjs` 等）统一放 `docs/plan/<task-id>/verify/`，脚本头部注释说明用途与运行方式；禁止与计划文档平铺混放。
2. **运行产物**（测试结果 json、截图、日志、构建输出等）统一输出到 `docs/plan/<task-id>/verify/out/`；执行脚本时必须显式指定输出目录，禁止在 Plan 目录就地落产物。产物可随时重新生成，权威文档不得将其作为事实来源引用。
3. **有长期价值的测试**必须落入正式测试目录（如 `test/`，使用现有 Vitest），Plan 内只保留入口命令与文件路径引用；不得把临时脚本的断言原样复制成产品测试，产品测试应验证修复后的预期结果。
4. Plan 目录整体被 `.gitignore` 排除；需要跨会话保留的验证逻辑必须落 `test/` 或权威文档，不得只存在于 `verify/` 临时脚本中。

## 6. 用户审批与总任务完成

1. 最终综合验证通过后，将总任务标为 `待用户审批`，向用户报告结果并暂停完成动作。
2. 验证通过不等于审批通过；只有用户明确表示批准，才将总任务标为 `已完成`。
3. 用户要求修改时，总任务退回 `执行中`，登记新的修正小任务并返回执行流程。
4. `已完成` 的总任务只保留轻量结果台账，不保留已删除小任务的失效链接、详细过程或临时交接内容；默认保留本地，只有用户明确要求时才删除。
5. 模块说明、架构决策、操作规范、测试规范及用户要求保留的验收证据不得留在 Plan 中作为唯一副本。需保留的验收证据迁往 `docs/quality/`（如 `docs/quality/verification/`），迁出后同步清理 Plan 内原引用。
6. 删除小任务只依据其完成标准和定向自动验证，不需要等待总任务审批；删除总任务仍需用户明确要求。

- [ ] 每个已完成小任务均已回写结果摘要和验证结论、移除链接并删除独立文档。
