## 1. 可恢复的阶段性提交

是否建立计划以 [Plan 适用范围](./plan-operation.md#0-是否需要建立计划) 为准。小型即时任务不为提交或验收额外创建计划；下面涉及总计划、子任务和 Plan ID 的要求仅适用于已建立计划的工作，其余任务在结果报告或提交说明中记录必要验证与未完成事项即可。

**完整验收不是提交前提。提交的首要标准是形成范围清晰、可继续开发的恢复检查点；一个小任务可以跨多个提交，人工验收统一在最终综合验证阶段完成。**

1. **按恢复点提交**：完成一段逻辑相关且状态明确的工作后即可提交，不要求当前小任务或总任务已经完成；不得为了凑提交拆出没有独立恢复价值的碎片。
2. **保证可以继续**：提交后的代码、总计划恢复检查点和当前小任务必须足以让新会话、执行者或环境判断已完成内容、剩余步骤、依赖、已执行验证和下一步命令。
3. **跨环境携带上下文**：`docs/plan/` 的根入口、任务 README、未完成子计划和可复用验证说明随阶段检查点提交；`verify/out/` 产物不提交。提交说明仍应包含总任务 ID、当前小任务、剩余工作和验证状态，确保切换环境后可从对应 Plan 恢复。
4. **最小自动验证**：提交前运行与本次改动最接近且可执行的自动检查。提交不表示最终验收通过；尚未执行、暂时失败或只能人工确认的项目必须在恢复检查点中如实记录。
5. **人工验收不阻塞提交**：需要用户操作、主观判断或真实界面确认的事项汇总到 [Plan 操作方案](./plan-operation.md) 定义的最后一个“综合验证与用户验收”小任务，不要求实现代码滞留在未提交工作区等待人工验收。
6. **保持提交边界干净**：每次只提交当前恢复点相关的代码、测试和持久文档，不夹带其他任务或用户尚未要求提交的工作区修改。发现后续问题时允许用新的逻辑提交修正，不改写已经共享的历史。

**Why**：提交历史既要保持逻辑边界，也要承担环境切换和中途接手时的恢复能力；把完整人工验收作为提交门槛会让大型任务长期堆积在单一工作区，增加丢失与冲突风险。

## 2. 图片验证一律交用户

**AI 不解析任何图片用于验证；涉及图片的验证（截图确认、渲染效果比对、图像输出检查）一律交给用户处理。**

1. **不读图**：不读取、解析、分析任何图片文件用于判断 UI 效果或输出正确性。
2. **不绕过**：不以「裁剪」「转 base64」「OCR」等间接手段代替直接读图。
3. **留待用户验证**：任务涉及图片验证时，完成功能代码后提示用户自行验证，而不是尝试解读图片。

**Why**：用户明确要求，避免 AI 对图片内容的解读产生偏差；图片类验证由用户亲自确认。

## 3. 文档影响先判定

**代码任务开始时先判断是否改变持久文档负责的事实；确有影响时先更新权威文档，再写代码。局部实现变化不影响契约、边界、稳定入口、关键流程、扩展方式或验证入口时，不制造文档改动。**

1. **先判定影响**：检查任务是否改变契约、模块职责、稳定代码入口、关键流程、跨模块依赖、扩展点或验证方式。
2. **有影响则先更新**：确认影响持久事实后，先更新对应权威文档，再实现代码；模块缺少必要入口时先补最低可用骨架。
3. **无影响则不改文档**：纯局部实现、等价重构、格式化和 typo 修复不需要为满足流程而改写文档。
4. **按作用域归档**：跨任务复用的强制规则按 [规范总入口](../README.md) 归入 `global/`、技术域目录或 `modules/<module>/`；功能事实写入对应模块文档，不混入通用规范，也不只留在对话或记忆目录。
5. **保持可定位**：所有持久文档遵守 [大型项目可定位文档规范](./llm-readable-documentation.md)，用任务意图、代码入口、关键符号和验证入口缩小实现搜索范围。

**Why**：文档必须先于它描述的行为变化，同时避免为不影响长期知识的代码调整制造噪声和维护成本。

## 4. Review 清单

- [ ] 本次提交是否形成范围清晰、可在其他会话或环境继续的恢复检查点？
- [ ] 是否记录了已执行验证、未执行项、已知失败和下一步命令？
- [ ] 是否只包含当前恢复点相关修改，没有夹带其他任务或用户修改？
- [ ] 是否尝试解析图片代替用户验证？
- [ ] 是否先判断文档影响，并在必要时先更新权威文档？
- [ ] 新增规则是否按作用域归档，功能事实与实现要求是否留在对应模块文档？
