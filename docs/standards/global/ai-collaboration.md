# AI 协作与工作流规范

> **状态**：强制执行。
> **适用范围**：AI 辅助开发与开发者协作时的需求调查、设计确认、实施、提交、验证与文档维护。
> **配套规范**：规范分类与读取顺序见 [开发规范总入口](../README.md)；前端设计语言约束见 [前端设计语言规范](../frontend/design-language.md)。

## 0. 设计确认与连续实施

本节维护本项目的设计授权、开工、暂停与恢复政策。需求调查、设计、项目需求审核及交接前，读取[按场景开展需求调查与设计](../documentation/requirements-design.md)：通用方法选择、主动调研、提问、技术比较、完整设计检查及交接要求由该文档唯一维护。适用于功能开发、问题修复、重构及改变协作方式的文档任务；实施阶段在已确认范围内连续完成，不重复询问已经决定的事项。

计划的文件结构、状态和清理方式遵守[计划规范](../documentation/plans.md)，项目配置与验证权限遵守[项目文档配置](project-documentation.md)。简单、边界明确的修改可以在一次对话中完成设计，不强制建立计划或凑足提问轮数；不能因此省略相关影响检查，也不能把复杂任务伪装成多个简单修改来提前实施。

### 0.1 先调查，再按层次讨论

默认完整设计本次任务的全部范围。只有用户明确批准拆为可独立交付的部分时，才可以分别设计与实施；共同接口、共享数据和前后依赖仍须提前确定。实施步骤的拆分不代表允许把尚未设计的功能留到开发中再决定。

按[方法选择](../documentation/requirements-design.md#2-从当前问题选择方法)和[分层讨论](../documentation/requirements-design.md#3-从整体到细节讨论)识别主要未知，选择适合场景的方法，并核对[结果检查点](../documentation/requirements-design.md#7-结果检查点与返回条件)。检查点可以合并讨论，不新增任务状态或机械审批。

本项目第三方能力依据官方文档与允许的证据核实，不读取依赖安装目录代码，不逆向构建产物。设计期小实验按[通用实验方法](../documentation/requirements-design.md#43-设计期小实验)提出，并在具体范围、环境、费用、验证方法和清理责任获用户授权后执行；不因批准设计方向而获实验或产品修改权限。图片、浏览器及外部操作仍遵守项目限制。

### 0.2 提问与决定如何记录

提问时机、每轮说明和关联影响遵守[提问与关联影响](../documentation/requirements-design.md#32-提问与关联影响)，记录位置遵守[设计记录与实施授权](../documentation/plans.md#21-设计记录与实施授权)。本项目界面行为、数据含义、请求响应、错误处理、权限、费用、保存删除，以及用户、模型和程序职责都须明确并经用户确认；未改变约定的内部写法由执行者安排。设计文档持续维护，终版确认见第 0.6 节。

### 0.3 全链路细节检查

本项目所有功能执行[功能细节检查](../documentation/requirements-design.md#61-功能细节检查)与[双向核对和反例检查](../documentation/requirements-design.md#62-双向核对与反例)，覆盖全部相关前后端、协议、保存与调用方。用户、模型和程序的职责分配须先确认；无关项说明原因，不能借检查增加未经确认的业务机制。已有项目审核使用[场景审核方法](../documentation/requirements-design.md#63-现有项目审核)，审核授权不等于修改授权。

### 0.4 发现上层问题时返回重新设计

细节调查发现整体方向、职责或流程不能成立时，停止基于该方案继续细化，返回最早受影响的设计层。不能靠新增例外、兼容分支、额外确认或未经批准的程序判断掩盖原方案问题。

1. 说明新事实、它与哪项已确认决定冲突，以及影响哪些功能、接口、数据和验收条件；没有证据时明确仍待调查。
2. 将受影响决定及依赖它们的下游设计标为待重新确认，暂停将其用于实施。目标本身有问题时从目标层重来，职责有问题时从职责层重来，不能只修末端表现。
3. 与用户重新确认该层方案，再按第 0.1 节从该层向下完成新的设计周期。所有依赖项都要重新核对，不能沿用与新方案矛盾的旧结论。
4. 没有受影响的事实与有效授权可复用，说明适用依据，不要求用户重答无关问题。用新结论替换失效内容，同步完成条件和未决事项，不保留两套互相冲突的执行方案。

若问题发生在实施中，先按第 0.7 节暂停整项实施。设计返回哪个层次和哪些已有实现受影响要明确记录，不能把自行修改后的行为反写成用户已经同意的规则。

### 0.5 进入实施前的条件

AI 必须逐项复核以下条件，给用户提供最终方案摘要及详细设计入口。详细程度以执行者能直接按约定实现为准，文档篇幅和提问次数不是完成标准。

- [ ] 本次完整范围、目标、必须保持的行为和不包含项明确；拆分交付已有用户批准。
- [ ] 整体方案、各方职责、所有功能行为和跨模块约定已明确并经用户确认；第 0.3 节的适用内容没有遗漏，正常与异常路径相互对应。
- [ ] 影响本次范围的未决问题已解决，没有未经确认的业务假设、“待定”字段或“开发时再决定”的功能设定；不纳入项已有明确范围决定，不能仅改名为后续工作。
- [ ] 关键依赖与可行性有调查依据，调用方、共享文件、数据处理和实施顺序明确；存量大模块的修改方式已按根入口要求选定。
- [ ] 方法选择与场景相符，关键调研证据适用于当前版本和环境，方案比较说明优势、缺陷及项目适配条件，反例检查已处理。
- [ ] 每项需求能对应实现入口和验收结果；必要测试、数据、环境、授权与用户实际验收方式已安排，不能计划把技术排错留给用户。
- [ ] 方案整体复核没有矛盾，正式文档的维护位置已确定；用户明确批准该方案进入实施，授权范围和限制可恢复。
- [ ] 已按[终版与交接要求](../documentation/requirements-design.md#8-终版文档与交接准备)核对接手所需资料；采用其他模型或独立执行者的权限明确，文档自查未冒充独立评审。

用户已经针对完整方案明确要求实施时，直接沿用该授权，不再机械请求一次相同批准。只同意调查、方向、某个选项或文档草案，不等于授权尚未明确的实现。批准实施也不等于最终验收通过，或额外授予部署、收费调用、浏览器操作等权限。

### 0.6 持续完善文档与终版确认

文档持续编写、草稿和正式事实的区别遵守[内容规范](../documentation/content.md#71-设计记录与正式文档)，终版内容与理解检查遵守[终版文档与交接准备](../documentation/requirements-design.md#8-终版文档与交接准备)。本项目实施前必须取得完整终版的确认与实施授权；终版是完整度和确认状态要求，不限制文档写入次数，也不冻结后续设计。

默认由当前执行者完成交接文档自查；确需新会话、其他模型或独立执行者时，先说明收益和成本并取得用户授权。模型能力和成本按[模型分工](../documentation/requirements-design.md#9-模型分工与总成本)评估，沿用本任务已确认 Agent，不自动切换或分配。批准需求不代表实现完成，批准实施不代表最终验收。

纯局部实现变化不需要制造长期文档。纯文档任务以落实已确认规则为实施内容，同样先讨论、后落实，再检查一致性。

### 0.7 实施连续推进与整项暂停

已确认范围内连续完成实现、必要文档同步和最小校验，不逐文件、逐步骤或逐子任务询问“是否继续”，不重复选择已经获准的模型。普通编译错误、实现缺陷、局部写法调整由 AI 自行排查修正，只要没有改变已确认功能及跨模块约定。

出现以下需要用户决定的新问题时，**暂停本任务整项实施**，不能转做同一任务的其他实现部分：

- 需求遗漏或冲突需要新增业务规则、改变交互、数据含义、接口约定、程序与模型职责或完成条件。
- 新事实证明已确认方案不可行，或必须改变整体结构、依赖、旧数据处理方式、费用或授权范围。
- 实际工作区、其他任务或外部条件的变化使原方案不能按约定执行，且无法在现有授权内解决。

暂停后可以继续只读调查、解释方案、更新设计讨论与恢复记录；不能以临时替代、默认值、额外分支或“先做起来”绕过决定。报告必须包括：新事实与依据、影响的原决定及工作范围、可选方案与建议、需要用户决定什么、已完成部分的真实状态。区分当时已知却未处理的遗漏与开发、部署、使用中新取得的事实；若源于前期遗漏，指出遗漏的设计检查项并补齐，不只提出一个局部补丁。不能将所有后期发现都归咎于前期设计，也不能以无法提前预见为由不安排处理。

用户决定后，按第 0.4 节完成必要的重新设计，更新正式约定、受影响计划和验收条件，确认开工条件再次满足才恢复实施。用户已经在新方案中明确要求继续时，不再重复询问；没有恢复授权时不得自行继续。缺少必要环境或工具等执行条件时也须停止无法进行的工作并报告，不能把未执行项写成成功。

新发现的问题按[待处理事项](../documentation/plans.md#31-待处理事项)持续登记，并关联处理工作与验证结果；不能只留在聊天中或全部推迟到最终验收。已确认行为的实现缺陷按现有授权直接修正，不因补记验收项而重新审批整个方案；改变业务行为、范围或完成条件时仍按本节暂停并取得决定。

### 0.8 验证与用户实际验收

设计期明确验证目标与准备条件；实施中仅做约定的必要最小校验。整体实现结束后，先逐项确认需求已有实现、文档与引用同步，再集中执行类型检查、相关测试、构建和必要流程验证，具体范围遵守[测试规范](../../quality/testing/baseline.md)及项目权限。

人工验收由 AI 负责组织、准备、记录和跟进，用户负责必要的真实操作、体验判断及业务决定。交出清单不代表 AI 工作结束。操作卡、结果、延期及最终批准的记录要求统一见[计划规范](../documentation/plans.md#4-最终综合验证与用户验收)。自动检查、真实外部服务结果、实际部署与用户界面验收分别记录，不能互相替代。

1. **准备后再交接。** AI 完成授权范围内的技术验证并处理失败，核对本轮版本、实际入口、必要数据和可访问条件。缺少环境或数据时继续承担可完成的准备；确需用户提供设备、账号条件或权限时，说明具体缺少什么、用户最少需要做什么，以及补齐后由谁继续。准备未完成不能报告为等待用户验收，也不能把技术排错交给用户。
2. **按实际动作协同。** 用户按权限操作浏览器、设备或真实业务，AI 在授权范围内检查日志、接口和保存结果，再由用户确认界面或体验。需要交替执行时按顺序说明各自动作，不把整段过程都归给用户。未获权限的部署、收费请求、主动发送、浏览器和图片操作仍需具体授权。
3. **接收部分反馈。** 用户可以按编号或清晰名称反馈通过、异常或尚未执行，不要求填写正式报告。AI 将反馈对应到具体项目和测试对象，记录已完成部分；含义不清时先利用已有上下文调查，再询问缺少的信息，不能推断其他项目通过。
4. **处理后安排复验。** 不符合已确认设计时，AI 按有效授权定位和修复，完成受影响的技术验证，再说明用户需要重做的最小操作及原因；设计本身需要改变时返回第 0.7 节。入口、环境或准备条件导致无法操作时先处理条件，不直接判业务失败。未变化且仍适用的结论保留。
5. **每次交接明确下一步。** 说明当前在准备、等待操作、分析反馈还是修复复验，下一执行人、具体动作及所需条件；已有计划写入唯一恢复检查点并链接详细记录，无需计划的任务在结果报告中说明。用户暂时无法操作时如实保留未完成项；恢复时检查条件和证据有效性，不要求重做全部已通过项目。没有实际提醒或调度能力时，不承诺自动催办。
6. **主动组织结束确认。** 当前范围必要验收满足后，AI 汇总通过结果、已确认限制及转交事项，明确是否满足结束条件并请求尚缺的最终批准。用户已明确表示对应项目通过且可以结束时沿用该批准，不再机械多问一次；没有回应不等于批准。

### 0.9 已有任务与跨会话恢复

恢复任务时，先核对计划中的当前范围、有效决定、授权、未决问题与实际工作区，再检查剩余工作是否满足本节要求。已有有效确认直接复用，不追溯重做已完成工作，也不凭文档缺少新格式就认定用户从未批准。

剩余设计缺漏先补调查；能从已确认契约确定的内容自行补齐，确需用户决定的内容集中提出。影响实施方向时暂停整项实施并返回相应设计层。不得在恢复记录中把待确认建议自动升级成正式规则，也不得要求用户重新确认没有变化的模型、整体目标和全部既有决定。

恢复验收中的任务时，先确认下一步由谁执行、入口和版本是否仍有效、已收到哪些反馈、哪些修正或条件尚未完成，再按第 0.8 节继续。旧记录只有“待人工验收”时，由 AI 补齐准备与交接信息，不能要求用户重新说明完整背景，也不能把材料缺失当作用户验收拖延。

## 1. 可恢复的阶段性提交

是否建立计划以 [Plan 适用范围](./plan-operation.md#0-是否需要建立计划) 为准。小型即时任务不为提交或验收额外创建计划；下面涉及总计划、子任务和 Plan ID 的要求仅适用于已建立计划的工作，其余任务在结果报告或提交说明中记录必要验证与未完成事项即可。

**大任务必须按[计划规范](../documentation/plans.md#2-拆分与分布执行)拆成小任务，按小任务分别提交。每次提交只对应一个小任务；同一小任务可以有多个提交，不得把多个独立功能放入同一次提交。完整验收不是提交前提，人工验收统一在最终综合验证阶段完成。**

1. **按小任务提交**：先明确功能划分、依赖及提交顺序，再在各小任务范围内形成可继续开发的恢复点。提交授权覆盖多个小任务时，分别提交，不合成一个总任务提交。“同属一个大任务”“本轮收尾”或“需要恢复”都不是合并独立功能的理由。恢复点必须服从小任务边界，也不为凑提交拆出没有独立恢复价值的碎片。
2. **保证可以继续**：提交后的代码、总计划恢复检查点和当前小任务必须足以让新会话、执行者或环境判断已完成内容、剩余步骤、依赖、已执行验证和下一步命令。
3. **跨环境携带上下文**：`docs/plan/` 的根入口、任务 README、未完成子计划和可复用验证说明随对应小任务的恢复检查点同步；`verify/out/` 产物不提交。提交标题说明本小任务的功能或结果，提交说明包含总任务 ID、小任务编号或清晰名称、剩余工作和验证状态，确保切换环境后可从对应 Plan 恢复；不能只写总任务名或笼统的“收尾”。
4. **最小自动验证**：实施过程中只做必要简单校验，整体实现与需求完成核对后集中验证。提交不是最终验收；已执行检查、未执行项和限制按[计划规范](../documentation/plans.md)登记。
5. **同步与验收**：提交或交接前更新当前任务、恢复信息及相关引用，核对本任务新增和临时文件。反馈在总任务及时分配处理，人工验收不阻塞阶段性提交。验证结果与审批材料的维护位置统一遵守计划规范，本文件不复制其规则。
6. **提交前逐项检查边界**：暂存前列出本次授权范围内的小任务及各自拟提交内容；提交前核对暂存差异，每一处都必须属于同一小任务的代码、测试、必要文档或恢复信息。发现包含其他独立功能时先拆分，不因文件共享、改动已集中完成或验证一起执行而整批提交；也不夹带其他任务或用户尚未要求提交的工作区修改。这是执行者每次提交前的必查项，不等待用户提醒。发现后续问题时用新的逻辑提交修正；未经明确授权，不改写已有提交历史。

**Why**：提交历史既要保持逻辑边界，也要承担环境切换和中途接手时的恢复能力；把完整人工验收作为提交门槛会让大型任务长期堆积在单一工作区，增加丢失与冲突风险。

## 2. 图片与截图：一律交用户，除非用户明确授权

**没有用户明确允许，AI 不读取、解析、分析任何图片，也不得启动浏览器截图或读图去理解界面、排查渲染或验证输出；涉及图片的验证（截图确认、渲染效果比对、图像输出检查）一律交给用户处理。用户明确允许、或明确要求由 AI 自己查看图片时除外。**

1. **不读图**：不读取、解析、分析任何图片文件用于判断 UI 效果或输出正确性；不得默认用截图或读图理解页面效果、布局、交互或渲染结果。
2. **不绕过**：不以「裁剪」「转 base64」「OCR」等间接手段代替直接读图。
3. **留待用户验证**：任务涉及图片验证时，完成功能代码后提示用户自行验证，而不是尝试解读图片。
4. **强制原因**：本项目使用的模型不支持图片输入，图片一旦读入上下文会直接报错，导致整个任务中断、无法继续执行。

**Why**：用户明确要求，避免 AI 对图片内容的解读产生偏差；图片类验证由用户亲自确认。此限制同时由项目统一入口 AGENTS.md 强制执行。

## 3. 文档影响先判定

文档影响判定、事实归属与同步要求统一遵守[通用内容规范](../documentation/content.md#6-变更同步矩阵)。相关操作开始前读取；项目目录与验收选择见[项目文档配置](./project-documentation.md)。设计期间的讨论记录与正式文档落实时机见第 0 节。

## 4. 程序与模型的决策边界（强制）

- 只有用户明确要求或确认由程序作出的业务决策，才可以实现为程序规则。AI 可以提出方案，但不能自行决定把模型理解、指代判断、内容选择或操作选择改成关键词、固定窗口、唯一候选等程序判断。
- 需求没有明确某部分交给程序、模型或用户时，必须先列出不明确的边界、方案及影响，与用户核实后再实现；不得以“更稳妥”“节省成本”或“避免歧义”为由自行决定。
- 图片场景由模型理解文字、消息关系和所指图片。用户已确认最近历史默认携图、较早图片按需查询与读取的方向；具体默认范围、数量和工具交互未经确认，不得自行固定。
- 验证必须检查职责分配是否符合用户确认，而不只是检查新增规则的测试是否通过。未经确认的程序规则即使测试通过、接口成功或已部署，也不构成需求完成。

这类越界会将正常表达限制为特定措辞，导致反复返工、时间浪费与额外模型成本；必须在实现前确认职责，而不是上线后让用户纠正。任务恢复时先核对已确认边界，不将现有错误实现反推为需求。

## 5. Review 清单

- [ ] 设计是否从整体到细节完成，功能与跨模块约定已确认，实施授权适用于当前范围？
- [ ] 每项功能的前端、请求响应、后端处理、异常恢复与验收是否对应，没有未确认业务假设？
- [ ] 上层设计出问题时是否返回重设计；实施中新决定是否先整项暂停；已确认事项是否避免重复提问？
- [ ] 大任务是否已按功能拆成小任务，本次提交是否只对应一个小任务，并形成可继续开发的恢复检查点？
- [ ] 是否记录了已执行验证、未执行项、已知失败和下一步命令？
- [ ] 新发现和人工反馈是否已关联处理与验收，下一执行人、具体动作和所需条件是否明确？
- [ ] 是否只包含当前恢复点相关修改，没有夹带其他任务或用户修改？
- [ ] 是否尝试解析图片代替用户验证？
- [ ] 是否先判断文档影响，并在必要时先更新权威文档？
- [ ] 新增规则是否按作用域归档，功能事实与实现要求是否留在对应模块文档？
