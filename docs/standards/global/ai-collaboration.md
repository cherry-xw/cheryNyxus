# AI 协作与工作流规范

> **状态**：强制执行。
> **适用范围**：AI 辅助开发与开发者协作时的需求调查、设计确认、实施、提交、验证与文档维护。
> **配套规范**：规范分类与读取顺序见 [开发规范总入口](../README.md)；前端设计语言约束见 [前端设计语言规范](../frontend/design-language.md)。

## 0. 设计确认与连续实施

本节是本项目需求调查、设计对话、开工条件和实施暂停规则的唯一维护位置。适用于功能开发、问题修复、重构及改变协作方式的文档任务。设计阶段充分调查、持续提问，从整体到细节明确方案；实施阶段在已确认范围内连续完成，不重复询问已经决定的事项。

计划的文件结构、状态和清理方式遵守[计划规范](../documentation/plans.md)，项目配置与验证权限遵守[项目文档配置](project-documentation.md)。简单、边界明确的修改可以在一次对话中完成设计，不强制建立计划或凑足提问轮数；不能因此省略相关影响检查，也不能把复杂任务伪装成多个简单修改来提前实施。

### 0.1 先调查，再按层次讨论

默认完整设计本次任务的全部范围。只有用户明确批准拆为可独立交付的部分时，才可以分别设计与实施；共同接口、共享数据和前后依赖仍须提前确定。实施步骤的拆分不代表允许把尚未设计的功能留到开发中再决定。

| 层次 | AI 先调查和说明 | 与用户确认的结果 |
| --- | --- | --- |
| 目标与范围 | 用户要解决的问题、现有行为、使用者及使用场景、已有约束、成功条件 | 要达到的结果、本次包含和不包含什么、哪些行为必须保持；区分举例与硬性要求 |
| 整体方案与职责 | 现有架构和实际调用方、可复用能力、主要方案及取舍、依赖与可行性 | 采用的整体方向；用户、模型、程序及各模块分别负责什么；必要的旧功能替换和数据处理选择 |
| 完整功能流程 | 从入口到最终结果的完整操作、状态变化、数据流与副作用，覆盖正常和失败情况 | 每项功能的行为、可操作范围、完成含义、异常反馈与恢复方式 |
| 接口与交互细节 | 按第 0.3 节检查前端、后端、请求响应、持久保存和其他调用方是否对应 | 所有功能设定及跨模块约定，不能只确认界面外观或接口名称 |
| 整体复核 | 把所有功能重新连起来，检查矛盾、遗漏、依赖和验收准备 | 第 0.5 节的开工条件成立，明确最终方案和实施授权 |

上层方向未明确时，可以调查下层以判断可行性，但不能把下层猜测当作确定方案，更不能据此修改产品实现。各层按实际需要进行多轮讨论；用户的回答引出新影响时，继续追问直到相关问题解决。

调查从权威模块文档进入项目源码、类型和相关测试，核对实际入口、读写双方及调用方。既有实现只能证明当前行为，不能替用户决定目标行为。第三方能力依据官方文档及可核查的既有证据，不读依赖安装目录中的代码，不逆向构建产物。决定方案可行性的未知能力必须先核实，不能标为“实施时再看”。

### 0.2 提问与决定如何记录

1. **先查能查明的事实。** 已有文档、源码和用户已确认决定能回答的问题，由 AI 自行核对，不把调查工作转交用户。文档与实现冲突时说明两者差异，不默选其中之一作为需求。
2. **按层次和关联主题提问。** 先确认目标和方向，再细化功能与跨模块约定；不在方向未定时一次抛出大量字段和局部选项。每个问题说明当前事实、缺少的决定、不同选择对体验与实现的影响，以及有依据的建议。方案比较应包含实际存在的成本、数据和依赖差异。
3. **用户确认功能及跨模块约定，AI 安排内部写法。** 界面行为、数据含义、请求响应、错误处理、权限、费用、保存删除、程序与模型职责等必须写清并交用户确认。未改变这些约定的函数拆分、局部变量、内部代码组织由 AI 自行安排；不能以“技术细节”为由擅自决定用户行为，也不要求用户逐个审批内部名称。
4. **每轮回答都检查关联影响。** 更新当前结论，检查它是否改变前端操作、后端规则、共享协议、数据、其他调用方或验收；新产生的实质问题放入下一轮讨论。不能只记住用户选项而保留与它矛盾的其他设计。
5. **区分四类信息。** 已调查事实附依据；用户已确认决定写明适用范围；候选方案明确未获批准；未决问题写出影响及需要谁回答。用户未回应、没有反对或 AI 推荐均不等于批准。已确认的答案不重复提问，除非出现改变其适用性的事实，并明确说明变化。
6. **文档随讨论持续完善。** 需要计划的任务，在计划中维护当前结论、候选方案和未决问题，保留恢复所需信息；可以随讨论反复编写和修改设计文档、规范及模块说明中的相关内容。未确认内容明确标为草稿或待确认，不覆盖现行有效规则、不冒充已批准要求。小型任务可在对话中记录。实施前按第 0.6 节完成终版整理与确认，不限制此前的文档更新次数。

设计记录只维护当前有效内容，不复制逐轮聊天记录、失效方案或 AI 修改历史。需求和完成条件使用稳定编号或清晰名称，方便设计、实现与验收互相对应；不要为同一决定建立多份独立表格。

### 0.3 全链路细节检查

对本次每项功能，从“用户或外部入口触发 → 请求 → 后端处理与保存 → 响应或事件 → 使用者看到结果 → 失败恢复”完整走查，核对下列适用内容。已有可靠约定可直接引用，新增或改变的约定必须明确到实施者无需另做业务选择。无关项说明不适用原因，不为了填表新增功能。

| 方面 | 设计必须回答的问题 |
| --- | --- |
| 场景与职责 | 谁在什么条件下操作、作用于哪个对象、期望什么结果？判断由用户、模型还是程序完成？哪些行为不允许发生？ |
| 前端入口与操作 | 入口在哪里、用户能否发现、需要哪些上下文和输入？默认值与校验依据是什么？何时可操作、何时禁用、为何禁用？提交、取消、关闭和返回如何处理？ |
| 前端状态与反馈 | 初始、加载、空数据、编辑、提交中、成功、失败、无权限和连接中断时显示什么、允许什么动作？草稿如何保留，何时刷新？涉及会话切换、多窗口或多种界面时，各自如何保持一致？必要的窄窗口、键盘操作和帮助入口如何处理？ |
| 请求与响应 | 调用入口和方法、身份与目标对象、请求及响应字段的类型、必填性、默认值、单位、取值范围、缺失与空值含义是什么？谁产生和校验？成功、失败及结果未知如何区分？相关字段如何对应界面输入与显示？涉及分页、过滤和排序时如何约定？ |
| 事件与异步流程 | 请求、任务和事件如何关联？“已接受”“已保存”“已生效”“已完成”分别由什么事实证明？如何处理流式过程、延迟响应、顺序颠倒、重复事件、取消与完成同时发生，以及订阅恢复？不使用这些机制时无需新增。 |
| 后端处理与持久保存 | 从接口到业务处理再到存储的真实路径是什么？校验顺序、状态变化、写入与生效时机、关联副作用是什么？多次操作或并发修改如何处理，是否允许部分成功？哪些数据需要重启后保留，谁读写和清理？ |
| 异常与恢复 | 输入无效、对象不存在、权限变化、超时、网络中断、服务失败、保存失败时，接口返回什么、用户看到什么、已发生的动作怎样处理？是否允许重试、由谁触发、怎样避免重复副作用？结果未知时如何查询确认？ |
| 数据与权限边界 | 哪个身份可读写哪个对象？不同用户、会话、连接和模块如何隔离？敏感字段怎样保存、返回与记录？保留、删除和历史访问的规则是否已明确？ |
| 依赖、迁移与其他调用方 | 哪些客户端、插件、工具、后台任务和配置模板也使用同一规则？外部服务与库是否支持所需能力？需要什么配置和运行环境？旧接口、旧入口及存量数据怎样处理，实施顺序有何约束？ |
| 验证与交付 | 每个目标怎样观察到成功和失败？哪些由 AI 自动验证，哪些需要真实服务、设备或用户操作？测试入口、数据、环境、已有授权和必要准备是否明确？实际交付是否包含部署，用户从哪里验收？ |

对新增或变化的接口，应提供足以核对含义的正常请求响应和关键失败示例；异步功能补充必要的消息顺序或状态表。字段表、示例、前端显示和后端保存必须相互一致，不能分别写完却没有共同检查。

整体复核至少按两个方向进行：先从每个用户操作检查请求、处理和最终反馈是否完整，再从每个界面结果倒查它需要的字段由谁产生、何时更新、是否实际可取得。对关键失败情况也做同样检查，防止出现前端需要但后端未提供的数据、接口有结果但界面没有反馈，或请求成功却没有完成用户目标。

例如“保存设置”不能只写“点击按钮调用保存接口”。还需明确哪些内容被保存、是否立即生效、成功响应证明什么、失败后草稿是否保留，以及重复提交、并发修改和响应丢失如何处理。具体选择由该功能的已确认需求决定，本规范不预设某一种业务策略。

设计中应能逐项对应以下内容，可放在现有任务表或验收表中，不强制另建重复文件：

| 需求或场景 | 已确认的行为与异常结果 | 设计或契约位置 | 实现入口与调用方 | 验证方式及预期结果 |
| --- | --- | --- | --- | --- |
| 使用稳定编号或清晰名称 | 写可观察结果，不只写“支持某能力” | 引用唯一维护位置 | 已有入口写实际路径与关键符号；拟新增入口明确标注 | 区分自动检查与用户实际验收，列明必要前提 |

### 0.4 发现上层问题时返回重新设计

细节调查发现整体方向、职责或流程不能成立时，停止基于该方案继续细化，返回最早受影响的设计层。不能靠新增例外、兼容分支、额外确认或未经批准的程序判断掩盖原方案问题。

1. 说明新事实、它与哪项已确认决定冲突，以及影响哪些功能、接口、数据和验收条件；没有证据时明确仍待调查。
2. 将受影响决定及依赖它们的下游设计标为待重新确认，暂停将其用于实施。目标本身有问题时从目标层重来，职责有问题时从职责层重来，不能只修末端表现。
3. 与用户重新确认该层方案，再按第 0.1 节从该层向下完成新的设计周期。所有依赖项都要重新核对，不能沿用与新方案矛盾的旧结论。
4. 没有受影响的事实与有效授权可复用，说明适用依据，不要求用户重答无关问题。用新结论替换失效内容，同步完成条件和未决事项，不保留两套互相冲突的执行方案。

若问题发生在实施中，先按第 0.7 节暂停整项实施。设计返回哪个层次和哪些已有实现受影响要明确记录，不能把自行修改后的行为反写成用户已经同意的规则。

### 0.5 进入实施前的条件

AI 必须逐项复核以下条件，给用户提供最终方案摘要及详细设计入口。详细程度以执行者能直接按约定实现为准，文档篇幅和提问次数不是完成标准。

- [ ] 本次完整范围、目标、必须保持的行为和不包含项明确；拆分交付已有用户批准。
- [ ] 整体方案、各方职责、所有功能行为和跨模块约定已明确并经用户确认；第 0.3 节的适用内容没有遗漏，正常与异常路径相互对应。
- [ ] 影响本次范围的未决问题已解决，没有未经确认的业务假设、“待定”字段或“开发时再决定”的功能设定；不纳入项已有明确范围决定，不能仅改名为后续工作。
- [ ] 关键依赖与可行性有调查依据，调用方、共享文件、数据处理和实施顺序明确；存量大模块的修改方式已按根入口要求选定。
- [ ] 每项需求能对应实现入口和验收结果；必要测试、数据、环境、授权与用户实际验收方式已安排，不能计划把技术排错留给用户。
- [ ] 方案整体复核没有矛盾，正式文档的维护位置已确定；用户明确批准该方案进入实施，授权范围和限制可恢复。

用户已经针对完整方案明确要求实施时，直接沿用该授权，不再机械请求一次相同批准。只同意调查、方向、某个选项或文档草案，不等于授权尚未明确的实现。批准实施也不等于最终验收通过，或额外授予部署、收费调用、浏览器操作等权限。

### 0.6 持续完善文档与终版确认

文档是设计讨论的工作材料，应随调查、提问、回答和重新设计持续编写、修改与完善。已经明确的内容可以及时落实到对应规范、共享契约或模块文档；仍待确认的内容保留清晰状态，不能被当成现行规则。计划保留当前执行范围、用户授权、依赖、完成条件与恢复信息，正式规则只有一个维护位置。

“最终落实文档”指实施前形成完整、相互一致且经用户确认的终版，不是只允许一次写入，也不是必须等讨论全部结束才能写文档。终版整理应统一当前有效决定，解决影响本次范围的未决问题，清除失效或冲突的设计并核对引用，再按授权修改实现。终版也不是永不修改；后续需要改变已确认约定时，按重新设计流程更新并确认新的终版。

已批准要求与当前实现是两种事实：批准的契约可以先明确，但功能尚未实现或尚未验证时必须说明，不能宣称已可用。调查期间的候选方案不能进入正式规则；已经失效的设计不能继续作为实施依据。实现过程中及时更新真实实现状态、入口和引用，不在收尾时凭记忆补写。

纯局部实现变化不需要制造长期文档。纯文档任务以落实已确认规则为实施内容，同样先讨论、后落实，再检查一致性。

### 0.7 实施连续推进与整项暂停

已确认范围内连续完成实现、必要文档同步和最小校验，不逐文件、逐步骤或逐子任务询问“是否继续”，不重复选择已经获准的模型。普通编译错误、实现缺陷、局部写法调整由 AI 自行排查修正，只要没有改变已确认功能及跨模块约定。

出现以下需要用户决定的新问题时，**暂停本任务整项实施**，不能转做同一任务的其他实现部分：

- 需求遗漏或冲突需要新增业务规则、改变交互、数据含义、接口约定、程序与模型职责或完成条件。
- 新事实证明已确认方案不可行，或必须改变整体结构、依赖、旧数据处理方式、费用或授权范围。
- 实际工作区、其他任务或外部条件的变化使原方案不能按约定执行，且无法在现有授权内解决。

暂停后可以继续只读调查、解释方案、更新设计讨论与恢复记录；不能以临时替代、默认值、额外分支或“先做起来”绕过决定。报告必须包括：新事实与依据、影响的原决定及工作范围、可选方案与建议、需要用户决定什么、已完成部分的真实状态。若源于前期遗漏，指出遗漏的设计检查项并补齐，不只提出一个局部补丁。

用户决定后，按第 0.4 节完成必要的重新设计，更新正式约定、受影响计划和验收条件，确认开工条件再次满足才恢复实施。用户已经在新方案中明确要求继续时，不再重复询问；没有恢复授权时不得自行继续。缺少必要环境或工具等执行条件时也须停止无法进行的工作并报告，不能把未执行项写成成功。

### 0.8 验证与用户实际验收

设计期明确验证目标与准备条件；实施中仅做约定的必要最小校验。整体实现结束后，先逐项确认需求已有实现、文档与引用同步，再集中执行类型检查、相关测试、构建和必要流程验证，具体范围遵守[测试规范](../../quality/testing/baseline.md)及项目权限。

交用户前，AI 应完成授权范围内的技术验证并处理失败，提供实际可进入的验收入口、准备条件、操作和期望结果。自动检查、真实外部服务结果、实际部署与用户界面验收分别记录；不能互相替代。未完成项或缺少的条件如实说明，不能把有已知缺漏的任务说成“只剩用户看一眼”。

用户主要确认真实使用、界面交互和最终结果，不负责通过反复试错替 AI 补需求和定位技术错误。验收发现实现不符合已确认设计时，直接修正并按影响重验；发现设计本身需要改变时，返回设计流程。最终审批与计划清理仍按[计划规范](../documentation/plans.md#4-最终综合验证与用户验收)执行。

### 0.9 已有任务与跨会话恢复

恢复任务时，先核对计划中的当前范围、有效决定、授权、未决问题与实际工作区，再检查剩余工作是否满足本节要求。已有有效确认直接复用，不追溯重做已完成工作，也不凭文档缺少新格式就认定用户从未批准。

剩余设计缺漏先补调查；能从已确认契约确定的内容自行补齐，确需用户决定的内容集中提出。影响实施方向时暂停整项实施并返回相应设计层。不得在恢复记录中把待确认建议自动升级成正式规则，也不得要求用户重新确认没有变化的模型、整体目标和全部既有决定。

## 1. 可恢复的阶段性提交

是否建立计划以 [Plan 适用范围](./plan-operation.md#0-是否需要建立计划) 为准。小型即时任务不为提交或验收额外创建计划；下面涉及总计划、子任务和 Plan ID 的要求仅适用于已建立计划的工作，其余任务在结果报告或提交说明中记录必要验证与未完成事项即可。

**完整验收不是提交前提。提交的首要标准是形成范围清晰、可继续开发的恢复检查点；一个小任务可以跨多个提交，人工验收统一在最终综合验证阶段完成。**

1. **按恢复点提交**：完成一段逻辑相关且状态明确的工作后即可提交，不要求当前小任务或总任务已经完成；不得为了凑提交拆出没有独立恢复价值的碎片。
2. **保证可以继续**：提交后的代码、总计划恢复检查点和当前小任务必须足以让新会话、执行者或环境判断已完成内容、剩余步骤、依赖、已执行验证和下一步命令。
3. **跨环境携带上下文**：`docs/plan/` 的根入口、任务 README、未完成子计划和可复用验证说明随阶段检查点提交；`verify/out/` 产物不提交。提交说明仍应包含总任务 ID、当前小任务、剩余工作和验证状态，确保切换环境后可从对应 Plan 恢复。
4. **最小自动验证**：实施过程中只做必要简单校验，整体实现与需求完成核对后集中验证。提交不是最终验收；已执行检查、未执行项和限制按[计划规范](../documentation/plans.md)登记。
5. **同步与验收**：提交或交接前更新当前任务、恢复信息及相关引用，核对本任务新增和临时文件。反馈在总任务及时分配处理，人工验收不阻塞阶段性提交。验证结果与审批材料的维护位置统一遵守计划规范，本文件不复制其规则。
6. **保持提交边界干净**：每次只提交当前恢复点相关的代码、测试和持久文档，不夹带其他任务或用户尚未要求提交的工作区修改。发现后续问题时允许用新的逻辑提交修正，不改写已经共享的历史。

**Why**：提交历史既要保持逻辑边界，也要承担环境切换和中途接手时的恢复能力；把完整人工验收作为提交门槛会让大型任务长期堆积在单一工作区，增加丢失与冲突风险。

## 2. 图片与截图：一律交用户，除非用户明确授权

**没有用户明确允许，AI 不读取、解析、分析任何图片，也不得启动浏览器截图或读图去理解界面、排查渲染或验证输出；涉及图片的验证（截图确认、渲染效果比对、图像输出检查）一律交给用户处理。用户明确允许、或明确要求由 AI 自己查看图片时除外。**

1. **不读图**：不读取、解析、分析任何图片文件用于判断 UI 效果或输出正确性；不得默认用截图或读图理解页面效果、布局、交互或渲染结果。
2. **不绕过**：不以「裁剪」「转 base64」「OCR」等间接手段代替直接读图。
3. **留待用户验证**：任务涉及图片验证时，完成功能代码后提示用户自行验证，而不是尝试解读图片。
4. **强制原因**：本项目使用的模型不支持图片输入，图片一旦读入上下文会直接报错，导致整个任务中断、无法继续执行。

**Why**：用户明确要求，避免 AI 对图片内容的解读产生偏差；图片类验证由用户亲自确认。此限制同时由项目统一入口 AGENTS.md 强制执行。

## 3. 文档影响先判定

文档影响判定、事实归属与同步要求统一遵守[通用内容规范](../documentation/content.md#6-变更同步矩阵)。相关操作开始前读取；项目目录与验收选择见[项目文档配置](./project-documentation.md)。设计期间的讨论记录与正式文档落实时机见第 0 节。

## 4. Review 清单

- [ ] 设计是否从整体到细节完成，功能与跨模块约定已确认，实施授权适用于当前范围？
- [ ] 每项功能的前端、请求响应、后端处理、异常恢复与验收是否对应，没有未确认业务假设？
- [ ] 上层设计出问题时是否返回重设计；实施中新决定是否先整项暂停；已确认事项是否避免重复提问？
- [ ] 本次提交是否形成范围清晰、可在其他会话或环境继续的恢复检查点？
- [ ] 是否记录了已执行验证、未执行项、已知失败和下一步命令？
- [ ] 是否只包含当前恢复点相关修改，没有夹带其他任务或用户修改？
- [ ] 是否尝试解析图片代替用户验证？
- [ ] 是否先判断文档影响，并在必要时先更新权威文档？
- [ ] 新增规则是否按作用域归档，功能事实与实现要求是否留在对应模块文档？
