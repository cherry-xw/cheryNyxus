## 1. 未验收不提交

**功能在完全验收通过之前，不得直接提交代码；阶段内的中间调整只保留在工作区，不提交。**

1. **一次功能一次提交**：一个功能在持续调整、测试直到完全验收通过之后，再一次性提交。
2. **中间调整不提交**：验收过程中的迭代修改只保留在工作区；验收失败继续在同一工作区迭代，直到通过。
3. **禁止修复提交**：未验收就提交会导致后续修改必须以「修复提交」追加，污染提交历史。
4. **与全局节奏协调**：验收通过后按「每个完整阶段性任务提交一次」的节奏提交，不做无意义的碎片提交。

**Why**：用户希望提交历史干净——一个功能对应一次完整提交，而非功能 + 一串修复补丁。

## 2. 图片验证一律交用户

**AI 不解析任何图片用于验证；涉及图片的验证（截图确认、渲染效果比对、图像输出检查）一律交给用户处理。**

1. **不读图**：不读取、解析、分析任何图片文件用于判断 UI 效果或输出正确性。
2. **不绕过**：不以「裁剪」「转 base64」「OCR」等间接手段代替直接读图。
3. **留待用户验证**：任务涉及图片验证时，完成功能代码后提示用户自行验证，而不是尝试解读图片。

**Why**：用户明确要求，避免 AI 对图片内容的解读产生偏差；图片类验证由用户亲自确认。

## 3. 文档影响先判定

**代码任务开始时先判断是否改变持久文档负责的事实；确有影响时先更新权威文档，再写代码。局部实现变化不影响契约、边界、稳定入口、关键流程、扩展方式或验证入口时，不制造文档改动。**

1. **先判定影响**：检查任务是否改变契约、模块职责、稳定代码入口、关键流程、跨模块依赖、扩展点或验证方式。
2. **有影响则先更新**：确认影响持久事实后，先更新对应权威文档，再实现代码；模块缺少必要入口时先补最低可用骨架。
3. **无影响则不改文档**：纯局部实现、等价重构、格式化和 typo 修复不需要为满足流程而改写文档。
4. **按作用域归档**：跨任务复用的强制规则按 [规范总入口](../README.md) 归入 `global/`、技术域目录或 `modules/<module>/`；功能事实写入对应模块文档，不混入通用规范，也不只留在对话或记忆目录。
5. **保持可定位**：所有持久文档遵守 [大型项目可定位文档规范](./llm-readable-documentation.md)，用任务意图、代码入口、关键符号和验证入口缩小实现搜索范围。

**Why**：文档必须先于它描述的行为变化，同时避免为不影响长期知识的代码调整制造噪声和维护成本。
