## 1. 未验收不提交

**功能在完全验收通过之前，不得直接提交代码；阶段内的中间调整只保留在工作区，不提交。**

1. **一次功能一次提交**：一个功能在持续调整、测试直到完全验收通过之后，再一次性提交。
2. **中间调整不提交**：验收过程中的迭代修改只保留在工作区；验收失败继续在同一工作区迭代，直到通过。
3. **禁止修复提交**：未验收就提交会导致后续修改必须以「修复提交」追加，污染提交历史。
4. **与全局节奏协调**：验收通过后按「每个完整阶段性任务提交一次」的节奏提交，不做无意义的碎片提交。

**Why**：用户希望提交历史干净——一个功能对应一次完整提交，而非功能 + 一串修复补丁。

## 2. 图片验证一律交用户

**AI 不解析任何图片用于验证；涉及图片的验证（截图确认、渲染效果比对、图像输出检查）一律交给用户处理。**

1. **不读图**：不读取、解析、分析任何图片文件用于判断 UI 效果或输出正确性。
2. **不绕过**：不以「裁剪」「转 base64」「OCR」等间接手段代替直接读图。
3. **留待用户验证**：任务涉及图片验证时，完成功能代码后提示用户自行验证，而不是尝试解读图片。

**Why**：用户明确要求，避免 AI 对图片内容的解读产生偏差；图片类验证由用户亲自确认。

## 3. 文档先行（确认）

**任何任务执行前，先修改涉及模块的 `docs/` 文档，再写代码；纯文档/纯阅读/搜索/解释类任务不触发。**

1. **第一步动文档**：接到任务（含 bug 修复、重构、新功能、配置变更）时，先更新对应模块文档，再动代码。
2. **缺文档先补骨架**：任务涉及的模块尚无文档，先在 `docs/` 下补出对应骨架，再实现。
3. **禁止先改后补**：「先改代码再补文档」或「代码文档同时改」均视为违规；纯重构、格式化、typo 修复豁免。
4. **规范唯一归集**：任何新规范、修订、裁决一律落入 `docs/standards/`（见 [README.md](./README.md) 第 3 条），不散落在对话或记忆目录。

**Why**：项目 CLAUDE.md 已声明 Doc-First，但执行不到位，2026-07-13 用户明确强化为硬约束。

## 4. 读规范凭证（强制）

**每个写入型任务动手前，必须阅读涉及规范，并在不提交的凭证目录写入一条带时分秒命名的 txt，作为「已读规范 + 将按规范执行」的物理凭证，杜绝跳过读规范直接操作。**

1. **凭证目录**：`E:\dev\cheryClaw\.claude\read-proof\`（已加入 `.gitignore`，不随代码提交，仅本地留存供用户抽查）。
2. **文件名**：读取时刻的时分秒（`HHmmss.txt`）；内容首行带日期，防跨天同名混淆。
3. **触发**：每个**写入型任务**（代码 bug 修复 / 重构 / 新功能 / 配置变更 / 文档修改）动手前，先读 `docs/standards/README.md` 操作声明 + 本任务涉及的模块规范，**读毕立即写凭证**；纯阅读 / 搜索 / 解释类任务（无写入）不触发。
4. **内容**：一句话读后评论——读到哪些规范 + 本任务将如何按规范执行。空泛的「已读规范」不算，须能证明理解。例：`已读 ui-visual-and-interaction.md §1/§3：字重正文一律 400、新元素全直角(border-radius:0)，本任务按钮与面板均按此执行。`
5. **验证**：用户可随时查看该目录，确认每个时段动手前确有读规范行为且理解正确；**缺失凭证即视为跳过读规范，该次操作不受认可**，可要求补证后重做。
6. **豁免**：本规范自身的修订不触发凭证（避免自证死循环）；单个会话内连续多次小改可只写一条，但覆盖本会话所有任务。

**Why**：仅靠文档声明无法保证 AI 每次动手前真的读规范；留下时间戳凭证让「读规范」这一步可被抽查、可被追溯。
